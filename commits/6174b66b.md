## Decompiled

**Fact.** Five more StatIndex handlers (`DoMoveLowerAccuracy1`,
`DoMoveSweetScent`, `DoMoveNastyPlot`, `DoMoveSwordsDance`, `DoMoveTailGlow`),
plus four that leave the template and one unrelated function:

- **`DoMoveBlowback`** passes the *attacker's own* `action.direction`, read as
  `GetEntInfo(attacker)->action.direction`. The asm's `[r0,#0xB4]` then
  `[r2,#0x4C]` lands on `entity::info` and `monster::action` + 2, which is
  `action.direction` — the same field `SetLeaderAction` uses.
- **`DoMoveHiddenPower`** forwards `move` and `item_id` to `DealDamage` with a
  `0x100` multiplier, the fifth argument passed on the stack.
- **`DoMoveDecoy`** passes three constants, the last on the stack.
- **`DoMovePsychoShift`** guards on `attacker != defender` before transferring.
- **`DebugRecruitingEnabled`** returns `TRUE` unconditionally.
  `include/dungeon_recruitment.h` already declares it, so its signature is
  given, not guessed — the only function in this run of fifty for which that is
  true.

## One function was dropped rather than forced

**Fact.** `DoMoveCharm` was the intended tenth and is **not** in this commit. It
forwards to `ApplyOffensiveStatMultiplier` (declared in `move_orb_effects.h`
with an `fx32_8` multiplier), and the obvious candidate scores 405: the target
schedules the fifth argument as `mov ip, #1` early and stores it later, while
the candidate emits `mov r3, #1` / `str r3, [sp]` together. The constant is
right (`0x80`; `FX32_CONST(0.5)` gives `0x800` and is wrong).

It is a scheduling difference, not a logic one, and it stays in asm. Recorded
so the next attempt starts from the diff rather than from scratch.
