## Landing shape — a head merge, so the object is renamed, not split

**Fact.** All five functions are at the *head* of the `.s`, and `main.lsf`
listed `asm/overlay_11_023090DC.o` immediately after `src/overlay_11_02307334.o`.
`extract_function.py`'s merge-at-file-start branch therefore applies: the
functions join the preceding `src` object, and the asm remainder is rebased on
its new first address.

- `asm/overlay_11_023090DC.s` → `asm/overlay_11_02309EE4.s` (−1049 lines)
- `asm/include/overlay_11_023090DC.inc` → `asm/include/overlay_11_02309EE4.inc`
  (−51 `.public` lines — the symbols only the five removed functions referenced)
- `main.lsf` changes **one line in place**; the object count is unchanged.

This is the opposite shape from [`f8eaf87f`](f8eaf87f.md), where the function sat
at position 145 of 215 and the file genuinely split into two objects.

## The four small functions

All four are short enough that the asm is close to self-documenting; each is a
straightforward read and each reached score 0 in all three regions.

`ov11_02309E48` is the one carrying real evidence for the rest of the commit.
**Fact**, from its target asm at `cad4a75f`:

```asm
	mov r0, #0x34
	mov r1, #0
	bl MemAlloc
	...
	ldr r0, [r4, r6, lsl #3]      ; stride 8 — the entry size
	add r1, r4, r6, lsl #3
	cmp r0, #1
	bne _02309E9C
	ldrsh r0, [r1, #4]            ; field_0x4 is signed 16-bit
```

So `sizeof(struct unk_02309EE4) == 0x34` is not inferred — it is an **immediate
in the target**, and the landed C spells it `MemAlloc(sizeof(struct
unk_02309EE4), 0)`, which makes the compiler enforce it. Likewise the 8-byte
stride and the signed-halfword `field_0x4` of `struct unk_0230A044`.

**Naming a type for that 8-byte entry was load-bearing, not cosmetic** (LEDGER
finding E): both `ov11_02309E48` and `ov11_023090DC` hoist `&list[i]` into a
register once and reach both the tag and `field_0x4` through it. With the entry
as an anonymous inner struct there is no way to spell that local pointer and
MWCC recomputes the address in each arm. Naming it took `ov11_02309E48` from
score 355 to 0.

## `ov11_023090DC` — structure first, then one register permutation

The ledger records the score history: **13624 → 7607 → 7151 → 2948 → 2548 →
2233 → 1245 → 295 → 230**, and then 230 → 0 by the rule below.

### The structural finding: the 0x11C sub-object is its own type

**The strongest piece of evidence in the run.** Case 0 keeps **one** pointer,
`r4 = p + 0x11C`, and reaches six different fields through it (**fact** — all
six displacements read off the asm, all six landing on the right absolute
offset):

| C | absolute offset | instruction |
|---|---|---|
| `lst->field_0x0.field_0x0[i]` | 0x11C | `ldr [r4, i lsl 3]` |
| `lst->field_0x0.field_0x30` | 0x14C | `ldr [r4, #0x30]` |
| `lst->field_0x34` | 0x150 | `str [r4, #0x34]` |
| `lst->field_0x38` | 0x154 | `add r7, r4, #0x38` |
| `lst->field_0x70[i]` | 0x18C | `strb [r4 + i, #0x70]` |
| `lst->field_0x76[n]` | 0x192 | `add r6, r4, #0x76` |

Declared as flat members of `unk_02324D90` and addressed from `p`, MWCC emits
`strb [r0, #0x18C]`, `str [r9, #0x150]`, `add r0, r9, #0x92` — a different
instruction every time — and keeps `p` live in a register the target never uses.
Moving to a nested type took 7151 → 2948 and made the candidate's row count
exactly equal the target's.

**Inference**, and a reviewer may push back: that the sub-object is a distinct
*type* rather than MWCC choosing a common base register for flat members. The
counter-evidence would be some other source shape that also yields one base;
none was found.

A separate corroboration of the capacity, **fact** from the landed layout:
`field_0x0[6]`, `field_0x70[6]` and `field_0x76[6][0x100]` all hold six, and
`field_0x38[7]` holds six plus the terminator the loop writes
(`w->field_0x0 = 0; w->field_0x4 = -1;`).

### What closed the last 35 rows

At score 230 the function was at **`STRUCT 0`** — every instruction the right
instruction in the right place, with the right immediates and branch targets;
820 target rows against 820 candidate rows. What remained was a single register
permutation confined to case 0:

| role | target | candidate at 230 |
|---|---|---|
| `n` (string-buffer counter) | `r8` | `r6` |
| `move_id` (loop 1) | `r6` | `r8` |
| `lst->field_0x76` base (loop 2) | `r6` | `r9` |
| loop 2's `i` | `sl` | `r8` |
| loop 2's `e` / `gm` / `tm`, then `q` | `r9` | `sl` |

The ledger's entry #6 reads **"Declaration order — EXHAUSTED, three times
over"**: all 120 permutations of the five case-0 register variables, against
each of three successive body shapes, plus inner-scope permutations, plus
split declaration/assignment, plus function/case/loop scope for four of them.
Entries #7–#13 close off loop-counter identity, prologue statement order,
coupling to the other 27 cases, the function-scope aggregates, `p`/`lst` as
variables, a `static inline` helper, and `q`'s placement and type — every one
measured, every one inert.

The ledger's *untried direction #5* then says, in its own words, that the only
thing left is to read MWCC's allocator behaviour directly rather than sweep —
**and that is what closed it.** The rule, as measured and now written up in
`docs/MATCHING_TIPS.md` → *MWCC colours the long-lived locals in DECLARATION
ORDER*:

> the locals that live across a call take `r4, r5, r6, r7, r8 …` in **case-scope
> declaration order**, lowest free register first. A variable assigned only
> inside a loop body does **not** join that group from case scope — it goes to
> `fp` from every position.

So a body with four qualifying locals (`lst`, `mode`, `n`, `w`) can only ever
paint them `r4`–`r7`. The target puts one on `r8`, so **a fifth member has to
exist**, and no permutation of four will find it. Hoisting `e`, `move_id`, `k`
and `q` out of the loop bodies into case 0's declaration list supplies the fifth.
No statement moved and no type changed.

Two things about this a reviewer should weigh:

- **The earlier sweep was not wrong, it was under-populated.** A negative result
  on an ordering sweep is only as general as the *set* swept. That is the
  transferable lesson and it is why the tips entry says to record which
  variables were in the set.
- **The source shape is not uniquely determined.** The tips entry records **two
  independent routes to score 0**, found by separate agents: the case-scope
  hoist that landed, and one shared `e` for both loops (230 → 105) followed by a
  C89 hoist to function scope with the `e, move_id, w, n` fragment (105 → 0).
  Only that triple's internal order is pinned; positions 4–10 all score 0. The
  bytes do not say which the original was.

### Shapes in the landed C that look wrong

| where | the shape | status |
|---|---|---|
| the four `PreprocessString` arms | `q = n * 0x100;` written **four times**, once per arm | measured; see below |
| case 0 prologue | `v_flag = 0; n = v_flag; ... v_sel = n;` — three zeros through a `bool8` | `bool8 v_flag` is measured (295 → 230); **the chained spelling is not recorded as measured anywhere** |
| loop 1 | `move_id = GetItemMoveId16(item_id);` inside the loop, with a loop-invariant argument | forced: the target calls it per iteration (**fact** — a call cannot be elided without changing bytes) |
| loop 1 | `monster_id` and `k` are assigned only in the `field_0x0 == 1` and `== 2` arms, then read unconditionally afterwards | see open questions |
| case 7 | a genuine `#ifdef JAPAN` fork | **fact**, see *Regions* |

On the repeated `q`: the target computes the `PreprocessString` destination **at
each of the four call sites** and separately keeps `n << 8` alive across the
call (`add r0, r6, r8, lsl #8` per site; `lsl r9, r8, #8` saved; then
`add r0, r6, r9` in the tail). That only happens when the call's address and the
stored pointer are different *values* — otherwise MWCC commons them, hoists the
address out of the `mode == 2` arm's two sub-branches, and keeps the whole
address in one register, which is what every earlier candidate did. Capturing
the offset inside each arm scored 1245 → 295.

**This is the weakest-looking part of the candidate and the ledger says so
itself.** Four copies of one assignment is not what a person writes. The
alternatives — `q` before the chain, after the chain, at the top of the body —
were all measured and all collapse back into the whole-address CSE. Two
readings are consistent with the evidence: the original really did assign the
offset per branch (the four calls were clearly written out separately — three
different format strings), or there is a formulation not yet found. **Recorded
as an open question, not a conclusion.**

Also falsified along the way, worth not re-running (LEDGER #4, #5): a flat
`char field_0x76[0x600]` indexed `[n * 0x100]` is byte-identical to the 2-D
form — MWCC canonicalises them — and **every textual re-spelling** of the stored
pointer (`&lst->field_0x76[n][0]`, `lst->field_0x76[0] + n * 0x100`,
`&lst->field_0x76[n * 0x100]`, each also with `n - 1`) compiles identically.
MWCC's CSE works on the value, not on how it is written.

## Shared-type change 1: `struct unk_02324D90`

**Flagged loudly for a reviewer.** This struct is defined at file scope in
`src/overlay_11_02307334.c` (not in `include/`), so the blast radius is that one
translation unit — but it is used by **already-matching** functions in it, and
two of them take its `sizeof`:

```c
ov11_02324D90 = MemAlloc(sizeof(struct unk_02324D90), 8);   /* :1109 and :1120 */
```

The previous declaration (introduced by `5cda338e`) named three members and
covered the rest with padding. `ov11_023090DC` touches many more offsets, so the
padding had to be broken up. **The total size must not move.**

**Fact**, and it does not move — the arithmetic closes twice over:

| | NA/EU | JAPAN |
|---|---|---|
| old: `4 + 0x110 + 4 + 2 + 0x67A` | **0x794** | `4 + 0xF0 + 4 + 2 + 0x67A` = **0x774** |
| new: `0x11C + sizeof(struct unk_023090DC)` = `0x11C + 0x678` | **0x794** | `0xFC + 0x678` = **0x774** |

and `sizeof(struct unk_023090DC)` = `0x34 + 4 + 0x38 + 6 + 0x600` = 0x676,
rounded to 0x678 by the pointer alignment of its `field_0x38` members.

**This was not left to arithmetic.** `wip/ov11_023090DC/tools/sizecheck.py`
compiles, per region, one function whose return value is a bitmask of
`sizeof`/`offsetof` comparisons against the values implied by the *original*
declaration, and reads the folded constant back out of the generated code. All
three regions return `mov r0, #0` — 18 sizes and offsets each, covering
`sizeof`, the three pre-existing members and every new member including the four
inside the nested type. That is the real compiler answering, not this file.

### The JP `-0x20` decomposes exactly

**Fact.** The asm at `cad4a75f` carried its own region macro:

```asm
#define OV11_02309084_OFFSET -0x20      ; JAPAN
#define OV11_02309084_OFFSET 0          ; otherwise
```

applied to every displacement from `0x7c` upward. The struct absorbs it: three
name buffers at `0x3e` / `0x52` / `0x66` are `0x14` in NA/EU and `0xA` in JAPAN.
`3 × (0x14 − 0xA) = 0x1E`, plus the two bytes of `u32` alignment padding that
NA/EU needs at `0x7A → 0x7C` and JAPAN does not need at `0x5C`. `0x1E + 2 =
0x20`. The whole regional delta is accounted for, which is a real check on the
buffer lengths rather than a restatement of them.

**The member names keep their US offsets in JAPAN** (so `field_0x66` sits at
`0x52` under JAPAN). That is this struct's own pre-existing convention — the
tree already called the member at JP offset `0xF4` `field_0x114`. The
alternative would force an `#ifdef` at every use site in the body.

## Shared-type change 2: the parent-menu tables

This is the part of the commit least visible in the ROM and most worth a
reviewer's attention, because **the build cannot check it**.

Seven data globals are now `struct unk_0202A5CC[]`. Previously:

- **four** were declared `extern s32 ov11_02322D10;` and friends — a *scalar*
  standing in for an array, which is why every call site wrote `&ov11_02322D10`;
- **one** (`ov11_02322D38`) had a locally-defined duplicate,
  `struct unk_02322D38 { u16; u16; u32; }`, byte-identical to the real type;
- **two** (`ov11_02322E00`, `ov11_02322E28`) were new in this commit, and
  `STATUS.md`'s landing checklist offered `u8 ov11_02322E00[];` as an acceptable
  alternative "both compile and both are byte-identical at the call site";
- the file carried its **own** prototype,
  `extern u8 CreateParentMenuFromStringIds(void *, u32, void *, void *);`,
  whose final `void *` is what let all of the above compile under `-W error`.

**The data settles it — fact**, `asm/overlay_11_022ECD24_data.s:1714-1723`:

```
ED 02 00 00 | 00 00 00 00      u16 string id, 2 bytes padding, s32 value
EE 02 00 00 | 01 00 00 00
EF 02 00 00 | 02 00 00 00
F0 02 00 00 | FF FF FF FF
00 00 00 00 | FF FF FF FF      terminator
```

Five 8-byte entries, and `0x02322E28 − 0x02322E00 = 0x28 = 5 × 8` closes it.
`ov11_02322E28` is six entries by the same measure. The other five tables at
`0x02322CD8`–`0x02322D88` have the identical shape, with their string ids
written as `.word 0x2B1 + OV11_02322CD8_OFFSET` — visibly ids, not bytes.

**Fact**, `include/main_0202A66C.h:4-8,17`: `struct unk_0202A5CC` is already
declared as `{ u16 field_0x0; u8 field_0x2[2]; s32 field_0x4; }` and
`CreateParentMenuFromStringIds` already takes `struct unk_0202A5CC *items`. So
nothing was invented here — the commit adds `#include "main_0202A66C.h"`, drops
the local prototype, deletes the duplicate struct, and lets the header's
declaration reach the call sites. Five now-redundant `&` come off.

**Byte-neutral, and confirmed by all three builds** — `&scalar` and an array
name yield the same address, and a pointer's *type* changes neither an address
nor a width.

That last sentence is the whole point, and it is now written up in
`docs/MATCHING_TIPS.md` → *A byte-match cannot validate a DECLARATION*: the
weaker `u8[]` typing would have **matched the ROM** and shipped as a sixth wrong
declaration on top of five existing ones. The build is structurally unable to
see this class of error. The same tips entry records the mirror-image failure
from the same session — `DrawTextInWindow`'s `s8` window id, where a per-TU
declaration that *disagreed* with the header was **right**, and "tidying" it to
the header's `s32` broke `OVY_13.sbin`. A disagreeing declaration is not
automatically stale and not automatically correct.

## Regions

**One genuine `#ifdef JAPAN` in the body**, in case 7 — **fact**, and the
distinction is worth stating precisely, because the other seven region forks in
the `.s` needed nothing:

```c
#ifdef JAPAN
    sub_0203FBD4(ov11_02324D90->field_0x10);
#else
    sub_0203FBD4(ov11_02324D90->field_0x11c.field_0x0
                     .field_0x0[ov11_02324D90->field_0x10].field_0x4);
#endif
```

The US arm loads `list[field_0x10].field_0x4`
(`add r0, r3, r0 lsl 3` / `add r0, r0, #0x100` / `ldrsh r0, [r0, #0x20]`); the JP
arm sign-extends `field_0x10` itself (`lsl #0x10` / `asr #0x10`) and passes that.
**These are different values, not the same value addressed differently** — which
is exactly why every *other* JP arm needs no `#if`: they are the same value at a
shifted offset, and the struct absorbs the shift.

Two region constants are spelled as macros, in the style the file already uses
for `OV11_02307334_OFFSET`:

| | NA/EU | JAPAN | delta |
|---|---|---|---|
| `OV11_023090DC_CONST_1` | `0x2F2` | `0x2FF2` | **+0x2D00** |
| `OV11_023090DC_CONST_2` | `0xA3A` | `0x875` | −0x1C5 |

**Fact:** these are the resolved pool words `_02309D94` / `_02309D98` of each
region's own target, and `targets/JP_DELTA.txt` in the wip shows the pair
changing together. **Fact, arithmetic:** `+0x2D00` is exactly the shift the
`ov11_02322E00` table applies to its own string ids
(`OV11_02322E00_OFFSET 0x2D` on the id's high byte). **Inference:** that
`field_0x84` therefore holds a string/message id from that same id space.
`CONST_2`'s `−0x1C5` fits no pattern found and is unexplained.

**Do not generalise any of these shifts.** Three distinct JP id offsets appear in
this one data file: `+0x2D00` (`OV11_02322E00_OFFSET`), `+0x2D20`
(`OV11_02322CD8_OFFSET`, used by the neighbouring menu tables), and
`OV11_02322BE0_OFFSET` above them. [`f8eaf87f`](f8eaf87f.md) made the same
warning about the `+2` between EU and NA in this object.

**The instruction count in the task sheet was wrong, and that mattered.** The
sheet said 807; NA/EU is **809**. `809 + 11 pool words = 3280 = 0xCD0 =
0x02309DAC − 0x023090DC` exactly, and 807 + 11 would leave the address walk
eight bytes short of the next symbol. **807 is the JAPAN count** — two of the
eight JP arms emit one instruction fewer than their US counterparts. This was
caught because `tools/mktarget.py` re-derives the whole layout every run and
asserts that the walk closes on `ov11_02309EE4`, rather than trusting a number
handed to it.

JAPAN needed a *different* walk rather than a weaker one: the JP arms reuse the
**same** `_0XXXXXXX` label names as the US arms, so under JAPAN those names spell
US addresses while the function is eight bytes shorter — demanding that every
label agree on one entry address would assert something false by construction.
`mktarget.py` instead runs a shift walk: label name-sets must match NA exactly,
per-label shift must start at 0 and be monotone, and the **last** label's shift
must equal the block's total NA-minus-JP size. That last equality is the
non-tautological part.

This was decompilation, not identification. Every `ov11_<addr>` keeps its name in

| `struct unk_0202A690` | the 4th parameter of `CreateParentMenu` (`asm/main_0202A690.s`), which walks it as a NULL-terminated `{string, value}` list | good — it is that function's argument type |

| `struct unk_023090DC` | **neither placeholder form applies** — it has no global of its own and is nobody's argument. Named for the function that materialises it | **weak; a reviewer may prefer another name, and nothing depends on it** |

`struct unk_02309DAC` was **not** invented here — it already existed in
`include/overlay_11_02307334.h` with exactly the derived layout
(`{ s32 field_0x0; s16 field_0x4; }`), and both call sites in this file already
used it.

**It is deliberately not unified with `struct unk_0230A044`, despite byte-identical

from `{1, 2}` to `{0, 1}` — **fact**, read off the landed body. Equating the two
types would assert something the asm contradicts. A reviewer who wants them
