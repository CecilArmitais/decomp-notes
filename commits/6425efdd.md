## Types: three cases where the scratch's guess had to yield

**Fact.** A scratch declares its own cut-down structs, so every one of them has
to be re-checked against the tree before landing.

- **`struct unk_0202AAA8` already exists** and already types the
  `GetWindowContents` result — `src/main_020307A4.c`, the destination file,
  uses it two lines above where these functions land. The scratch had invented
  `struct unk_020307B8`. The existing type is used instead, and offsets
  0x1C0/0x1C1 become its `field_0x1C0[2]`.
- **`include/main_0202AAA8.h`'s `field_0xFC[0x9C]` is refined** to
  `field_0xFC[8]` / `u32 field_0x104` / `field_0x108[0x90]`, so offset 0x104 is
  addressable. Byte-neutral (8 + 4 + 0x90 == 0x9C), and **fact**: `field_0xFC`
  is referenced nowhere in the tree but its own declaration, so no other file
  can see the change.
- **`sub_02032984`'s parameter is `void *`**, not the `struct unk_02032558 *`
  the scratch used. The call site shows only `(u8 *) w + 4`; that is not enough
  to claim a type, so it guesses weakly per the caller-first rule.

## Two matching techniques, both new to `MATCHING_TIPS.md`

**Fact.** `if (A && B) return TRUE; return FALSE;` and every ordinary
respelling of it — nested `if`s, an explicit `else`, a duplicated
`return FALSE`, a single result variable — score **identically** (515), because
MWCC lowers them to one CFG and then if-converts the short block into
`moveq r0, #1` / `bxeq lr`. Negating the whole condition and returning the
failure early —

```c
if (!(d->is_destination_floor && d->type == type)) {
    return FALSE;
}

return TRUE;
```

— puts the success return out of line, reached by a branch, which is retail's
layout. **0** for both mission functions.

**Fact.** A stand-in `enum` written for a scratch context is a *signed* byte
when its enumerators span a small range, so a 1-byte field reads back as
`ldrsb` — and since `ldrsb` has only an 8-bit offset, it drags in an extra
`add rN, base, #0x700` that retail's plain `ldrb r1, [r2, #0x761]` does not
have. Widening the stand-in's range fixes both rows. The same cause
sign-extends a `u8` argument passed to such a parameter (`lsl`/`asr #24`),
which was `GetLearnableIqSkills`'s last mismatch. **Inference**: this is a
scratch artifact only — the landed `.c` includes the real header, so the
stand-in never ships. It is worth knowing because it fabricates diffs that look
like a codegen problem and are not.

## The one thing here that is a stand-in, not recovered code

**Fact.** `EnableAllLearnableIqSkills` reads `skills[i]` **twice** in retail —
`ldrb r0` for the `== 0` test, then `ldrb r1` for the argument — from the same
base and index register, with no call or store between them. MWCC CSEs that
load under every ordinary respelling tried: the test through a second pointer
into the same buffer, the argument through it instead, `*(skills + i)`,
`!skills[i]`, an explicit `(u32)` cast, and moving the test into the `for`
condition (which scored 760, much worse).

**Fact.** Reading through a `volatile u8 *` reproduces retail exactly (110 →
**0**), and — as `MATCHING_TIPS.md` already records for `SetLeaderAction` —
**three spellings compile byte-identically**: the array declared `volatile`, or
a cast on either access. The least intrusive was chosen (the buffer stays
`u8 skills[0x48]`; only the argument read is cast), because the others force a
cast at the `GetLearnableIqSkills` call too.

**This is flagged as a stand-in, not presented as recovered source.** `volatile`
on a scratch buffer is an implausible thing for the original to have written.
What the match establishes is the *mechanism* — those two accesses do not CSE.
If a more natural construct with the same property is found, it should replace
the cast verbatim. **This is the one place in the commit where the C is known
not to be what retail's programmer wrote**, even though the bytes are identical.

## Open questions for a reviewer

1. **The `volatile` cast in `EnableAllLearnableIqSkills`** — above. The most
   likely explanation is a construct not yet thought of, not a compiler quirk.
2. **`GetLearnableIqSkills` needs an explicit `(enum iq_skill_id)` cast** that
   the scratch did not. **Fact**: the scratch flag string has no `-W error`,
   the real build does, and MWCC treats the implicit `unsigned char` → enum
   conversion as an error under it. The cast is byte-neutral (verified by the
   build), but it is a reminder that a scratch is a *weaker* check than the
   build, not an equivalent one.
3. **Is refining `field_0xFC` the right call?** It is byte-neutral and nothing
   referenced it, but it does edit a struct ten files share. The alternative
   was `*(u32 *) &w->field_0xFC[8]` at the one use site.
4. **The `sub_0204E6FC` / `0204E770` / `0204E780` trio** in `sub_0206A7CC` is
   a special-episode / dungeon-progress selector whose three arms were not
   investigated — only their return values are used, and a scratch cannot see
   past a `bl`.
