## The type changes are the part to scrutinise

Two declarations changed, and both touch code already committed — one of them an
enum introduced by the PR under review. Reviewers should weigh these
independently of the function itself.

### `enum script_entity_id` gains `ENTITY_NONE = -1`

**Fact.** The target reads the `SPECIAL_ACTORS` redirect slots with `ldrsheq` —
a *signed* halfword load. Under `-enum min`, an enum with no negative enumerator
is unsigned, so those fields compile to `ldrh`. Different instruction, different
bytes.

**Fact.** An explicit `(s16)` cast at the read site does **not** fix it. The
destination store is 16-bit, so the conversion is redundant and MWCC folds it
away — still `ldrh`. Measured, not assumed: cast → score 800, unchanged from no
cast.

**Fact, and the answer to "does it break anything".** The sentinel was built in
isolation — added to `enums.h` with no other modification anywhere in the tree —
and the ROM still matched. So it is byte-neutral everywhere that currently
exists, and only changes code that *reads* such a field.

Why it went unnoticed until now: **storing to a field cannot reveal its
signedness.** `strh` is the same instruction either way. The eight setters in
the PR only ever store, so the enum's unsignedness was invisible there.
`sub_02065050` is the first decompiled function to read these slots.

Naming follows `EPISODE_NONE = -1`, already in `enums.h`.

### `struct unk_020A7FF0.field_0x0` becomes `s16`

Same mechanism, and this one was **my error**. I declared that struct while
matching `sub_02065B14`, which reads only `field_0x8` — genuinely unsigned
(`ldrh`). I had no evidence about `field_0x0` and guessed `u16`. Both resolvers
read it with `ldrsh`, so it is signed.

**Generalisable**: when declaring a struct, a field you have not seen *read* has
no established signedness. Guessing costs nothing until someone reads it, then
costs a confusing mismatch in unrelated code.

### `sub_02055410` takes the member index

**Inference, but well-evidenced.** Declared `void`, everything matches except
that the `-1` constant lands in `r0` instead of `r1`. The target calls
`bl sub_02055410` with no register setup, and `r0` already holds the result of
`GetAppointedLeaderMemberIdx` — so if the function takes that value, no `mov` is
needed *and* `r0` stays occupied across the sentinel comparison, forcing the
constant to `r1`. Declaring `int sub_02055410(int)` produces an exact match.

The two sibling calls `sub_02055474(member)` and `sub_020554D8(member)` take the
same value, which makes the reading more plausible. It is still an inference:
another argument that happened to be in `r0` would look identical.

## What the function does

**Fact**, read off the control flow:

1. Redirects ids `0x2E`–`0x31` through `SPECIAL_ACTORS.talk_main` / `talk_sub` /
   `event_npc_main` / `event_npc_sub` (offsets `0x18`/`0x16`/`0x14`/`0x12`).
   This independently confirms the slot mapping claimed in the PR.
2. Returns -1 for id -1.
3. Dispatches on `ENTITIES[id].field_0x0`:
   - **1** — resolves a player slot from script variable `0x34`; returns 0.
   - **2** — resolves a team member from variables `0x35`/`0x36`, then maps the
     rewritten id to 1 or 2.
   - **3** — range-checks `0x16`–`0x19` or `0x1a`–`0x1d` against
     `GetUnitNpcIds` / `GetAdventureNpcIds`, honouring
     `DEBUG_FLAG_STAGE_NPC_DUMMY`; every path returns -1.
   - **otherwise** — handles id `0x3F` via the appointed leader.

**Inference.** `field_0x0` reads as a kind/type discriminator, taking at least
values 1, 2, 3. That is consistent across both resolvers but the field stays
unnamed — three observed values is not an enumeration.

## How it was matched

Four steps, 2445 → 0:

1. **Funnel every success path through one `ret` variable** (2445 → 240). The
   target sets `r4` and exits via a shared `mov r0, r4`; failure paths `return
   -1` directly. Returning literals throughout produces a different shape *and*
   costs a callee-saved register.
2. **`case 3:` and `case 9:` share a label** (240 → 10). The jump table sends
   both to one block; writing two identical `ret = 2; break;` bodies makes MWCC
   emit two.
3. **`sub_02055410(member)`** (10 → 0 on decomp.me).
4. **The two signedness fixes** (0 on decomp.me → matching build).

Step 3 came out of a ~50-variant sweep. Nothing about the *phrasing* of the
comparison moved the register — not control flow, not types, not declaration
order, not the comparison form. What moved it was permuting the **order of the
four tests in the chain**: whenever the test after the `-1` check consumed
`member`, the constant moved to `r1`, because `r0` was reserved for the
argument. Those permutations were all wrong answers (scores 135–1190), but the
common factor pointed at the real cause. Worth repeating as a technique: when a
site will not move, perturb what comes *after* it and watch what the allocator
does.
