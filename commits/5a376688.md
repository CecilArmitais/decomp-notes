## `unk_020A7FF0` — the table behind `ENTITIES`

**Fact.** 12-byte records (stride confirmed by `smlabb r0, r0, #12, r2`).
Record 0 decodes as `{0x0001, 0x0000, &ACTOR_LIST, 0x0000, 0x02, 0x01}`.

| offset | type | evidence |
|---|---|---|
| `0x0` | `u16` | read `ldrsh` in `sub_0206549C`, tested against **3** and **0xa**; data shows **1**. **Fact** that it is compared to those constants; **inference** that it is a "kind" field. |
| `0x2` | `u16` | `0x0000` in every record inspected; no read located. Unanalysed. |
| `0x4` | `char *` | points into an ASCII pool. Record 0 → `ACTOR_LIST`, whose bytes are `50 4C 41 59 45 52 00 00` = **`"PLAYER"`**. The pool runs to `NPC_METAMON_KIREIHANA` immediately before `ENTITIES`. **Fact.** |
| `0x8` | `u16` | returned by `sub_02065B14`; consumed as a string id — below. |
| `0xa`, `0xb` | `u8` | `0x02`, `0x01` in records inspected. Unanalysed. |

**Observation for a reviewer.** `ACTOR_LIST` — a pre-existing decomp name, not
mine — labels the bytes `"PLAYER"`, i.e. the *first string* of the entity-name
pool rather than a list structure. Either the name is scoped differently than it
reads, or it is mislabelled upstream. Not changed here, and not asserted to be
wrong; flagged so a later identification pass resolves it.

**Name suggestions**: the record looks like a script-entity descriptor
(pmdsky-debug: `struct script_entity`); `field_0x4` is the entity's symbolic
name; `field_0x8` a display-name string id. `field_0x0` is plausibly a kind
enum, but three observed values is not enough to name it — enumerate every `cmp`
against it across both resolvers first.

## `sub_02065B14`

```c
if (id == -1) return 0;
return ENTITIES[id].field_0x8;
```

**What it feeds — the strongest evidence chain here.** Its one located caller
(`asm/main_020151E4.s`) passes the result straight to `GetStringFromFileVeneer`,
and falls back to a name lookup when it is zero:

```asm
bl   sub_02065B14
movs r1, r0
beq  _02023F48                 ; 0 -> fall back
add  r0, sp, #0x42
bl   GetStringFromFileVeneer   ; (buf, string_id)
...
_02023F48:
bl   GetNameString
bl   strcpy
```

The in-tree header `include/main_0202593C.h` declares
`void GetStringFromFileVeneer(u8* buf, s32 string_id)` — **fact**, not
inference. So the return value is a `string_id`, and **0 means "this entity has
no string of its own"**.

**Inference**: `field_0x8` is a display-name string id and `sub_02065B14` is its
accessor. **Name suggestion**: `GetScriptEntityNameStringId`. Note it returns 0
both for "no entity" (`id == -1`) and "entity has no string", which the caller
cannot distinguish — consistent with the observed fallback.

**Matching note.** `return ENTITIES[id].field_0x8;` written directly scores
**905**: MWCC if-converts the body into predicated instructions and folds `+8`
into the literal (`ENTITIES+0x8`). Binding `&ENTITIES[id]` to a pointer local
first restores the target's `smlabb` + `ldrh [r0, #8]` + early `bxeq lr` —
**score 0**.

## `GetScriptEntityMonsterId` — and a warning about the harness

```c
s16 GetScriptEntityMonsterId(s16 entity_id)
{
    s16 monster_id;

    sub_0206549C(&entity_id, &monster_id);
    return monster_id;
}
```

That is the first and most obvious C, and it matches. It is recorded here
because it was wrongly written off earlier in this branch's work as an
unclosable 600/900 near-match, after roughly 25 attempts across C shapes, flag
sets, five compiler builds and six optimisation levels.

**Every one of those attempts was invalid.** The scratches used compiler
`mwcc_20_82`, which is *not* this project's compiler. The correct decomp.me id
is **`mwcc_30_137`**, displayed as "3.0 build 137 (MW 2.0sp2p2)" — the
`mwcc_30_*` number is the build series, and `MW 2.0sp2p2` in the label is the
Metrowerks product version that `MWCCVER` names. Same source, same flags:
`mwcc_20_82` → 600, `mwcc_30_137` → **0**, and the real build agrees.

Two things generalise:

- **A mismatch that is completely insensitive to the C is a signal to check the
  harness, not to try more C.** Identical deltas at `-O0` and `-O4,s` should have
  ended the search immediately.
- **Reproduce a second, unrelated function whose source is near-certain.**
  `SprintfStatic__020176E4` — a `vsprintf` forwarder whose `bic`/`add` is
  explained exactly by the tree's own `va_start` macro in `include/stdarg.h` —
  reproduced its entire body and showed the *identical* frame delta. Two
  unrelated functions failing the same way, one with unambiguous source, points
  at the tool.

`sub_0206549C`'s prototype is declared in `include/main_02065974.h` because that
function is still asm and has no header of its own. Its parameter types are a
reconstruction from how it is called and how it reads its arguments; move the
declaration if a better home appears.
