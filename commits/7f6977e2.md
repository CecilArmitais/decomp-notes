## The layout confirmed by the linker

**Fact.** Four bss symbols these functions index at stride `0xE0` are **aliases
into `WINDOW_LIST[0]`**, not separate objects: `_022A88E4` is `+0x8`,
`_022A88F0` is `+0x14`, `_022A88F8` is `+0x1C`, `_022A8994` is `+0xB8`.

**Fact.** The block from `WINDOW_LIST` to the end of `_022A8994` measures
`0xB8 + 0x10C8 = 0x1180 = 20 * 0xE0`, and **every one of those boundaries falls
on a field boundary** of the layout in [`30ea1f34`](30ea1f34.md).

That is independent corroboration of the maintainer's layout **from the linker
rather than from the struct definition** -- a fifth check, and the strongest.

## Five of ten never reached score 0, and were landed anyway

**This deviates from the project's usual rule and needs to be read carefully.**

**Fact.** `sub_020282F4`, `sub_0202830C` and `sub_02028324` score **5**;
`ClearWindow` and `sub_02027B1C` score **10**. **Every instruction matches.** The
only difference is the literal-pool word, which the target names `_022A8994`
where C indexing `WINDOW_LIST` emits `WINDOW_LIST+0xb8`.

**Fact.** Same address, same relocation target, **identical bytes once linked**.
The scratch diff compares relocation *symbols*, at a flat 5 per word.

**Fact.** The in-repo build -- which the project designates the source of truth
-- printed `build/pmdsky.us/pmdsky.us.nds: OK`.

**The check that separates this from a real mismatch**, before trusting it: the
differing line must be a `.word` in the literal pool and never an instruction;
both symbols must **provably** resolve to the same address (verified here by
adding up the `.space` runs in the bss file); and the score must be exactly
5 x the number of such words. If the arithmetic does not land exactly, it **is**
a real mismatch.

## The regression: do not unify two aliasing globals

**Fact.** `_022A7A74` is a real `.global`, 8 bytes after `_022A7A6C`. From that,
the conclusion was drawn that `struct unk_022A7A6C` was wrongly fusing two
separate symbols, and `NewWindowScreenCheck` was "cleaned up" to use
`_022A7A74[0]` and `[1]`.

**That failed `main.sbin`** -- no compile error, no overlay cascade, because the
object was the same size.

**Fact.** The target stores to `_022A7A6C` at `#8` and `#0xa`; the new accessors
index `_022A7A74`. **Both are real**, and which one appears is decided by whether
the index is constant:

- **constant offset** -> base symbol in the pool, offset in the instruction;
- **variable index** -> the offset folds **into** the pool word, because the
  index has to be scaled separately.

So **the literal the target chose says which global the original source named**,
and unifying them destroys that information. Reverted; both declarations kept,
because the target keeps both.

This is the same mechanism as the pointer-local trick in
[`643fd53b`](643fd53b.md), stated as a general rule.

## Type reuse, flagged as structural

**Fact.** `sub_020282C8` writes `width*8` and `height*8` through an out
parameter. It **reuses `Point`** rather than adding a second two-`s32` struct.

**Read that as structural reuse, not a claim about meaning** -- a size is not a
coordinate. The layout is identical and the type already exists, which is why it
was preferred over inventing `struct unk_020282C8`.

## Stale prototypes: two fixed, two deliberately left

**Fixed**, both rebuilt to confirm byte-neutrality: `overlay_31_02382820.c`
declared `UpdateWindow` itself; `overlay_31_02383880.c` declared `sub_020282F4`
taking `s8`.

**Left, with reasons:**

- `overlay_25_init.c` declares both `UpdateWindow` and `sub_02027B1C` taking
  `char *`. **That is a genuine mistyping** -- the value it passes is a window id
  -- but correcting it means retyping `ov25_0238B414`'s own parameter and its
  callers, a larger change than this batch.
- `overlay_13_0238BDA8.c` declares them taking `s8`, and **carries an upstream
  annotation** identifying `sub_02027B1C` as *"ClearAndUpdateWindow"* in
  Chesyon's notes. That annotation **independently corroborates this
  decompilation** (`memset` + `UpdateWindow`), and deleting another contributor's
  note to make a byte-neutral typing change was judged not worth it.
