Follow-up to [`a51777ff`](a51777ff.md), which matched the US branch only. The
asm block carried 21 preprocessor directives including two wholesale
`#ifdef EUROPE` duplications; this commit accounts for all of them.

## How the regions were separated from each other

**Fact.** Instruction counts per region, taken by resolving the directives three
ways: US 1627, EU 1645, JP 1614. That bounded the work before anything was
built — EU adds ~18 instructions, JP drops ~13.

**Fact.** Normalising both streams — every register replaced by one token, every
`_0xxxxxxx` label by another — turns the EU block's unreadable raw diff into 44
hunks, of which the great majority are one offset macro spelled `#0x15c +
APPLY_DAMAGE_OFFSET` in the US branch and `#0x15c` literally in the EU branch.
That is the same value; the macro is 0 outside JAPAN.

Everything below is what survived that normalisation.

## JAPAN — five source differences

| difference | evidence |
|---|---|
| `DefenderAbilityIsActive__0230A940` takes **three** arguments at six call sites | **fact**: `include/overlay_29_0230A994.h` already declares the 3-argument form under `#ifdef JAPAN`, so this was a *compile* failure, not a mismatch |
| every message id is **US − 0x2C1** (18 of them) | **fact**: read off the pool words and the two inline immediates; EU's are identical to US |
| no `UpdateStatusIconFlags` before the HP check | **fact**: the call is absent from the JP stream |
| no `end_floor_no_death_check_flag` guard on the revival-item path | **fact**: the five-instruction load/test is absent |
| reviver-seed block: no `ov29_022FBD24`, but `ov29_02307DC0` after the curse handling | **fact**: one call absent, one present that no other region has |

The message ids are region-conditional `#define`s at file scope rather than an
`#ifdef` at each call, following `src/dungeon_ai.c`, which already does exactly
this. **Naming**: they are keyed to their US value (`MESSAGE_C46`), which is
mechanical and claims nothing about what any message says.

`ov29_02307DC0` was declared nowhere in the tree; this commit adds an `extern`
for it. **Inference**: its parameter is `struct entity *` because the call site
passes the same register the neighbouring calls take the defender in. Nothing
constrains the return type, which is left `void`.

## EUROPE — a behavioural difference, not a layout one

**Fact.** The last arm of the defeat-message ladder sets a flag instead of
logging (`mov fp, #1` where US logs), the flag is cleared before the ladder
(`mov fp, #0`), and three later sites test it and log:

| site | table |
|---|---|
| the reviver-seed path, before `ov29_022FBD24` | `0x02353E44` |
| the revival-item path, before `ov29_022EAF20` | `0x02353E44` |
| the `else` of the revival-item condition | `0x02353E40` |

**Fact.** All three sites are inside the `IqSkillIsEnabled` block — the branch
that skips it jumps past the third site as well.

**Inference.** The message is being deferred until it is known whether the
monster was revived, and the two revival paths log a different message than the
fall-through. Nothing in the bytes says that; it is the reading that makes the
shape sensible.

### The EU-only data table

**Fact.** In `asm/overlay_29_rodata_02352A6C.s`, the EUROPE branch has
`ov29_02353218` followed by four more bytes that the US and JP branches do not
have, and that carry no symbol. The extractor could only print both pool words
as raw addresses (`0x02353E40`, `0x02353E44`), because it resolves against the
US symbol table and neither address exists there.

**Inference, now confirmed by the build.** `0x02353E40` is EU's
`ov29_02353218` and `0x02353E44` is the unnamed neighbour. This commit labels
the neighbour; the label and its `.global` add no bytes. Had either reference
been wrong, `pmdsky.eu.nds` would not have matched — so the EU checksum is the
evidence, not the argument above.

**Open question — the name.** `ov29_02353E44` is keyed to the symbol's
**EUROPE** address, which breaks this file's convention of naming by US
address. There is no US address available: the data does not exist in that
build. A reviewer may prefer a different scheme.

## The one change made purely for register allocation

With the regions' code correct, EU was instruction-exact (`ins=0 del=0 imm=0`)
and sat on a whole-function rotation of three callee-saved registers —
`r7→r5→r6→r7`, 227 rows from three fresh decisions. What moved it:

```c
/* rotation present */
dmon = defender->info;
if (dmon->is_not_team_member && !dmon->is_ally) { is_wild_enemy = TRUE; }

/* rotation gone */
if (((struct monster *)defender->info)->is_not_team_member
    && !((struct monster *)defender->info)->is_ally) { is_wild_enemy = TRUE; }
dmon = defender->info;
```

**Inference.** Introducing `dmon` after the test makes the allocator colour
`damage_data`'s web first, which is the order retail has. **Fact**: it costs no
instructions — the base pointer was already in a register — and it is
byte-neutral for the US and JP builds, both of which stayed at 0.

**Fact**, and the reason this took a while: inside the shared source the
rotation was immovable. 27 declaration positions for each of two variables, six
types for the EU flag, all 24 orderings of the four opening initialisations, and
two ways of splitting the loop webs were **every one byte-identical**. The fix
was found only after resolving EU into a standalone file where nothing had to
keep US and JP at 0.

## Open questions for a reviewer

- **The EU table's name**, above.
- **`ov29_02307DC0`'s signature** is inferred from one call site; its return
  type is unconstrained.
- **The EU deferred-message reading** is an interpretation of the control flow,
  not something the bytes state.
- **The `volatile` read** from [`a51777ff`](a51777ff.md) is unchanged and still
  the one construct in this function that is not plausible source.
- **`MESSAGE_*` naming** is deliberately mechanical. If the ids are ever given
  real names upstream, these should follow rather than compete.
