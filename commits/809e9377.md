## Landing shape — eleven merges, no split

**Fact.** Ten `.s` files are touched for eleven functions: every function sits
at the head or the tail of its file, so `extract_function.py` takes a merge
branch each time and splits nothing.

- Eight files lose their **head** function and are renamed to the new base
  address (`asm/main_02011528.s` → `main_02011554.s`, and seven more).
- Two lose their **tail** function and keep their name: `asm/main_02000DE0.s`
  (`MemAlloc`) and `asm/overlay_29_02337EC0.s` (`NearbyAllyIqSkillIsEnabled`).
- `asm/overlay_29_0234B350.s` gives up **both** its head
  (`LogMessageByIdWithPopupCheckUserTarget`) and its tail
  (`LogMessageByIdWithPopup`) — two functions out of one file, still no split.

**`main.lsf` gains no objects**: all eight of its changes are one-for-one
substitutions of a renamed `asm/*.o` (fact, counted in the diff). That is the
mechanical signature of a pure merge; a split would have inserted lines.

**The regenerated `.inc`s corroborate the merges, symbol by symbol.** Each
`.inc` declares the symbols its `.s` references from outside, so removing a
function should drop exactly the symbols that function was the sole user of —
and it does. Comparing the old and new `.inc`s **as sets** (fact, measured; the
raw diffs are noisier, see below):

| `.inc` | `.public` entries dropped | the departing function's references |
|---|---|---|
| `main_02000DE0` | `MemLocateSet` | `MemAlloc`'s tail-call target |
| `main_020308C4` | `DeleteWindow`, `MemFree` | `CloseAdvancedTextBox`'s two callees |
| `main_02051804` | `RANK_UP_TABLE` | `GetRankUpEntry`'s pool word |
| `main_02052AB0` | `_s32_div_f` | `GetExp`'s division helper |
| the other six | **nothing** | every symbol the departing function used is still called by a function that stayed |

Those four are the complete list of dropped symbols across all ten files. The
other six `.inc`s are **identical as sets** — including
`overlay_29_0234B3A4.inc`, which keeps `LogMessage`, `StringFromId` and
`ShouldDisplayEntityWrapper` because the three functions still in that file call
them too.

The raw `.inc` diffs look much larger than that because the tool also
**re-sorts** every `.public` list into plain ASCII order, where `_` (0x5F) falls
after the uppercase letters: `GINSENG_CHANCE_3` moves above
`GetMoveBasePowerGround`, `_s32_div_f` and `_020B09B0` move to the bottom of
their blocks. Read as a diff, `overlay_29_022EA008.inc` appears to lose
`_s32_div_f` and gain four symbols; as a set it is unchanged. That is noise from
the regeneration, not content.

## What pins each signature

### `MemAlloc` — a tail call that shifts its arguments

```
ldr ip, _02001184 ; =MemLocateSet
mov r2, r1
mov r1, r0
mov r0, #0
bx  ip
```

**Fact.** Both arguments move right by one register and a literal `0` is
injected into `r0`; `bx ip` is a tail call, so the return value passes straight
through. That is `return MemLocateSet(0, len, flags);` and nothing else.

The spelling `0` rather than `NULL` was copied from the structural sibling one
object later, `MemFree` in the same file, which the tree already spells
`MemLocateUnset(0, ptr)` (fact — it is in `src/main_02001188.c`).

**What the bytes do *not* say: the widths or the signedness of either
parameter.** Nothing is masked or extended; `MemLocateSet`'s own body is still
asm and was not read. `u32 len, u32 flags` is the majority in-tree spelling, not
a measurement — see the declaration sweep below.

### `GetRankUpEntry` — a 16-byte stride

```
ldr r1, _02051800 ; =RANK_UP_TABLE
add r0, r1, r0, lsl #4
bx  lr
```

**Fact.** `lsl #4` is a 16-byte stride, so `sizeof(struct unk_020517F4) == 16`,
and the harness compares the pool word *with its addend*, so score 0 confirms
the symbol is `RANK_UP_TABLE` itself and not `RANK_UP_TABLE + something`. The
ledger records two negative controls that both score **120**:
`&RANK_UP_TABLE[rank + 1]` and `(s32 *)&RANK_UP_TABLE[0].field_0x8`.

**Byte-neutral spellings, all measured at score 0** (fact, from the ledger):
`const` on the table and the return, `u32 rank` instead of `s32 rank`, and
`RANK_UP_TABLE + rank` instead of `&RANK_UP_TABLE[rank]`. The signature was
therefore chosen from the *tree* — the `extern` that already stood in
`src/main_0203D538.c` — and not from the score.

### `GetExp` — a signed load of a field the header calls unsigned

```
smlabb r0, r0, r1, r2     ; r1 = #0x44
ldrsh  r4, [r0, #0x1c]
mul    r0, r4, r3         ; r3 = level - 1
bl     _s32_div_f         ; r1 = #0xa
add    r0, r4, r0
```

**Fact.** `SMLABB` multiplies the low *signed* halfwords, so parameter 1 is a
16-bit signed id; `0x44` = 68 = `sizeof(struct monster_data_table_entry)`; the
division is `_s32_div_f`, i.e. ordinary signed `/ 10`.

**Fact, and the only thing this function got wrong on the first attempt:**
offset `0x1C` is loaded with `LDRSH` — *signed* — while
`include/monster_data.h:30` declares it `u16 exp_yield`. The uncast candidate
scored **200** with exactly one differing row (`ldrsh` vs `ldrh`); adding
`(s16)` took it to 0 in all three regions. The ledger also records the control:
with the field itself retyped `s16`, the *uncast* body scores 0 too — so the
cast and a signed field declaration are byte-identical, and the cast exists only
because the in-tree header says `u16`. **That is a shared-type question this
commit deliberately did not answer** — see below.

### `ApplyGummiBoostsToGroundMonster` — four offsets that land on an existing struct

```
stmia sp, {r1, r2, r3}
add r0, ip, #4    ; &monster->id              s16,   0x4
add r1, ip, #8    ; &monster->iq              u16,   0x8
add r2, ip, #0xc  ; monster->offensive_stats  u8[2], 0xC
add r3, ip, #0xe  ; monster->defensive_stats  u8[2], 0xE
```

**Fact.** All four offsets are exactly `struct ground_monster`'s, as
`include/common.h:33-52` already declares them, so **no new type was needed**.
`stmia sp, {r1,r2,r3}` forwards arguments 2–4 to the callee's stack slots with
no masking or extension, which is what pins them to the *same* declared types in
and out — that is a measurement, not a guess.

**Not pinned:** the third parameter's width. `int` and `bool8` both score 0
(fact, ledger; the `bool8` run is scratch `bRjU4`) because the value crosses a
32-bit stack slot. `int` was chosen only because `src/overlay_11_02307334.c`
already declared it that way. The ledger's own reading is that **`bool8` is the
likelier true type**, since the callee reads it back with `ldrb` — that is
**inference**, and it is not resolvable from this function.

### `CloseAdvancedTextBox` — the order is load-bearing

`GetWindowContents(id)` is cached, `DeleteWindow(id)` runs, *then* `MemFree` of
the cached pointer. A nine-instruction function is small enough that a broken
harness matches for free, so the ledger records three deliberate near-misses
(fact, all three measured):

| candidate | score |
|---|---|
| `MemFree(GetWindowContents(id)); DeleteWindow(id);` — the neighbouring `CloseAdvancedMenu`'s body | **245** |
| `DeleteWindow(id); MemFree(GetWindowContents(id));` — right calls, wrong order | **255** |
| correct body with return type `s32` + `return 0;` | **100** |

### `LogMessageByIdWithPopupCheckUserTarget` — the two checks do not short-circuit

**Fact, read off the asm.** `ShouldDisplayEntityWrapper` is called for `user`
*and* for `target` unconditionally; each result is folded into the same flag
register (`cmp r0,#0 / movne r4,#1`) before the flag is tested once. A `||`
would have skipped the second call. The landed C therefore uses a `bool8 display`
flag and two separate `if`s, which reproduces it.

The `(char *)` cast on `StringFromId`'s result is **not** a codegen device:
`include/main_0202593C.h:17` declares `u8* StringFromId(u32 id)` and the
file-local extern declares `LogMessage(..., const char *message, ...)` (both
facts), so the cast bridges two declarations the tree already disagreed about.
A cast-free variant was kept at `wip/LogMessageByIdWithPopup/cand/nocast.c`;
**its score is not recorded**. Casts between pointer types emit nothing
(inference), and the build compiles with `-W error`, which is the actual reason
the cast is there.

### `TickStatusTurnCounter`, `AdvanceFrame`, `NearbyAllyIqSkillIsEnabled`, `EndNegativeStatusConditionWrapper`

**Facts:**

- `TickStatusTurnCounter` returns the counter unchanged when it reads `0x7F` or
  `0`, and otherwise stores `value - 1` and returns it; the trailing
  `and r0, r1, #0xff` is a `u8` return being truncated. What `0x7F` *means* —
  a "permanent / does not tick" sentinel would be the obvious reading — is
  **inference and was not checked**; nothing in the tree names it.
- `AdvanceFrame` branches on byte `3` of `ov29_02353560` and tail-calls one of
  two functions with `r0` untouched. The `struct unk_02353560` placeholder it
  reads through **already existed** file-locally in
  `src/overlay_29_022E9FC0.c`; nothing new was introduced.
- `NearbyAllyIqSkillIsEnabled` calls `ov29_023381C0(entity, skill, 0)` and
  normalises the result to 0/1, then `and r0, r0, #0xff` — the byte truncation
  is what establishes a `bool8`/`u8` return rather than `int`. That the callee
  returns a **pointer** (the landed C writes `!= NULL`) is **inference**: the
  bytes only require a zero test.
- `EndNegativeStatusConditionWrapper` pushes a literal `0` as a fifth argument
  and tail-calls `EndNegativeStatusCondition`; the wrapper discards the `s32`
  the callee returns (fact — the wrapper is `void` and nothing reads `r0`).

## The declaration sweep

**Fact, counted from the diff: exactly 40 declarations are removed**, and 38
`#include` lines are added across `src/` to replace them. The breakdown:

| function | declarations removed | distinct spellings |
|---|---|---|
| `MemAlloc` | 13 | 9 raw, reducing to 5 prototypes |
| `LogMessageByIdWithPopupCheckUserTarget` | 11 | 1 |
| `AdvanceFrame` | 6 | 3 (`(u8)`, `(u32)`, `(u32 param_1)`) |
| `EndNegativeStatusConditionWrapper` | 3 | 1 |
| the remaining seven | 1 each | 1 each |

**After the commit, every one of the eleven has exactly one prototype in the
tree, in its own header, and no `src/*.c` declares any of them** (fact — a
tree-wide grep for a prototype of each of the eleven names at this commit
returns only the eleven header lines).

The commit message says `MemAlloc` "was declared six different ways". I count
**nine distinct strings** collapsing to **five distinct prototypes** after
normalising `extern` and `*` placement: `(u32 len, u32 flags)`,
`(u32 size, u32 nmemb)`, `(u32 size, u32 heapId)`, `(u32 size, u32 flags)` and
`(s32, s32)`. The difference is bookkeeping, not substance; the substantive
point is unchanged.

### The two disagreements

**`MemAlloc` — `void* MemAlloc(s32, s32);`** in `src/overlay_24_end.c` and
`src/overlay_25_init.c`. `overlay_24_end.c` **already included
`main_02001188.h`** (fact — the include is there at `809e9377^`), so the moment
the header carried a `u32, u32` prototype the two declarations met inside one
translation unit and the compile failed outright. It had been harmless only
because the function had no header to contradict. `overlay_25_init.c` had no
such include before this commit; its copy was removed by the sweep and the
include added.

**A reviewer should notice what settled this and what did not.** The build
settled that the two *declarations* cannot coexist. It did **not** settle which
one is right: `MemAlloc`'s asm forwards both registers untouched, so
signedness is unobservable there, and `MemLocateSet`'s body was not read.
`u32, u32` wins on majority (11 of the 13 removed declarations) and on
consistency with `MemFree`, which is a convention argument, not a measurement.

**`AdvanceFrame` — `void AdvanceFrame(u8);`** in `src/overlay_31_02382820.c`
and `src/overlay_31_02383880.c`, against the `u32` the header now carries.
Four of the six removed declarations said `u32`, two said `u8`; **the bytes
discriminate neither** (the parameter is forwarded in `r0` with no masking, and
a `u8` parameter feeding a `u8`-parameter callee needs none). `u32` is the tree
majority, not a measurement. A `u8` candidate exists at
`wip/AdvanceFrame/cand/alt_u8.c` with its own context; **its score is not
recorded.**

One correction to the commit message, worth making because it reads wider than
it is: *"every call site passes the literal `0x62`"* is true **of the two files
that carried the `u8` declaration** — all five of their call sites pass `0x62`
(fact) — but not of the tree, which also calls `AdvanceFrame(0x17)`,
`AdvanceFrame(0xF)`, `AdvanceFrame(0x18)` and, in
`src/overlay_29_0234BA54.c:43`, forwards a `u32` variable. Those files declared
it `u32` already, so no narrowing was ever in play there. The byte-neutrality
claim survives the correction; its scope is narrower than stated.

## Shared-type changes — read these first

### 1. `struct unk_020517F4` moves from a `.c` into a header

**This is the one shared-type edit in the commit.** It was defined file-locally
at `src/main_0203D538.c:21`; it is now defined once, in
`include/main_020517D4.h`, and that file includes the header instead. Without
the move, `main_0203D538.c` would have had two definitions of the tag the moment
it included the header for `GetRankUpEntry`.

**The argument that the layout is preserved is that there is no layout change to
argue about**: the definition is the same five lines, moved verbatim, and a grep
of `809e9377^` finds `struct unk_020517F4` in exactly one place in `src/` and
`include/` — there was never a second copy to reconcile. **Fact.**

**But the definition it preserves is suspect, and this commit deliberately did
not fix it.** From the ledger:

```c
struct unk_020517F4 { u8 field_0x0[8]; s32 field_0x8; s16 field_0xc; u8 field_0xe[2]; };
```

The still-asm caller in `asm/main_020504BC.s` does `bl GetRankUpEntry` followed
by `ldr r2, [r0, #4]` — **twice** — loading offset 4 as a *word*, which
`u8 field_0x0[8]` cannot express (fact). The data agrees with the caller rather
than with the struct: `asm/main_rodata_020A2808.s` emits each of the 13 entries
as `.word <0x177..0x183 + RANK_UP_TABLE_OFFSET>` followed by 12 bytes, i.e. a
word at `0x0` and plainly word-shaped values at `0x4` and `0x8` (100, 300, 1600,
3200 … at `0x4`; 64, 96, 200, 320 … at `0x8`). 13 × 16 bytes = `0xD0`, and the
next symbol `DS_DOWNLOAD_TEAMS` follows immediately — so the **16-byte stride
and the 13-entry extent are facts**, while what the fields *mean* is not
established here.

A 4 × `s32` shape also scores 0 for `GetRankUpEntry` (fact, ledger), so the
field shape is free as far as *this* function is concerned; only the size
matters. It was left alone on purpose, to be settled when `main_020504BC` lands
rather than "fixed" silently on a commit that cannot test it.

*(Region note, fact: the table's first word is `+0x208` under JAPAN — a
region-shifted id space. Nothing in this commit depends on it.)*

### 2. `monster_data::exp_yield` stays `u16` — and the bytes disagree

**Not changed, and a reviewer should weigh it.** `include/monster_data.h:30`
declares `u16 exp_yield; // 0x1C`. Retail loads it with `LDRSH`. The commit
casts at the use site rather than retyping the shared field, because retyping it
to `s16` deviates from pmdsky-debug's vocabulary and would touch every consumer
of that header. **Both spellings are byte-identical here** (measured — see
`GetExp` above), so this is a naming/typing decision for a human, not a matching
one.

### 3. Header self-containment (no layout effect)

`include/main_020114F8.h` gains `#include "common.h"`. `extract_function.py`
emits a header that names types it does not include, and because the `.c`
includes its own header first, `struct ground_monster *` in the prototype would
open a **new, function-scoped tag** and the later definition would read as a
redeclaration with a different type. The scalar typedefs (`u8`, `s32`, …) never
have this problem because `common.mk:149` compiles every `src/*.c` with
`-prefix global.mch`, which pre-includes `nitro.h` (fact) — so only *struct
tags* need the include. `include/main_020517D4.h` is the other header made
self-contained, by carrying the struct definition itself.

**No struct or enum field was retyped, resized or reordered anywhere in this
commit** (fact — the entire `include/` diff is eleven prototypes, one `#include`
and one relocated struct definition).

## Open questions for a reviewer

- **`struct unk_020517F4`'s field shape is probably wrong** and was relocated
  unchanged rather than corrected. `u8 field_0x0[8]` contradicts a word load at
  offset 4 in `main_020504BC.s` and the word-shaped data in the rodata table.
  Only the 16-byte size is established.
- **`monster_data::exp_yield` is `u16` in the header and signed in the ROM.**
  The commit casts instead of retyping. Whether the header should change is a
  pmdsky-debug-vocabulary decision.
- **`MemAlloc`'s parameters are `u32` by majority, not by measurement.** So are
  `AdvanceFrame`'s. Reading `MemLocateSet`'s body would settle the first.
- **The two `LogMessageById…` siblings disagree about the id parameter**:
  `LogMessageByIdWithPopup(…, s32 message_id)` versus
  `LogMessageByIdWithPopupCheckUserTarget(…, u32 message_id)`. Both were
  inherited verbatim from the call-site declarations they replaced, both forward
  into `StringFromId(u32)`, and neither is discriminated by the bytes. One of
  them should probably change.
- **`ApplyGummiBoostsToGroundMonster`'s third parameter is `int`, and the
  evidence points at `bool8`** (the callee reads it with `ldrb`). Both score 0.
- **`GetExp` is declared `enum monster_id monster_id` while its file-mates in
  `src/main_0205283C.c` use `s16 monster_id`.** Both score 0. The enum was
  chosen because the call site in `src/overlay_29_02308FBC.c:1291` already casts
  to it; switching to `s16` would turn that cast into an implicit narrowing that
  `-W error` might reject, which the scratch harness cannot see.
- **`LogMessage` is still in no header** and is declared identically in
  `src/overlay_29_0234B340.c` and `src/overlay_29_0234B4BC.c`. Same for
  `EndNegativeStatusCondition` (two files) after this commit.
- **EU and JP ROMs were not rebuilt for this commit.** Every function was
  verified at score 0 against all three regional targets, and none of the eleven
  blocks carries a region directive, but the two link-level builds were not run.
- None of the eleven was renamed and no new name was invented — every name here
  was already carried by the asm (`.public` entries) or by the declarations
  being replaced. `struct unk_020517F4`, `struct unk_02353560` and the
  `field_0x…` members keep their placeholder forms.
