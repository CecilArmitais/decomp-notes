## `TickNoSlipCap` — a definition inside an `#ifdef EUROPE`

This is the one a reviewer should read even if they skip the rest.

**Fact.** `extract_function.py` inserts its placeholder by *address position* and
has no model of the preprocessor. The address position for `TickNoSlipCap` in
`src/overlay_29_02311010.c` fell immediately after a pre-existing
`#ifdef EUROPE` … `#endif` block's opening line, so the landed definition sat
inside the guard: present in EU builds, absent in US and JP.

**Fact.** Nothing in the compile stage reported it. Every object compiled clean;
the failure appeared only at link, as `Undefined : "TickNoSlipCap"` referenced
from `ActivateEndOfTurnEffects` in the *same object*.

**Fact, and the reason this is worse than a simple mislocation.** A region guard
around a definition also suppresses that function's own missing declarations,
because the region that would compile the body never does. Moving the definition
out of the block immediately produced two fresh `-W error` failures, and the two
declarations they demanded are the ones now at `src/overlay_29_02311010.c:33-34`:

```c
extern s16 ov10_022C4BE4[20];
extern void ov29_0230FB30(struct entity *entity);
```

**Fact.** The merge *target* was right all along —
`main.lsf` lists `asm/overlay_29_0230F9A4.o` immediately followed by
`src/overlay_29_02311010.o`, and the function sat at the tail of the former. Only
the insertion point within the file was wrong.

A guard against the class now exists as `build-tools/check_landed_guards.py`
(workspace repo, **not** part of this pmd-sky commit — it cannot be, the rule
forbids tooling and comments in the tree). It reports any function definition at
preprocessor depth > 0 and is reported clean across every function landed on this
branch so far. **That report is the author's; it was not independently re-run for
this note.**

**Residue a reviewer may want tidied:** the `#ifdef EUROPE` block in
`src/overlay_29_02311010.c` now opens with a blank line where the placeholder
used to be. Cosmetic, byte-neutral, left as-is.

### `TickNoSlipCap` regions: no `#if` in the C

**Fact** (diff of the three targets): the three regions emit the same 36
instructions and the same pool word. The only difference is a displacement —
`[r4, #0x107]` on NA/EU, `[r4, #0x106]` on JP. The asm source carried this as its
own `#ifdef JAPAN` / `TICK_NO_SLIP_CAP_OFFSET` macro.

**Fact** (`include/dungeon_mode.h:361-365`): `struct monster::in_action` at `0x103`
is already inside `#ifndef JAPAN`, so every field below `0x103` sits one byte
lower in a JP build. `0x107 - 0x106 = 1`. The single C line
`monster->no_slip_cap_counter++` therefore reproduces all three regions with no
`#if` of its own.

**Fact, corroborating and not circular:** `include/dungeon_mode.h:372-374` already
carried `u8 no_slip_cap_counter` at `0x107` with the note "Capped at 0x13", which
is exactly the `movhs r0, #0x13` in the target. That header line predates this
commit; it was not written to fit the match.

`UnfreezeAnim` is the same mechanism at a different distance: **fact**, the store
is at `0x171` on NA/EU and `0x16d` on JP, and the header drops four bytes above
that offset under `JAPAN` (`in_action` plus `field_0x10d..0x10f`). `0x171 - 0x16d = 4`.
One C line, no `#if`.

## The redundant-looking pair — do not "simplify" it

`MoveIsNotPhysical` and `CategoryIsNotPhysical` both landed as:

```c
    if (category == CATEGORY_PHYSICAL) {
        return FALSE;
    } else if (category != CATEGORY_PHYSICAL) {
        return TRUE;
    }
    return TRUE;
```

The `else if` tests the negation of the `if`, and the trailing `return TRUE;` is
unreachable. Both look like something to delete. **Both are load-bearing**, and
this is the best-evidenced claim in the commit because the dead ends were measured
rather than argued — `wip/CategoryIsNotPhysical/LEDGER.md` records **179 measured
variants** across three sweeps, `wip/MoveIsNotPhysical/LEDGER.md` a further set.

**Fact** (target, `CategoryIsNotPhysical`): `cmp r0,#0 / moveq r0,#0 / movne r0,#1 / bx lr`.
The `moveq #0` comes **first**.

**Fact** (measured): every ordinary boolean spelling — `!=`, `!!x`, ternary,
`if`/`else`, `goto`, `do{}while(0)`, constants routed through locals, constants
cast to `u8`/`u32`, named enumerators instead of literals — emits MWCC's boolify
template, which materialises the `1` first and so gets the two predicated moves in
the opposite order. Score 60 for all of them; 160 with a `bool8` return, which adds
a trailing `and r0,r0,#0xff`.

**Fact** (the probes that pinned the mechanism): `if (c == 0) return 0; return 2;`
scores **5** — the target's exact shape with one wrong immediate. So the shape is
reachable; only the value pair `(0, 1)` is special-cased into the boolify.

**Fact** (each measured, from the ledger): dropping the trailing `return TRUE;`
costs an extra `bxeq lr` (score 100); replacing it with `return FALSE;` emits the
dead arm as an extra `moveq r0,#0` (score 200); swapping the two arms so the `!=`
test comes first puts the boolify straight back (score 60); an initialised local
(`int r = 0; if (c) r = 1;`) makes the first move unconditional (score 200); a
`switch` produces a real branch diamond (score 600).

**Inference, and flagged as such:** that retail's source literally contained an
`else if` on the complement plus an unreachable `return`. It did contain
*something* in that position — the bytes force a third exit-shaped construct — but
`return TRUE;` is the shortest spelling that reproduces them, not evidence about
what was written. A default arm, or a third condition the compiler proved dead,
would do as well.

The technique is written up in the workspace at `docs/MATCHING_TIPS.md` →
*"Two conditional moves in the 'wrong' order are an `else if` ladder, not a
boolify"*. **That file is uncommitted in the workspace as of this note.**

## The rest, briefly

**`AddFixedPoint64`** — **fact** read off 11 instructions: the upper sum is
computed *before* the lower, and the carry is an unsigned compare of the low result
against the low input (`cmp r2, ip / addlo r1, r1, #1`), with a single paired
`stmia r0, {r1, r2}`. The signature was taken verbatim from the pre-existing
`extern` in `src/overlay_29_0230BBAC.c`, which **agrees exactly**. Matched first
candidate, all three regions.

**`sub_02062AD0`** — three tail-chained calls with no shuffling and no narrowing:
`IsMonsterMissionAllowedStory(FemaleToMaleForm(GetBaseForm(id)))`. **Fact from the
ledger's measurements:** the only thing this function's bytes constrain is that its
return width *pairs* with `IsMonsterMissionAllowedStory`'s — declaring the callee
`s32` while returning `bool8` adds a trailing `and r0,r0,#0xff` (score 100). Both
`bool8`/`bool8` and `s32`/`s32` score 0, and `s16` versus `enum monster_id` for the
parameter is codegen-identical because `-enum min` sizes `monster_id` to a signed
short (`MONSTER_INVALID = -1`, max ≈ 1154). **So the landed signature is a choice
among byte-identical options, not a deduction.**

**`ov29_022EFB84`** — 10 instructions: `ov29_0234D8A0(0)` then a guarded
`ov29_022EA370(10, 0x62)`. The wip keeps two unmeasured variants (`var/alt_order.c`
with an inverted early-return, `var/alt_s32.c` with an `s32` parameter); **no scores
are recorded for them**, so this note cannot say whether either also matches.

**`ov29_022E45D0`** — two `PlayEffectAnimationEntity` calls with effect ids `0x2F`
and `0x30`, each taking `GetEffectAnimationWanOffset(<same id>)` as its fourth
argument. **Fact:** the `and r3, r1, #0xff` before each call is what pins that
fourth parameter to `u8`. **Fact:** the two calls use different scratch registers
for the four stacked arguments (`{r0, ip}` versus `r1`/`r2`); that fell out of
register allocation from two identically-written source statements and needed
nothing.

**`InitMoveWrapper`** — 4 instructions, a tail call that forwards arguments 2 and 3
to `InitMove` and **discards argument 1**. The ledger ran two negative controls,
which is what makes "it matched" mean anything on a function this small: passing
arg0 instead of arg1 scored 115, and dropping the unused first parameter scored 210
(both `mov`s vanish). **So the arity of three is forced by the bytes.** That the
discarded first argument is a `struct entity *` is **inference** from the two call
sites, where the same register is dereferenced at `+0xb4` (`struct entity::info`);
an unused parameter emits nothing, so no build can check it.

## Shared-type change — flag this loudly

`include/main_0202A66C.h` gains **two new struct types**, and the header is now
included by three translation units (`src/main_0202A66C.c`, `src/main_0203D538.c`,
`src/overlay_31_02382820.c`):

```c
struct unk_0202A5CC { u16 field_0x0; u8 field_0x2[2]; s32 field_0x4; };
struct unk_0202A75C { u8 field_0x0[0x100]; s32 field_0x100; };
```

Every number in both is **fact**, read off `CreateParentMenuFromStringIds`' 40
instructions:

- `add r1, r1, #8` / `add r6, r6, #8` — the input element stride is **8**.
- `ldrh r0, [r1]` — the field at `+0` is a **2-byte** load, used both as the loop
  terminator and as the id argument to `GetStringFromFileVeneer` (MWCC CSEs the
  one expression).
- `ldr r0, [r6, #4]` — a **4-byte** field at `+4`.
- `add r0, r2, #1 / add r0, r0, r0, lsl #6 / mov r0, r0, lsl #2` — `(n+1)*65*4`
  = `(n+1)*0x104`, so the **output** element is `0x104` bytes.
- `str r0, [r5, #0x100]` / `add r5, r5, #0x104` — `0x100` bytes of buffer, then a
  4-byte field at `+0x100`.
- `mov r1, #8` before `bl MemAlloc` — alignment flag 8.

The `u8 field_0x2[2]` is **padding inferred from the stride**, not a field anything
touches: stride 8 with a `u16` at `+0` and a 4-byte field at `+4` leaves two bytes
unaccounted for. Nothing reads them.

**Names are placeholders on purpose.** `unk_0202A5CC` is named for the function
that takes it and `unk_0202A75C` for `CreateParentMenuInternal`, per CLAUDE.md's
rule; no claim is made that this is a "menu item" type, even though the body plainly
turns string ids into rendered strings. **`struct unk_0202A75C` is arguably internal**
— it appears only in `src/main_0202A66C.c`, on the provisional `extern` for
`CreateParentMenuInternal` — and a reviewer might reasonably want it out of the
public header.

**Header hygiene, worth a look:** both structs are defined *above* the header's
`#include "util.h"`, so the header is not self-contained — it compiles only because
every includer already has the base integer typedefs in scope. (`util.h` itself has
the same dependency, so this is consistent with the tree rather than novel, but it
is not *right*.)

`include/overlay_29_0231E9F0.h` also gains `#include "dungeon_mode.h"` (needed for
`struct entity`), which now reaches every file including that header. Byte-neutral
per the build; noted because it widens a small header considerably.

**No existing struct or enum was modified by this commit.** `no_slip_cap_counter`,
`is_not_team_member`, `field_0x171` and `anim_ctrl` were all already in
`include/dungeon_mode.h` at their documented offsets — **fact**, checked; nothing in
`dungeon_mode.h` is touched by the diff.

### `CreateParentMenuFromStringIds` had three prototypes

**Fact**, all three in the tree before this commit, all mutually incompatible:

| site | declaration |
|---|---|
| `src/main_0203D538.c:70` | `u8 (void *, u32, void *, void *)` |
| `src/overlay_31_02382820.c:42` | `u8 (u32 *, u32, struct struct_2 *, u32 *)` |
| `src/overlay_11_02307334.c:97` | `u8 (void *, u32, void *, void *)` |

They could coexist only because the function had no header. The first two were
replaced by the include; the call sites now carry an explicit
`(struct unk_0202A5CC *)` cast on the fourth argument.

**Why cast rather than weaken the parameter to `void *`:** the body indexes the
fourth argument as `struct unk_0202A5CC` throughout — `+0` as a `u16`, `+4` as a
word, stride 8 — so typing it `void *` would only move the same casts inside the
function, where they would be less checkable. That is a judgement call, not a
byte-level requirement.

**The third one is still there.** As of this commit `src/overlay_11_02307334.c:97`
retains `extern u8 CreateParentMenuFromStringIds(void *, u32, void *, void *);`
and does **not** include `main_0202A66C.h`, so the disagreement remains and the
build still cannot see it. That file's six call sites pass `&ov11_02322D38` and
friends — globals whose own types were still unresolved here. This is exactly the
CLAUDE.md failure mode ("a build cannot catch this"), left open by this commit and
addressed later on the branch; a reviewer reading commits in order should expect it.

## Open questions for a reviewer

- **`ov29_022E45CC`'s parameter is a judgement call, and it cuts against tree
  precedent.** The bytes are one `bx lr`; `void f(void)` and
  `void f(struct entity *)` are byte-identical. The parameter comes from the call
  site in `TryInflictDestinyBondStatus` (`asm/overlay_29_0231516C.s:736`), where
  `mov r0, r5` immediately precedes the `bl` and `r5` has already been validated as
  an entity twice. But **26 of the 27 empty-bodied functions already in `src/` are
  declared `(void)`**, several with call sites that also load `r0` first. The 27th
  (`sub_02002228(u32)` in `src/main_0200224C.c`) is the precedent this followed. A
  reviewer may reasonably prefer consistency with the 26.
- **`extern s16 ov10_022C4BE4[20];` — the bound `20` is inference**, from the
  `movhs r0, #0x13` clamp, not from anything in the asm. An `extern` array's bound
  does not affect codegen, so **the build cannot check it** and a wrong bound would
  be silent.
- **`MoveIsNotPhysical` returns `int`, `CategoryIsNotPhysical` returns `bool8`,** for
  two functions with the same three-instruction tail. Each took the return type its
  pre-existing in-tree declaration used. Both were measured at score 0 with either
  type, so **this is inconsistency inherited, not deduced**; a reviewer may want them
  unified.
- **`CategoryIsNotPhysical`'s parameter is `s32`, not `enum move_category`,** though
  the name and pmdsky-debug's note both suggest the enum. Reason (**fact**): the only
  caller passes `damage_data->field_0xd`, declared `u8` in
  `include/overlay_29_02308FBC.h`; `u8 → s32` promotes silently, `u8 → enum` is the
  implicit integer-to-enum conversion the real build's `-W error` rejects and a
  scratch cannot see. Widening it means editing a caller this work did not touch.
- **The unreachable `return TRUE;` in both functions** is load-bearing but is not
  evidence about retail's source. See above.
- **Three functions have no ledger** — `ov29_022E45D0`, `TickNoSlipCap`,
  `ov29_022EFB84`. Each wip directory holds a single candidate byte-identical to
  what landed, which is consistent with a first-draft match, but **no scores and no
  intermediate attempts are recorded for them**. The commit message's blanket claim
  of score 0 in all three regions is the only record; this note does not
  independently corroborate it, and cannot reconstruct what (if anything) was tried
  in between.
- **`struct unk_0202A75C` may not belong in a public header**; only
  `src/main_0202A66C.c` uses it.
- **`CreateParentMenuInternal` (asm, `0x0202A75C`) has no declaration anywhere in
  the tree**; the one in `src/main_0202A66C.c:6` is new and provisional, and its
  first three parameters are `void *`/`u32`/`void *` purely because this function
  passes its own through untouched.
- **The `s32` field at `+0x100` of `unk_0202A75C` is copied from `+0x4` of
  `unk_0202A5CC` unchanged**, including once past the terminator — the target writes
  `q->field_0x100 = items->field_0x4;` after the loop, reading the *terminating*
  entry. That is **fact** from the asm; what it means is not established.
- **`ov29_022EFB84`'s `bool8` parameter is inference** from a `cmp r4, #0` on a value
  passed straight through; `s32` (kept as `var/alt_s32.c`) was never scored.
