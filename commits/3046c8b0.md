## `lib/DSE` is built with different flags -- this is the headline

**Fact, read off the real build command line, not assumed.** `lib/DSE` compiles
with **`-O4,p`** and **`-enum int`**, where the arm9 modules use `-O4,s` and
`-enum min`.

Anyone matching an SDK or `lib` function must check the actual `mwccarm.exe`
invocation the build prints for that object. Assuming the `main` flags is a
silent way to make correct C look unmatchable.

## Field evidence

**Fact.** Field names come from `struct dse_channel` in `lib/DSE/include/dse.h`
and match the offsets the asm uses: `bend_jitter_amplitude` at `0xa`,
`field_0x56` at `0x56`, `bend_sensitivity_override` at `0x59`.

**Inference.** That the last one's *meaning* agrees with `SetKeyBendRange`
writing to it. Consistent, not proven.

## A byte-order detail read straight off the shifts

**Fact.** `SetTuningJitterAmplitude` and `SetUnknown2` read their two operand
bytes in **opposite orders** -- little-endian for the first, big-endian for the
second -- which the asm's shift operands show directly.

Worth recording because it looks like a transcription error and is not.

## Two `lib/` landing mechanics `extract_function.py` does not handle

Both now in `docs/INSERTING_AND_BUILDING.md`:

1. The tool **hardcodes** `asm/`, `src/`, `include/` and `main.lsf`, so it must
   be run with `lib/DSE` as the working directory -- and the object lines it then
   inserts into `main.lsf` carry **no `lib/DSE/` prefix** and must be corrected.
2. It emits `.include "main_XXXX.inc"`, which is right for arm9 (search path
   `./asm/include`), but lib asm is built with `-Ilib/DSE/asm/` and its existing
   files use `.include "include/main_XXXX.inc"`. The four split files were fixed
   to match.
