**Fact.** The resolver that rewrites a script entity id **in place** and reports
which storage it maps to. It redirects the four special ids `0x2E`-`0x31`
through `SPECIAL_ACTORS`, then dispatches on the entity's kind field: kind 1
resolves the player slot from script variable `0x34`; kind 2 a team member from
variables `0x35` and `0x36`; kind 3 range-checks against the loaded unit or
adventure NPC list; anything else handles the appointed leader.

## The central lesson: a store cannot reveal signedness

`strh` is identical for `u16` and `s16`, so a wrong choice is **invisible until
something reads the field**. This is the first decompiled function that reads
these, which is why two type errors surfaced only now. Both were **diagnosed
from the load instruction**, not assumed.

### `enum script_entity_id` gains `ENTITY_NONE = -1`

**Fact.** Under `-enum min` an enum with no negative enumerator is unsigned, so
the `SPECIAL_ACTORS` redirect slots compiled to `ldrh` where the target has
`ldrsh`.

**Fact.** An explicit `(s16)` cast does **not** help -- the destination store is
16-bit, so the compiler folds the conversion away. This is worth knowing because
the cast is the obvious first thing to try.

**Fact, verified in isolation.** The sentinel was added alone, nothing else in
the tree modified, and the ROM still matched -- so it is byte-neutral everywhere
else and affects only code that reads such a field. The name follows
`EPISODE_NONE = -1`, already in the same file.

### `struct unk_020A7FF0.field_0x0` becomes `s16`

**Fact.** Same mechanism. It was declared `u16` in [`8157b86c`](8157b86c.md),
which reads only `field_0x8` -- genuinely unsigned, `ldrh`. Both resolvers read
`field_0x0` with `ldrsh`.

## A prototype that changes register allocation

**Fact.** `sub_02055410` is declared as taking the member index rather than
`void`. The argument is already in `r0` from `GetAppointedLeaderMemberIdx`, so
the call needs no register move -- which is what leaves `r0` occupied across the
sentinel comparison. Declared `void`, the function is otherwise identical but
allocates that constant to `r0` instead of `r1`.

Worth generalising: a **provisional prototype is not only a typing question**,
it can decide codegen. A wrong one can make an otherwise-correct body unmatchable
in a way that looks like a body problem.
