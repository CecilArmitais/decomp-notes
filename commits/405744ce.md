## `enum monster_id` gains `MONSTER_INVALID = -1`

Third instance of the same defect, and the reasoning is identical to
`ENTITY_NONE` in `4f8467eb`:

- **Fact.** This function reads nine `SPECIAL_ACTORS` slots of type
  `enum monster_id` with `ldrsh` — a signed load. An enum with no negative
  enumerator is unsigned under `-enum min`, so those compiled to `ldrh`.
- **Fact.** Verified byte-neutral in isolation: added alone, with nothing else
  in the tree modified, and the ROM still matched. That is the standard the
  community asked for, applied the same way as last time.
- **Naming**: `MONSTER_NONE` is **taken** — the `_MONSTER_ID_GENDERED(NONE, 0)`
  macro defines it as 0 — so the `_NONE = -1` idiom used by `EPISODE_NONE` and
  `ENTITY_NONE` was unavailable. `MONSTER_INVALID` was chosen by the human
  directing this work, not by me.

**`struct unk_020A7FF0.field_0x2` also becomes `s16`**, on the same evidence:
the switch's `default` case reads it with `ldrsh`.

That is now **three** fields corrected this way across two commits. The reason
they all surfaced late is worth stating plainly: **storing to a field cannot
reveal its signedness** — `strh` is the same instruction either way. The PR's
setters had every store matching while two of these types were wrong. Only a
read can tell, and this cluster contains the first readers.

**Open**: whether other enum-typed fields elsewhere in the tree have the same
latent problem. Anything never read is unverified by construction.

## New declarations

`struct unk_020B0A48` — the 0x44-byte record `TEAM_MEMBER_TABLE_PTR` points at,
with an `s16` at `+4`. **Fact**: the stride comes from `smlabb r1, r2, #0x44, r3`
and the field from the `ldrsh [r1, #4]` that follows. The address `0x020B0A48`
is derived by counting from the preceding label in
`asm/main_rodata_020A2808.s` — `TEAM_MEMBER_TABLE_PTR` holds one word and is
followed by `_020B0A4C`.

`GetMainCharacter1`, `GetMainCharacter2`, `GetMainCharacter3`, `GetHero`,
`GetPartner` and `sub_02056914` all return that pointer and had no declaration
anywhere. **Inference**: that they return the *same* type is read from all six
being dereferenced at `+4` with `ldrsh` and their results used identically.

## What the function does

**Fact**, from control flow:

1. Calls `sub_02065050(p)` to resolve the id in place, keeping its result as the
   return value for the non-failure paths.
2. Clears `*out`, and returns -1 immediately if the resolved id is -1.
3. If `ENTITIES[id].field_0x0 == 3`, range-checks `0x16`–`0x19` (unit NPCs) or
   `0x1a`–`0x1d` (adventure NPCs), consulting `OverlayIsLoaded(0xd)` /
   `ov11_022E96E4`, `DEBUG_FLAG_STAGE_NPC_DUMMY`, and
   `GetUnitNpcIds` / `GetAdventureNpcIds`. Every path here returns -1; they
   differ only in what they write to `*out` and whether they poison `*p`.
4. Otherwise a switch over the entity id maps to a team member
   (`GetMainCharacter1/2/3`, `GetHero`, `GetPartner`, `sub_02056914`), a script
   variable (`0x3e`, `0x40`, `0x44`), or a `SPECIAL_ACTORS` slot.
5. The `default` falls back to `ENTITIES[id].field_0x2` when `*out` is still 0.

**Inference.** Read together with `sub_02065050`, this pair is "given a script
entity id, produce the monster it currently refers to" — the redirect layer that
makes `SPECIAL_ACTORS` meaningful. That reading is consistent but the functions
keep their `sub_` names.

**Worth a reviewer's eye**: case `0x39` writes `*out` **only when the slot is
non-zero**, while the other `SPECIAL_ACTORS` cases always write and then test.
That asymmetry is in the target (`strneh` vs `strh` + `cmp`), not a slip.

## How it was matched

4195 → 1500 → **0**, three iterations, and the first two fixes were techniques
already recorded from earlier functions in this cluster:

1. **Bind `&ENTITIES[id]` to a pointer local**, because the target computes the
   element address once (`add r3, ip, r3`) and reuses it in the `default` case.
   Combined with **converging the type-3 failure paths on one trailing
   `*p = -1; return -1;`** instead of letting them predicate inline: 4195 → 1500.
2. **Switch case bodies are emitted in source order.** The target's blocks run
   `0x3a, 0x3b, 0x39, 0x32, 0x33, 0x35, 0x36, 0x37, 0x38, 0x34` — not numeric.
   Reordering the source to match: 1500 → **0**.

The second is new and now in `docs/MATCHING_TIPS.md`. Read the order off the
target's block addresses rather than guessing; it costs nothing and is
mechanical.
