## Naming

Nothing is named for what it means. All three struct types are placeholders, all
fields are offsets, and `EVENTS`, `_020AFC70` and `sub_0201E380` were already in
`upstream/main` and keep their names.

| type | named for | why |
|---|---|---|
| `struct unk_020A5488` | address of `EVENTS` | it types that table |
| `struct unk_02064F94` | the function that receives it | no global uses it |
| `struct unk_02064FE4` | ditto | ditto |

Local names are deliberately structural: `data` is a cursor over 4-byte records,
`count` the loop bound, `value` the field a comparison reads, and
`sub_0201E380`'s parameters are positional (`a`, `b`, `c`, `d`) because only its
call site is understood, not the function. An earlier draft called them `colors`,
`index` and `slot`, and the `EVENTS` field `kind` — all inferred from code two
calls downstream, so all removed.

## `unk_020A5488` — the `EVENTS` record

**Fact.** 12 bytes. Both `sub_02064FFC` and `sub_02065014` index it with a
stride of 12. First record decodes as:

| offset | bytes | type |
|---|---|---|
| `0x0` | `04 00` | `s16` (read `ldrsh`) |
| `0x2` | `B9 00` | `u16` |
| `0x4` | `00 00` | `u16` |
| `0x6` | `FF FF` | `u16` |
| `0x8` | `.word` | `char *` |

**Fact worth flagging to a reviewer.** `_020A5490` is **not** a separate table.
It is a `.global` sitting at `EVENTS + 8`, i.e. on the pointer field of record 0.
`sub_02064FFC` uses it as its base, so the target's literal pool reads
`.word _020A5490` while this source produces `EVENTS+0x8`. Same address — the
matching build proves it. decomp.me cannot resolve that equivalence and will
show it as a diff (score 5); it is a false positive, the same shape as
`DEMO_TEAMS+0x2` vs `_020A68CA` seen earlier on this branch.

**Inference, moderately strong.** This layout is identical to pmdsky-debug's
12-byte `struct script_level` — `uint16 mapty; undefined2; uint16 mapid;
uint16 weather_id` (documented as `0xFFFF` for none, and offset `0x6` here *is*
`0xFFFF`); `char* name`. That is suggestive, but the global is named `EVENTS`,
not levels, so I have not acted on it. Whoever identifies this table should
resolve that tension rather than assume either way.

## `sub_02064F94` and `sub_02064FE4`

```c
void sub_02064F94(struct unk_02064F94* a, u32* data, int count)
{
    int i;

    for (i = 0; i < count; i++, data++) {
        sub_0201E380(_020AFC70 + 0xcc, data, a->field_0x8, i);
    }
}

void sub_02064FE4(struct unk_02064F94* a, struct unk_02064FE4* b)
{
    sub_02064F94(a, (u32*)((u8*)b + b->field_0x20), b->field_0x24);
}
```

**Facts.** `_020AFC70` holds a pointer and is **reloaded on every iteration**
(the load sits inside the loop), so the C must read it there. `sub_02064FE4` is
a tail call (`bx ip`). Its `b` supplies a byte offset at `0x20` and a count at
`0x24`. The one located caller, `sub_0206407C`, tail-calls
`sub_02064FE4(*_020B0B04 + 0x40, arg)`, so `a` is a sub-object at `+0x40` inside
whatever `_020B0B04` points at.

**Inference.** This is palette work: `sub_0201E380` computes
`x->field_0x18 + 2 * (d + c * 256)`, passes it to **`Rgb8ToRgb5`**, then sets
`x->field_0x1c[c] = 1` — reads as "convert a colour into a palette slot and mark
it dirty". Everything in that sentence except the arithmetic is inferred from one
function name, which is why none of it reached the source.

## Matching notes

Three techniques, all "write it the way a human would", all confirmed here:

1. **Converge on one return instead of an early one.** `sub_02065014` first came
   out with the `id == -1` guard as an early `return 1`, which MWCC turned into
   predicated `moveq`/`bxeq` (score 465). The target branches to a *shared* tail,
   so nesting the guard — `if (id != -1) { … } return 1;` — matched at 0. This is
   the exact inverse of `sub_02065B14` in commit `5a376688`, where the fix was to
   *keep* an early return; the diff tells you which you need.
2. **Iterate with an advancing pointer, not an index.** `&data[i]` makes the
   compiler re-index from the base each pass (`add r1, r7, r5, lsl #2`); the
   target keeps a running cursor (`mov r1, r7` … `add r7, r7, #4`). Score
   340 → 30.
3. **Increment order follows source order.** With `data++` in the body and `i++`
   in the `for` clause, the body's increment emitted first. Moving both into the
   clause as `i++, data++` matched. Score 30 → 0.
