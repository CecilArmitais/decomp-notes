## The find: a stale extern that the build could not catch

**Fact.** `src/overlay_29_0232E250.c` declared

```c
extern s32 ATK_STAT_IDX;
extern s32 SPATK_STAT_IDX;
extern void BoostDefensiveStat(struct entity*, struct entity*, s32 stat_idx, s16 n_stages);
```

while `include/move_orb_effects.h` — the canonical header, whose definitions
live in `src/move_orb_effects.c` — declares

```c
struct StatIndex { int id; };
void BoostDefensiveStat(struct entity *user, struct entity *target, struct StatIndex stat, s32 nStagesRaw);
```

The two disagree on the third parameter (a one-int struct by value vs `s32`) and
the fourth (`s32` vs `s16`), and on the globals' type. **Because the two
declarations lived in different translation units the compiler never saw the
disagreement, and the ROM matched anyway** — exactly the failure mode
`CLAUDE.md` warns about, found here only because this batch needed the same
symbols.

Replaced with `#include "move_orb_effects.h"` plus correctly typed globals.
`DoMoveDefendOrder` in that file is otherwise untouched and still matches.

**How it surfaced:** writing the ten new wrappers against the header produced a
`redeclared` error naming `struct StatIndex`, which is what sent me to compare
the two. Candidates written against the *stale* extern would have compiled and
matched too — so this was luck of ordering, not diligence.

## Decompiled

**Fact.** DoMoveTag0x1AB, DoMoveDoubleTeam, DoMoveMinimize, DoMoveAmnesia,
DoMoveBoostAttack1, DoMoveBoostDefense1, DoMoveBoostDefense2, DoMoveDefenseCurl,
DoMoveGrowth, DoMoveFamish.

Eight forward to `BoostOffensiveStat` / `BoostDefensiveStat` /
`BoostHitChanceStat` with `ATK_STAT_IDX` or `SPATK_STAT_IDX` and a stage count
of 1 or 2. `struct StatIndex` being a single-`int` struct passed by value is why
the asm loads the global's word straight into `r2`.

**Inference.** `DoMoveFamish` reads an `s16` global (`ov10_022C45BC`, `ldrsh`)
and passes it to `TryDecreaseBelly`; that helper is undeclared and its prototype
is written from the call site.
