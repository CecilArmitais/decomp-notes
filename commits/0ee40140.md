## Two codegen levers, both measured

### `DUNGEON_PTR` as a scalar or as an array is not a style choice

This is the headline finding of the batch and it is fully measured, in
`wip/PopulateActiveMonsterPtrs/LEDGER.md`.

Both spellings name the same address and **both are established in the tree**,
so neither is an invention. **Fact, counted at this commit:** the array form
`extern struct dungeon *DUNGEON_PTR[];` (used as `DUNGEON_PTR[0]->`) appears in
**52** `src/*.c`; the scalar `extern struct dungeon *DUNGEON_PTR;` (used as
`DUNGEON_PTR->`) in **29**. The array form is the majority, which is what makes
"normalising" to it feel like tidying — but the scalar form is not a rarity
either, and `docs/MATCHING_TIPS.md`'s framing of it as the unusual one
understates how common it is.

**Measured:** with the array form, `PopulateActiveMonsterPtrs` scores **235**
with 8 differing rows arising from **one** defect — MWCC hoists the
`ldr DUNGEON_PTR` out of the third loop, where retail reloads it every
iteration. With the scalar form it scores **0** in all three regions. Nothing
else changed.

**Falsified, all at the identical 235 / 8 rows** (fact, eleven variants in
`cand/`): `while` vs `for`, `n++` inside the subscript, storing `0` vs `NULL`
vs a local set to `NULL`, writing through the union's other arm,
`*(struct dungeon **)&…` and `*(void **)&…` casts on the store, the store
written twice, a `struct dungeon *` local assigned in the body, and a fresh loop
variable. **No spelling of the store defeats the hoist.**

**The mechanism was confirmed before a plausible spelling existed**, using
`volatile` purely as a diagnostic:
`(*(struct dungeon *volatile *)&DUNGEON_PTR[0])->…` scored 0, and
`extern struct dungeon *volatile DUNGEON_PTR2[];` scored 5 — the residual being
only the renamed `.word`. The scalar declaration then reproduced that with no
`volatile` at all.

**And there is a control measurement**, deliberately kept as
`wip/GetTeamMemberIndex/cand/arrayform.c`: in the neighbouring
`GetTeamMemberIndex`, whose loop **stores nothing**, the two spellings produce
identical instructions — including the *hoisted* `ldr r3, [r1]` above the loop.
(The control scores 5 rather than 0 only because it declares the global under a
renamed symbol, `DUNGEON_PTR_A`, so its one differing row is the `.word` name.)
So the lever only bites in a loop that stores.

The *inference* on top of the measurements: with `struct dungeon *DUNGEON_PTR[]`
MWCC concludes the store `active_monster_ptrs[n] = NULL` cannot alias the array
element, making the load loop-invariant; with a scalar object it does not. Not
verified beyond these measurements.

**Consequence a reviewer should look at, because it reads as inconsistency:**
this commit lands **both** spellings, deliberately. `src/dungeon_util_2.c` gets
the scalar (its most-constrained function requires it); the four other new files
get the array form (their functions are indifferent, so the house style wins).
Normalising either way without re-measuring would move a function that currently
matches.

### A long `a | b | c | …` gets reassociated into a tree

`UpdateStatusIconFlags` ORs fifteen 64-bit table entries into one accumulator.
The target is a strict chain — every `orr` consumes the previous one (fact, read
off `0x022E3AB4`). Both single-expression spellings miss: `icons |= A | B | …;`
builds `A|B|…` first (**189 differing rows, +11 length**), and the
left-associated `icons = icons | A | B | …;` is no better because MWCC
rebalances the operand list into a tree (**155 differing rows, +10**). Writing
**one statement per term** took NORTH_AMERICA from 155 to score 0, and EU and JP
matched with it. That single edit was the whole difference.

Two readings that fell out of the same function and are *evidence*, not levers:

- **`orr rHI, rHI, #0` next to a real `orr rLO, rLO, #const` means the
  accumulator is 64-bit.** MWCC folds `x | 0` away for a 32-bit `x`. That is how
  `u64 icons` was identified before any C was written.
- **`add rA, base, idx lsl #3` + `ldr rLO, [base, idx lsl #3]` +
  `ldr rHI, [rA, #4]` is a 64-bit array element**, not two parallel `u32`
  arrays — hence `extern const u64 STATUS_ICON_ARRAY_*[];`. The `ldm`/split-pair
  distinction is a scheduling outcome, not a type difference.

Both entries are written up with before/after C in
`docs/MATCHING_TIPS.md` (workspace commit `8efb20a`, the companion to this one).

## Evidence behind the individual bodies

### `UpdateStatusIconFlags` — four of the bit constants corroborate against the header

**Fact**, counting bit positions in `struct status_icon_flags`
(`include/dungeon_mode.h:65`, pre-existing, with pre-existing comments):
`0x2000` = bit 13 = `f_low_hp`, `0x1000000` = bit 24 = `f_grudge`,
`0x2000000` = bit 25 = `f_exposed`, `0x8000000` = bit 27 = `f_lowered_stat`.
Each is set by the branch you would expect from the field name — the `< max_hp/4`
test, `info->grudge`, `info->exposed`, and the ten-way stat-modifier test. Four
independent hits is good corroboration that the bodies are read correctly. The
constants were **left as hex literals rather than named**, which is the
conservative choice (naming them would assert the mapping); a reviewer may
reasonably want them replaced by the field names.

**`icons |= 0x2000` appears twice** — once for low HP and once under
`DUNGEON_PTR[0]->identify_orb_flag` — and that is not a transcription slip:
the target emits `orrne r1, r1, #0x2000` at two separate sites (fact, lines 151
and 164 of the NA target). Retail sets the same icon bit from two conditions.

**`*(u64 *)&info->status_icons = icons;`** writes the whole 8-byte bitfield
through a pointer cast. It is the only spelling tried that is recorded; whether
a union member or a field-by-field assignment also matches is **not checked**.

The Sudowoodo guard is worth one line because it looks like a compiler joke and
is actually evidence: `mov r5, #1` (which is `show_sleep = TRUE`) is *reused* as
the operand of `addne r3, r5, #0x310` to build `0x311` =
`MONSTER_SUDOWOODO_SECONDARY`. For `r5` to hold 1 there, the source must assign
`show_sleep` **before** the id test — fact, and it pins the statement order.

### `IsFloorOver` — pmd-red gave the shape and the shape was wrong

**Fact, from the commit message:** pret/pmd-red has an equivalent function;
translating its **nested** form literally scored **1525**, and flattening to
**four independent early returns** scored 0. pmd-red is a different game built
by a different compiler, so it is a source of structure and never of spelling.
This is the clearest instance in the batch, and it is the argument for treating
a pmd-red body as a hypothesis rather than an answer.

The two `end_floor_flag` tests (`== 1`, `== 2`) are written as separate `if`s
setting the **same** `floor_loop_status`, rather than as `||`. That is what
scored 0; whether `||` also would is **not recorded**.

### `EndBurnClassStatus` / `EndCurseClassStatus` — the switch is wider than the enum

**Fact, read off the targets.** `EndBurnClassStatus` does `cmp r0, #5` and a
dense six-entry jump table; `EndCurseClassStatus` does `cmp r0, #7` and a dense
eight-entry table. But `enum status_burn_id` (`include/enums.h:2836`) stops at
`STATUS_BURN_PARALYSIS = 4`, and `enum status_curse_id` (`:2904`) stops at
`STATUS_CURSE_EMBARGO = 6`. To make the table dense, the source must have a
`case` at 5 and at 7 respectively.

The commit writes **bare `case 5:` and `case 7:`** alongside the named
enumerators, rather than adding enumerators. That is the right call under
CLAUDE.md — an enumerator is a name, and `include/enums.h` is shared — but it
leaves a live question: **the asm says these enums are missing a value each**,
and that is a finding for pmdsky-debug rather than for this diff. Whether the
retail source wrote a named constant there is unknowable from the bytes.

Block layout confirms the usual MWCC rule and is worth recording because three
other functions in this commit depend on it: in `EndCurseClassStatus` the jump
table points case 3 at the **earlier** address and case 2 at the later one, so
**blocks are emitted in source order while the compare/table is sorted**. The C
therefore lists `CURSED, SNATCH, DECOY, GASTRO_ACID, HEAL_BLOCK, EMBARGO` —
source order, not numeric order.

### `GetMonsterOrTrapName` / `SubstitutePlaceholderStringTags` — the same dispatch, twice

Both switch on `entity->type` (`ldr` at offset 0, fact) and both rely on the
source-order rule above. `SubstitutePlaceholderStringTags`' block order is
MONSTER, ITEM, TRAP; `GetMonsterOrTrapName`'s is MONSTER, TRAP, …, default.

**`ENTITY_ITEM`'s position in `GetMonsterOrTrapName` is genuinely not
recoverable** (fact, and the ledger says so): its body is empty, so it emits no
block and folds into the sorted compare chain wherever it was written. It is
placed third because that is where the id sorts — an arbitrary, byte-neutral
choice.

`((struct trap *)entity->info)->id` is read `ldrb` in both, consistent with
`enum trap_id` being a 1-byte unsigned enum under `-enum min` (fact).
`GetTrapName` has **no declaration anywhere in the tree** — only
`.public GetTrapName` and its body — so the one added here is provisional,
derived from that body. Both `enum trap_id` and `u32` for its second parameter
score 0; the enum form was kept only because it avoids an implicit conversion
the scratch (no `-W` flags) cannot see.

## Region handling — two different JP shifts in one commit

copies. Consolidating it is out of scope here but is the kind of thing that gets
harder with each copy.

The four effect wrappers need **no** region handling at all: `0x144`, `0x143`,
`0x25` and `0x30E` are identical in all three targets (fact), and `0x144` is a
valid rotated-8-bit ARM immediate so it is even emitted as `mov`, not a pool
word.

## Shared-type changes: none — and two near misses

**Fact, from the diff:** the only files under `include/` touched are eight
headers, and **every hunk in them is a function declaration**. `dungeon_mode.h`,
`enums.h`, `dungeon.h`, `item.h` and every other shared type header are
untouched. No struct grew, no enum gained a member, no field changed width.

That is not an accident, and the two places it was nearly otherwise are the
interesting part:

1. **`enum status_burn_id` and `enum status_curse_id` are each one enumerator
   short of what the asm dispatches on** (see above). Extending them would have
   been the natural-looking fix and was not done. Under `-enum min` neither
   addition would have changed the storage width (both stay under 256), so this
   was a naming decision, not a layout one — but a reviewer should know the
   option was on the table.
2. **Three cross-translation-unit *declaration* changes** that are not in
   `include/` and therefore easy to miss in a header-only review:
   `SetPreprocessorArgsStringToName` widened (`src/move_orb_effects.c:43`),
   `SpawnDroppedItem` retyped to `bool8`
   (`src/dungeon_projectile_throw.c:39`), and `IsFloorOver`'s two `s32`
   declarations replaced by a `bool8` header. These behave like shared-type
   changes — they are the tree's only statement about those symbols — without
   living where a reviewer looks for them.

Neither `SetPreprocessorArgsStringToName` nor `SpawnDroppedItem` nor `strcpy`
has an owning header; each is still declared per-file, so the corrected
signatures now coexist with other spellings elsewhere. **`strcpy` in particular
is declared in seven `src/*.c` files** (fact, grep), and they do not agree:
`src/main_0202593C.c:6` and `src/item_util_1.c:28` drop the `const`. The line
added to `src/dungeon_util_2.c` copies the majority spelling verbatim from
`src/overlay_11_02307334.c:206`, which is the conservative choice and also
another copy.

## Naming — mostly inherited, with one thing to check

Nothing was identified in this commit. Function names all came from the asm
(pmdsky-debug names already in the tree, or `ov29_<addr>` placeholders kept as
placeholders: `ov29_022E3E74` stays `ov29_022E3E74`). Data symbols keep their
`ov29_<addr>` names. `struct unk_0233C9E8` and its `field_0x…` members are
inherited from [`3ce56d48`](3ce56d48.md).

**Parameter names: mostly inherited, and checkably so (fact).**
`EndCurseClassStatus`'s `next_curse_class_status_being_applied` /
`log_message`, `SpawnDroppedItemWrapper`'s four, `EndBurnClassStatus`'s
`user`/`target` and `UpdateStatusIconFlags`' `entity` are **verbatim** the names
in the pre-existing externs being deleted. That is the right provenance:
the tree already said it.

Two exceptions:

- `SubstitutePlaceholderStringTags`' first parameter is landed as `pos`, while
  the nine deleted externs called it `slot` (×2) or `string_id` (×7). `pos` is
  a *third* name, chosen to match `SetPreprocessorArgsStringToName`'s parameter
  that it forwards into. Defensible; still a new name.
- **`CreateHallway`'s seven parameter names are the open question**, and
  [`6422dc78`](6422dc78.md) hands it to this note explicitly. That commit's
  ledger logs a rejected proposal in which a census owner took
  `x0/y0/x1/y1`, `vertical` **from pmdsky-debug** and narrated them as reasoned
  from the code; they were scrubbed back to `arg1 … arg7`. This commit lands
  `x, y, end_x, end_y, vertical, turn_x, turn_y` — which includes `vertical`.

  **I could not establish where they came from.** There is no census, ledger or
  note for `wip/CreateHallway` (its `ctx_extra.h` is literally
  `/* Intentionally empty. */`), the commit message does not say, and nothing
  in the workspace records a derivation. The names *are* consistent with the
  decompiled body — the `vertical` branch really does walk `y` first, and the
  `turn_*` pair really are the mid-points — so independent derivation is
  entirely possible. But it is **inference**, and given the rejected import sits
  one commit upstream, a reviewer should decide deliberately rather than assume.
  Parameter names are not symbols and cost nothing to change.

One episode is recorded only in the companion workspace commit `8efb20a`'s

tidy-up pass on `src/overlay_29_02308FBC.c` dropped two
`(enum exclusive_item_effect_id)` casts on a `u8` field, scored 0 in **all
three** regions, and **failed the real build** —

```
src\overlay_29_02308FBC.c:385: illegal implicit conversion from 'unsigned
src\overlay_29_02308FBC.c:385: char' to 'exclusive_item_effect_id'
```

because the scratch flag string carries no `-W`. The casts were restored; this

## Open questions for a reviewer

1. **No EU or JP ROM build.** All sixteen are score 0 against all three regional
   targets, but only `pmdsky.us.nds` was built. Running `make -C pmd-sky eu` and
   `… jp` is the cheap check.
2. **`GetMonsterOrTrapName`'s third parameter** is retained on caller evidence
   alone; the callee's bytes cannot distinguish two parameters from three, and
   the declaration this commit deletes asserted the opposite. Also: the call
   site passes `u8[256]` into a `char *` with no cast and no change.
3. **`enum status_burn_id` and `enum status_curse_id` each dispatch on a value
   they do not name** (5 and 7, dense jump tables). Written as bare `case`s.
   Worth raising upstream in pmdsky-debug.
4. **`CreateHallway`'s parameter names** — provenance not established; see above.
5. **`SpawnDroppedItem`'s `bool8` return** is inference; the call site shows only
   that a value is returned onward.
6. **Both `DUNGEON_PTR` spellings now appear in new files from one commit.** It
   looks like an oversight, it is measured, and normalising it would break
   `PopulateActiveMonsterPtrs`. Do not tidy without re-scoring.
7. **The commit message says "eighteen" pre-existing declarations; the diff has
   twenty.** Prose only.
8. **`JPN_MSG_OFFSET` is not a single global shift** — two id bands in this
   commit take `−0x2C0` and `+0x100`. Nothing enforces which a given function
   needs.
9. **`*(u64 *)&info->status_icons = icons;`** type-puns a bitfield struct. No
   alternative spelling was tested.
10. **Twelve of the sixteen have no ledger**, so for those the only record of
    what was tried is the surviving `cand/` files and the commit message.
