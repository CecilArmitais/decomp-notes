## Layout evidence

**Fact.** All six index `struct dse_channel`'s existing `lfo_settings[4]`, at
offset `0x74` with a `0x10` stride -- the stride the asm computes as
`ip lsl #4`, and the offset another handler in this family loads directly as
`channel + 0x74`.

**Fact.** The three pairs address entries 0, 1 and 2, so key bend, volume and pan
each own one `lfo_settings` slot. Within an entry the setters write `+0xa` and
`+0xc` (`msec_until_lfo_started`, `lfo_envelope_len_msec`) and the `Use` handlers
write `+1` and `+2` (`type`, `output_type`).

**Observation, explicitly not a labelled fact.** `output_type` is set to 1, 2 and
3 for key bend, volume and pan respectively, consistent with the slot each uses.
That is an observation about the constants; the bytes do not label it.

## The finding: statement `if/else` vs ternary

**Fact.** The `Use` handlers needed an explicit `if`/`else` rather than a
ternary. **Every** conditional-expression spelling tried -- `v ? N : 0`,
`v == 0 ? 0 : N`, `!v ? 0 : N`, and `(v != 0)` -- emits `movne` **before**
`moveq`, where the target emits `moveq` before `movne`. The statement form
reverses the pair and matches.

Worth generalising: a ternary and an `if`/`else` are *not* interchangeable to
this compiler, and the difference shows up as **predicate ordering**, which is
easy to misread as noise.
