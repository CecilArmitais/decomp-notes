## `SetPokemonBattled` had a template already in the tree

**Fact.** It is the *battled* counterpart of `SetPokemonJoined`, already
decompiled in `src/main_0204FDFC.c`, and merges into that file beside it. It
differs only in which completion flag it sets (`2` vs `1`) and which flag array
it indexes.

**So the existing function is the evidence**, not anything derived here —
including the `dex_num / 32` and `dex_num % 32` spelling, which is what produces
the target's signed `asr` / `lsr` / `ror` division idiom.

## `GetNbItemAcquired`

**Fact.** Counts the set bits of `items_acquired_flags` across `0x580` entries.
The pointer is hoisted to a local because the target loads it **once** before the
loop; the word and bit indices use signed division and remainder.

## Why the remaining seven are harder than they look

**The instruction counts understate it.**

Four are simply large: `ComputeSpecialCounters` (144 instructions), `CopyLogTo`
(122), `CopyLogFrom` (120), `ClearAdventureLogStruct` (74).

The other three — `SetChallengeLetterCleared`, `SetSentryDutyGamePoints`,
`SetItemAcquired` — are **not** large, but they index the region at `0x260` as
an array spanning `special_challenge_flags` **and** the five
`sentry_duty_game_points` that follow it, and they mix signed and unsigned
division *of the same index* within one function (`SetChallengeLetterCleared`
uses `lsr #5` for the word but the signed `ror` idiom for the bit).

Expressing that without either misdescribing the struct or writing something the
compiler will not reproduce needs more care than this batch had left. **That is a
statement about the time spent, not about the functions.**
