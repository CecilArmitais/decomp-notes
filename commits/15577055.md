## What they do

**Fact**, read off the asm against `common.h`'s `team_member_table`:

1. read `active_team` (offset `0x9877`);
2. index the three `number_active_team_members_*` fields (`0x9850`/`52`/`54`) by
   it, giving a `s16` — call it `n`;
3. if `n == -1`, fail (-1 / NULL);
4. otherwise return `active_roster_member_idxs[n]` — the member index —
   or, for `sub_02056914`, `&members[that index]`, failing if it is also -1.

`sub_02056914` is the pointer counterpart of `GetAppointedLeaderMemberIdx`, the
same pairing as `GetHero`/`GetHeroMemberIdx`. Its caller (`sub_0206549C`) does
`sub_02056914()->id`, which is consistent with the `ground_monster*` return.

**Worth a reviewer's eye — an oddity I reproduced but did not explain.** Step 2
reads what `common.h` names *number of active team members*, and step 4 uses that
value as an **index** into the current team's 4-entry member-index array. If the
field really is a count, indexing by it reads one past the last active member.
Either the field's upstream name is imprecise, or the leader genuinely lives at
that slot. The bytes are exact; the meaning is not established, and I have not
renamed anything on the strength of a guess.

**Also note**: the three `number_active_team_members_*` fields are separate
scalars in `common.h`, not an array, so indexing them requires pointer arithmetic
from the first one. The struct layout guarantees contiguity, and this is what the
asm does, but it is worth seeing.

## Types

`GetAppointedLeaderMemberIdx` returns `u32`, consistent with the other
`*MemberIdx` functions (see `0f08744f` for why that type matters). Both
prototypes move out of `main_02064FFC.h` — where they lived while their callers
were being decompiled — into the new headers. `sub_02065050` and `sub_0206549C`
call them and were rebuilt to confirm the `int` → `u32` change is byte-neutral.

No new names: every type, field and both function labels pre-exist in the tree.

## How they were matched — a diagnostic worth reusing

Both scored a near-match on the **first** attempt (20 and 25), and **every
mnemonic already matched** — only immediates differed (`#0x877` vs `#0x423`,
`#0x9800` vs `#0x9300`, `#0x44` vs `#0x42`).

That pattern means **the C is right and the scratch's struct layout is wrong** —
not that the code needs restructuring. The giveaway was `mov r0, #0x44` vs
`#0x42`: my scratch's `ground_monster` was 0x42 bytes, which undersized
`members[555]` by 0x376 and shifted every field of the roster region after it.
Correcting that one field size in the *context* took both functions to **0**; the
C never changed. The real `common.h` struct has the correct size, so it landed
first try.

Generalised into `docs/MATCHING_TIPS.md`: if all mnemonics match and only
offsets/immediates differ, fix the context struct, don't refactor the C.
