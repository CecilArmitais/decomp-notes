## The largest part of this commit is declaration cleanup

**Fact.** Three of the five contradicted a declaration the tree already carried,
written from a call site by an earlier contributor. Each was checked against the
bytes and corrected, and the corrections touch **five** files that this sweep did
not otherwise decompile.

### `SubstitutePlaceholderStringTags`'s first parameter is not a pointer

**Fact.** The tree declared it four different times as
`u8 *string_id` — and once, in `src/move_orb_effects.c`, as `int a`. It already
disagreed with itself before this commit.

**Fact.** `DoMoveGuardSwap` passes the literal **`1`**:

```asm
	mov r0, #0
	bl SubstitutePlaceholderStringTags
	mov r1, r4
	mov r0, #1
	bl SubstitutePlaceholderStringTags
```

A `u8 *` parameter cannot receive `1` without a cast, and the existing call sites
all passed `0`, which is why nothing caught it: `0` is a valid null pointer
constant. The four `u8 *` declarations are changed to `s32 slot`, agreeing with
the `int` one that was already there.

**Inference.** The parameter looks like a string-buffer slot index (0 for the
user, 1 for the target). The name `slot` is a placeholder, not a claim.

### `TryIncreaseHp`'s hp parameter is 32-bit, not `s16`

**Fact.** Two files declared `s16 hp`. `DoMoveSwallow` loads its argument from a
**word** array with `ldr r2, [r2, r3, lsl #2]` and passes it through untouched.
With `s16` MWCC inserts a sign extension and the function scores **210**; with
`s32` it scores **0**.

**Inference.** The existing `s16` call sites — `HEAL_ORDER_HP_RESTORATION` and
`MORNING_SUN_HP_RESTORATION_TABLE[…]` — are themselves `s16` data loaded with
`ldrsh`, which leaves the value already sign-extended in the register, so
widening the *declaration* to `s32` should be byte-neutral for them. The build is
what settles that, and it was run.

### `ShouldTryEatItem`'s parameter is signed

**Fact.** The range check compiles to `blt`/`ble`, not `bcc`/`bls`:

```asm
	cmp r4, #0x45
	blt _0231E9A8
	cmp r4, #0x8a
	ble _0231E9B0
```

`enum item_id` under `-enum min` has no negative enumerators and so compares
unsigned — score **400**. Any signed type scores 0; `s16` was chosen because the
adjacent `IsItemValidVeneer(s16 item_id)` uses it and every caller produces the
argument with `ldrsh`.

## `DoMoveSwallow` — arm order again

**Fact.** The candidate with `if (stage == 0) { log } else { heal }` scored 530
with the branch sense inverted; the *same* two arms written
`if (stage != 0) { heal } else { log }` score 0.

This is the third instance in three sweeps (`sub_02009DCC` in
[`4d2a484c`](4d2a484c.md), and here) of the same rule: **MWCC lets the first arm
in the source fall through**, so which arm is written first is a source decision
the bytes record, independent of the condition.

## `sub_0205B738` — a member at `+0xB0` that was really element `[1]`

**This one was landed wrong first, and the build caught it.** The record is kept
because the failure mode is worth recognising.

**Fact.** The function reads a byte at `+0xB0` off `_020B0A54.struct0`, then
block-copies **176 bytes** over that same region. `struct unkStruct_020B0A54` in
`include/main_0205B690.h` visibly ends at `unkAE`, so the first reading was that
the struct stopped short: a new 176-byte member `unkB0` was appended and a
`struct unk_0205B738` invented for it. That scored **0** on a scratch.

**Fact.** The real build then failed with **29** mismatched checksums — `main`
and every overlay, including overlays this sweep does not touch. A whole-binary
shift, not a codegen difference.

**Fact.** 176 is `0xB0`, and `0xB0` is `sizeof(struct unkStruct_020B0A54)`. Two
already-decompiled neighbours say so outright:

```c
u8* sub_0205B77C(u32 a)
{
    return a * 176 + &_020B0A54.struct0->unk0;
}

void sub_0205B7C8(s32 index)
{
    MemsetSimple((u8*) &_020B0A54.struct0[index], 0, 0xB0);
```

So `struct0` is an **array** of 0xB0-byte records, `+0xB0` is element `[1]`, and
the 176-byte copy is one whole element. Growing the struct changed its `sizeof`,
which changed the stride in `sub_0205B77C`, `sub_0205B794` and `sub_0205B7C8` and
the copy length in `sub_0205B6EC` — hence the global shift.

**Fact.** The correct source needs no header change at all, and also scores 0:

```c
bool8 sub_0205B738(struct unkStruct_020B0A54* src)
{
    bool8 result = FALSE;

    if (_020B0A54.struct0[1].unk0 != 0) {
        result = TRUE;
    }

    _020B0A54.struct0[1] = *src;

    return result;
}
```

**The general point.** A load at `[base, #N]` is indistinguishable from element
`[1]` of an array whenever `N == sizeof(*base)` — the asm cannot tell them apart,
and *both* readings can score 0 on a scratch, because a scratch compiles one
function and never sees the other users of the type. Only the full build does.
**Before adding a member at an offset, check it against the struct's size**; if
they are equal, it is an array index.

**Fact.** This is the second time in two sweeps that a scratch score of 0 was
necessary and not sufficient — see the `u8` vs enum note on
[`8cfb04e1`](8cfb04e1.md), where the build's warning flags rejected what the
scratch accepted.

## Region-varying message ids

**Fact.** Three of the five log a message whose id differs between US and JP, and
the difference is not a constant offset:

| function | US | JP | delta |
|---|---|---|---|
| `DoMoveGuardSwap` | `0xF2E` | `0x2495` | +0x1567 |
| `DoMoveSwallow` | `0xEE4` | `0xC26` | −0x2BE |
| `DoMoveHelpingHand` | `0xEDA` | `0xC1C` | −0x2BE |

**Fact.** `src/move_orb_effects.c` defines `JPN_MSG_OFFSET` as `-0x2C0`, which
is close to the −0x2BE seen twice here but **not equal**, and `DoMoveGuardSwap`
does not follow either. That macro is therefore a local convenience for one
file's ids, not a general rule, and it is deliberately not reused.

**Fact.** Each id is spelled as a file-scope `#ifdef JAPAN` / `#define`, which is
the tree's existing pattern for exactly this (`CANNOT_USE_ITEM_MESSAGE` in
`src/dungeon_ai.c`, `CURVED_PROJECTILE_LOG_MESSAGE_1` in
`src/dungeon_projectile_throw.c`).
