## What changed

`fa6aa54e` declared `struct unk_020B0A48` for the records
`TEAM_MEMBER_TABLE_PTR` points at. That was **my error**: the tree already types
that global as `struct team_member_table` (`common.h`), whose `members[]`
elements are `struct ground_monster`. The placeholder reinvented an existing,
documented struct, and re-declared `TEAM_MEMBER_TABLE_PTR` a second time
alongside the extern two other decompiled files (`main_02058FA4.c`,
`main_02059060.c`) already use.

Replaced with the canonical types. `members[]` is at offset 0 and
`ground_monster` has the same 0x44 stride and 0x4 field as the placeholder, so
every read computes an identical address — confirmed byte-unchanged by the
build. `->field_0x4` became `->id`; the two table-indexed reads became
`->members[i].id`.

**Generalisable**: before inventing `struct unk_<addr>` for a global, grep the
tree for the symbol — an existing decompiled file may already have typed it. I
should have done that when I first declared the placeholder.

## Why the early SPECIAL_ACTORS fields are `monster_id`, not `script_entity_id`

A reviewer asked what makes us certain. As of this commit the answer is
**self-contained in decompiled code and already-merged structs**, with no
reliance on the `GetScriptEntityMonsterId` name (which is an upstream sync, not
our analysis).

The two field groups are consumed differently, and that is visible in C:

- **The four redirect slots (offsets 0x12–0x18)** are written by `sub_02065050`
  into the id it resolves, and that id then **indexes `ENTITIES[]`**. A value
  used to index the script-entity table is a `script_entity_id`. This leg is
  airtight.
- **The nine species slots (offsets 0x00–0x10)** are written to `*out` in
  `sub_0206549C` and **never** index anything. `*out` is filled from six
  independent sources, and **every one is a species** — this is the crux:

| `*out` source (all in `sub_0206549C`) | why it is a species | needs the upstream name? |
|---|---|---|
| `GetHero/Partner/MainCharacter1-3()->id`, `sub_02056914()->id` | `ground_monster.id`, `common.h` comment: **"0x4: Monster ID"** | no |
| `TEAM_MEMBER_TABLE_PTR->members[i].id` | same struct | no |
| `ARM9_UNKNOWN_TABLE__NA_20A68BC[i]` | initial data decodes (via the tree's `_MONSTER_ID_GENDERED` macro) as **ONIX, NIDOKING, PIDGEY, RATTATA, SANDSHREW, ZUBAT** | no |
| literals `0x5F`, `0x22` (debug path) | = **ONIX, NIDOKING** — the table's own first two entries | no |
| `LoadScriptVariableValue(0, 0x3e / 0x40 / 0x44)` | `VAR_HERO_FIRST_KIND` / `VAR_PARTNER_FIRST_KIND` / `VAR_RANDOM_REQUEST_NPC03_KIND` (KIND = species) | no |
| the nine `SPECIAL_ACTORS` slots | the fields under review | — |

A single-purpose function fills one output from six sources that are *each*,
independently, a monster id. The nine slots share that output, so they are the
same type.

**The hardest single datum** needs no naming at all: `RandomizeDemoActors`
writes slots 0x04 and 0x0a straight from `DEMO_TEAMS`, whose data decodes as 18
starter hero/partner pairs, including two `_SECONDARY` (gendered) forms that
exist only in `monster_id`.

### What is still inference

- **Seven of the nine slots are typed by analogy.** Only `demo_hero` /
  `demo_partner` have direct data proof (via `DEMO_TEAMS`). The other seven feed
  the same `*out` in the same switch with identical code shape — strong, but not
  a per-slot data decode.
- The `default` branch `*out = ENTITIES[id].field_0x2` is a fallback and its own
  meaning is unresolved; it does not weigh on the nine slots either way.

## Open questions
