## The finding: a re-read needs `struct item_volatile`

**Fact.** It reads `item->flags` through `struct item_volatile`. The target
**loads the flags byte twice**, once for each test, where a plain `struct item`
lets the compiler **reuse the first load**.

**`item.h` already carries `item_volatile` for exactly this purpose and says so**
-- so this is using an existing facility, not inventing one.

This is one half of a general diagnostic now in `docs/MATCHING_TIPS.md`: *a load
count that differs by one is a `volatile` question, not a logic one*. The other
half -- a discarded read that needs `volatile` to survive at all -- appears in
[`019b4543`](019b4543.md).

**Fact.** The cast is written **at each access**, following
`dungeon_ai_items.c` and `special_move_types.c` rather than casting the cursor
once -- **though both spellings score 0**, so this is convention, not necessity.

## Boolify one test but not the other

**Fact, and a precise contrast.** Only the **second** flag test is left as a bare
mask. The existence test goes through an explicit `bool8` because the target
boolifies it (`tst`, `movne`, `moveq`, `tst #0xff`), while the second test
branches straight off `tst`, which is what a bare mask in an `if` produces.

Two tests, two different spellings, in one function -- decided entirely by what
the target emits. This is the clearest example on the branch that the boolify
choice is observable rather than stylistic.
