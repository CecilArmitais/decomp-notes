**Fact.** All ten reach `struct dungeon` through `DUNGEON_PTR`; every offset
lands on a field `dungeon.h` already names — `id` at `0x748`,
`hidden_outlaw_defeated_message` at `0x2`, `unk_music_flag` at `0x792`,
`dungeon_music_playing_id` / `field_0x2cb00` at `0x2CB06` / `0x2CB00`,
`gen_info.fixed_room_id` at `0x40DA`, and
`fainted_monster_dungeon_end_reason` at `0x2CA66`. **No new types.**

**Nine of ten matched on the first candidate**, the second batch running against
the preprocessed `dungeon.h` context.

## The one that needed work

**Fact.** `IsDungeonEndReasonFailure` reads its union member through an explicit
`(s16)` cast. `enum damage_source_non_move` declares no negative enumerator, so
under `-enum min` it is **unsigned** — compiling to `ldrh` with `movcc`/`movcs`,
where the target has `ldrsh` with `movlt`/`movge`.

Reading `.move` instead of `.other` does **not** help (600 either way); only the
cast does.

**A deliberate choice worth reviewing.** The alternative fix is adding a `-1`
sentinel to `enum damage_source_non_move`, which is what this branch did for
`monster_id` in [`39a8db1b`](39a8db1b.md). It was not done here: **the cast is
local and reversible, a shared-enum change is neither**, and one function is thin
evidence for changing a tree-wide type. If a later function needs the same read,
that calculus changes.

## A landing trap, and the build catching it

**Fact.** Two of the ten merged into `src/run_dungeon_1.c` — a **pre-existing**
file, not an `overlay_29_*.c` one. The fill script's glob only covered
`src/overlay_29_*.c`, so both landed with **empty bodies**, which compiled (the
build passes `-W nomissingreturn`) and produced five failing checksums.

**The lesson is about the automation, not the compiler.** `extract_function.py`
merges into whatever source file is adjacent by address, which need not share the
naming pattern of the batch. A fill step keyed on a filename glob will silently
miss those. Checking for a remaining `{\n\n}` in *every* changed `.c` — not
just the expected ones — costs nothing and would have caught it before the build.

**Fact.** That file declares `DUNGEON_PTR` as an array and reaches it as
`DUNGEON_PTR[0]->`. Both functions follow the file's existing convention rather
than introducing a second spelling; **both forms were checked on a scratch and
produce identical bytes**, so this is style, not codegen.

## Open questions

  header calls that field "related to playing dungeon music" and nothing here
  narrows it.
- `unk_music_flag` is documented upstream as taking values 0–4 for specific
  tracks; `ov29_022EAEFC` returns whether it is zero, and `ov29_022EAF20` /
  `SetUnkMusicFlag` are its plain getter and setter. Their `ov29_` names are kept
  since identification was not the task.
