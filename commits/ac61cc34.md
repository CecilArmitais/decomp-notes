## Decompiled

`GetHeroMemberIdx`, `GetPartnerMemberIdx`, `GetMainCharacter1MemberIdx`,
`GetMainCharacter2MemberIdx`, `GetMainCharacter3MemberIdx`, into a new
`src/main_0205567C.c`.

**Fact.** Each returns the index of a `TEAM_MEMBER_TABLE_PTR->members` entry when
that entry's `is_valid` bit is set, or `-1` otherwise -- hero index 0, partner
index 1, and the `GetMainCharacter` functions choosing by game mode (2/3/4 in a
special episode, 0/1/none otherwise). They are the index-returning counterparts
of the pointer accessors in the previous commit.

## The finding worth keeping: `u32` defeats the negate idiom

**Fact, and the reason the return type is `u32` rather than `int`.**

With a **signed** return, the compiler recognises `valid ? 0 : -1` as the idiom
`-(!valid)` and emits an arithmetic negate. The target uses a **conditional-move
select**. Under `u32`, `-1` is `0xFFFFFFFF`, the negate idiom no longer applies,
and the compiler emits the select the target has.

**Fact about the scope of the evidence, and this is the honest part.** The
distinction is only observable for **hero**, whose index is the constant `0`. For
the others the index is non-zero or runtime, so *both* signednesses produce the
select. The whole family is typed `u32` for **consistency**, which is a
judgement, not a byte-level requirement.

**Inference a reviewer may want to overturn.** If upstream prefers `s32`/`int`
for an index that can be `-1`, four of these five can take it with no change in
output; only `GetHeroMemberIdx` genuinely requires `u32`.
