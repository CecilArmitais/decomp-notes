**This commit opens the menu cluster**, which runs for the next eight commits and
is the largest single family on the branch.

**Fact.** The four menu functions all resolve their window through
`GetWindowContents`, which `src/overlay_10_022BCC60.c` already declares as
returning `void *`.

**Fact.** What it returns has fields at `0x198`, `0x19C` and `0x1A0` and **no
existing type** (checked), so it is introduced as `struct unk_0202AAA8`, named
for the lowest-addressed function that uses it, with placeholder fields.

## A deliberate choice about where the struct lives

**Fact.** The struct and the `GetWindowContents` prototype live in
`include/main_0202AAA8.h` and are **included** by the second source rather than
repeated in it.

The reasoning is worth keeping: **two copies of a struct definition in two
translation units is the same drift risk as two prototypes**, and nothing in the
build would report them disagreeing. This branch hit that exact class of silent
disagreement more than once.

## Return widths are read off the target, and they differ

**Fact.** `IsEmptyString` and `CheckParentMenuField0x1A0` end in
`and r0, r0, #0xff`, so they return `bool8`. **`IsParentMenuActive` does not, so
it is word-sized despite reading like a predicate.**

That contrast in a single commit is the clearest possible demonstration that the
byte-width return diagnostic is real and must be applied per function -- not by
what the name suggests.

## Bind the state field to a local

**Fact.** `IsParentMenuActive` needed its state field bound to a local. Comparing
`menu->field_0x19C` against two values inline emits **two loads**; the target
loads it once.

Same family of finding as the `volatile` load-count diagnostic, in the opposite
direction: here the C must be made to load *less*.
