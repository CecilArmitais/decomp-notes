## Decompiled

| function | address |
|---|---|
| `DseTrackEvent_SetupVolumeLfo` | `0x020724A8` |
| `DseTrackEvent_SetupPanLfo` | `0x020726C4` |
| `DseTrackEvent_SetupLfo` | `0x02072770` |

**Fact.** Each reads five bytes and initialises one `lfo_settings` entry:
waveform index, a signed 16-bit amplitude, a phase-change time, and zeroes for
the envelope fields. The two fixed-slot handlers also set `type` and
`output_type`, using the same slot-to-`output_type` mapping as the `Use` handlers
(2 for volume, 3 for pan). `SetupLfo` is the indexed form and takes its slot from
`channel + 0x61`.

## A struct change, and why it is safe

**Fact.** `struct dse_lfo_settings` gains `field_0xE`. All four of these handlers
store a zero byte at that offset, which the struct previously described as
**trailing padding**.

**Fact.** The struct's size is unchanged: it already rounded to `0x10` for the
`s32` amplitude's alignment, and the `0x10` stride is confirmed by the
shift-by-4 the asm uses to index the array. Adding the field is therefore
byte-neutral to every existing user, **which the build confirms**.

This is a shared-type change and a reviewer should weigh it as one -- though it
is about as low-risk as such a change gets, since it converts padding into a
named field without moving anything.

## The finding: read all operands before the first store

**Fact.** All five stream bytes are read into locals before the first store.
Reading them inline instead **interleaves the loads between stores**; the target
issues all five `ldrb` up front.

## `DseTrackEvent_SetupKeyBendLfo` was deliberately NOT landed

This is the honest part of the commit and the note repeats it in full.

**Fact.** It is the same shape and reaches an **instruction-for-instruction
identical body** -- every mnemonic, offset and immediate matches -- differing
only in **which registers the allocator picks**, at score 65.

**Tried, and recorded:** reordering the locals; introducing an explicit amplitude
temporary; dropping the pointer local. Each moved the score without closing it.

**It was left in asm rather than landed as a near-match.** That is the correct
outcome: a near-match is not a match, and inline asm to force the bytes would not
be a decompilation.

**This is emphatically not a claim that the function cannot be matched.** Retail
was compiled from ordinary C by this toolchain, so a matching source exists by
construction. What is recorded here is **the limit of the attempts made**, and
the directions still untried -- register pressure is influenced by things not yet
varied here, such as the order of the trailing zero stores, the type of the
amplitude temporary, and whether the slot index is hoisted.

The saved scratch is `zAe84`.
