## Landing shape — a truncation, not a split

**Fact.** `main.lsf` puts `asm/overlay_11_02308D1C.o` immediately after
`src/overlay_11_02307334.o`, and all twelve sit at the *head* of that `.s`, so
`extract_function.py` **merges** each into the end of the existing `.c` and
truncates the `.s` from the front. No new object: `main.lsf` changes by exactly
one line, `asm/overlay_11_02308D1C.o` → `asm/overlay_11_023090DC.o`.

Countable consequences, all **fact**:

| | before | after |
|---|---|---|
| `arm_func_start` in the `.s` | 70 | 58 |
| `.public` in its `.inc` | 188 | 181 |
| `main.lsf` objects | unchanged | unchanged |

The seven dropped `.public`s are exactly the symbols nothing in the truncated
file still references: `CloseDialogueBox`, `CloseInventoryMenu`,
`CloseTextBox2`, `CreateDialogueBox`, `ov11_02322DB8`, `ov11_02324D8C`,

### One asm-side move a reviewer should look at directly

**Fact.** The `#ifdef JAPAN` block defining `OV11_02309084_OFFSET` used to sit

### `ov11_02308DD8` — the raw-byte flag test

**Fact.** `f = (*(u8 *)team_member & 2) != 0;` is not a stylistic choice. The
target has a bare `tst r0, #2`; reading the named bitfield `flags_unk1` emits an
`lsl`/`lsr`/`and` triple instead (measured: 600). This is the case
`docs/MATCHING_TIPS.md` already documents on `GetUnitNpcIds`, against this exact
struct and this exact instruction, and the spelling is copied verbatim from the
landed `src/main_02056D70.c:22`.

**Fact.** Both `bool8` locals are written `x = field != 0; if (x)` rather than
`if (field)`, because the target boolifies (`cmp`/`movne`/`moveq`) and then
re-tests the byte (`tst rN, #0xff`) — the `bool8` truncation MATCHING_TIPS
describes.

**Fact, from the data section.** The format string it passes,
`ov11_02322DB8`, decodes as `"[CS:%c]%s[CR]"` (14 bytes, next `.global` is
`ov11_02322DC8`), which is why it is declared `char[]` rather than the `u8[]`
its immediate neighbour `ov11_02322DB0` uses.

**Inference.** That the colours `0x44` / `0x46` / `0x59` (`'D'`, `'F'`, `'Y'`)
mean what the variable name `color` suggests. They are literals fed to a `%c`;
nothing in the tree names them.

### `ov11_02308F4C` — the `id` cast, and the header disagreement behind it

This is the one place in the commit where the landed C carries something that
looks like a wart, and a reviewer should know it is a symptom.

**Fact.** The target reads `team_member::id` with **`ldrsh`** — a *signed*
halfword load. `include/common.h:69` declares that field `u16 id;  // 0xC`.
A value cast `(s16)mem->id` does nothing (measured: still 200; the load width
and signedness follow the *declared field type*). The reinterpret
`*(s16 *)&mem->id` matches at 0.

That is why the two arms of the function are asymmetric in the landed source:

```c
dst->field_0x8 = mon->id;              /* ground_monster::id is already s16 */
dst->field_0x8 = *(s16 *)&mem->id;     /* team_member::id is declared u16   */
```

**Fact.** `struct ground_monster::id` at `0x4` is `s16` in the same header, and
pmdsky-debug types *both* fields identically (`struct monster_id_16`).

**Inference, and the reviewer's call.** The `u16` looks like a materialisation
slip rather than a real difference between the two structs. The wip measured it:
with `team_member::id` flipped to `s16`, the cast-free `dst->field_0x8 =
mem->id;` also scores 0. **It was deliberately not applied here** —
`team_member::id` is read from other translation units
(`src/overlay_29_02308FBC.c`, `src/overlay_29_023000E4.c`, …), so flipping it is
a shared-type change that needs its own commit and its own three-region build.
See *Shared-type changes* below.

**Also measured and not adopted:** spelling the 8-byte head copy as a nested
`struct unk_02309DAC field_0x0;` member instead of the cast
`*(struct unk_02309DAC *)dst = *src;`. It scores 0 too, and is probably closer to
what retail wrote (**inference**), but it would rename eight existing field
references inside the already-landed `ov11_02307334` for no byte change. Recorded
so the choice is visible rather than silently made.

**Fact.** The head copy is *one struct assignment*, not two field stores: the
target loads both words before storing either, then re-reads `[r4]` for the
following `cmp`.

### `ov11_0230901C` — the missing return

The landed body is, verbatim:

```c
s32 ov11_0230901C(struct unk_02308F4C *a)
{
    if (a->field_0x0 == 0) { return a->field_0x4 | 0x20000; }
    if (a->field_0x0 == 1) { return a->field_0x4 | 0x30000; }
}
```

**Fact.** There is no `return` on the third path, and mwccarm emitted **no
diagnostic at all** — so `-W error` in the real build has nothing to promote.
The target's own shape is two predicated `ldrsh`/`orr` pairs and a predicated
`bxeq`, with nothing written to `r0` when neither test holds.

**Fact (falsified).** A `switch` over the same two cases scores **765** (11 rows
against 9): MWCC emits a real join block and an unconditional branch. The
if-chain is what produces the predication.

**Not discriminated.** `if (…) … else if (…) …` also scores 0. The two
spellings are indistinguishable here.

### `ov11_02308EB4` — three spellings, all matching

**Fact.** The function makes exactly one tail call and never materialises a
return value, so its return type and its pointer element types are
codegen-invisible. Three spellings were measured on NORTH_AMERICA and all three
score 0:

- `void ov11_02308EB4(char *, const char *, ...)`  ← chosen
- `void ov11_02308EB4(u8 *, const u8 *, ...)`
- `s32 ov11_02308EB4(u8 *, const u8 *, ...)` with `return vsprintf(…);`

**Inference (weak, but tree-backed).** The `char *` form was chosen because the
tree already has this exact wrapper shape in
`src/item_util_1.c:55` (`SprintfStatic__0200E990`), calling the same
`extern s32 vsprintf(u8 *, const u8 *, va_list)` with `char *` arguments, and
that combination is proven under the real `-W error` build. If it ever does
object, the `u8 *` form is byte-identical.

### The two allocators, and the region split

`ov11_02309040` and `ov11_02309084` are the same function with different
payloads: `MemAlloc`, null-check, two or three stores, return 0/1.

**Fact.** Neither returns `bool8`: `moveq r0,#0` / `movne r0,#1` with **no**
trailing `and r0, r0, #0xff`. Both keep the `int` the pre-existing call-site
declarations already gave them.

**Fact.** The allocation size is region-varying — `0x794` US/EU, `0x774` JP —
and the field displacements move by exactly the same `0x20` (`0x114`→`0xF4`,
`0x118`→`0xF8`). Two independent facts that agree, which is what says the
literal is `sizeof(struct unk_02324D90)` and the `#ifdef JAPAN` belongs in the
struct's padding rather than in either function body. Writing it that way means
**neither landed body contains any preprocessor**.

**Fact.** JP `ov11_02309084` is 19 instructions against the US/EU 20: it loses
an `add r1, r1, #0x100` because the JP displacement `0xF8` fits an ARM 8-bit
immediate where `0x118` does not.

**Fact, and worth recording because the shape looks deliberate and is not.**
The first store goes through the cached `MemAlloc` result while the next two
reload the global. Writing all the stores through the global reproduces that
asymmetry on its own — MWCC forwards the just-stored value to the first use and
reloads for the rest. No local-variable spelling was needed.

**How JAPAN was actually measured.** `ov11_02309040`'s labels are US names
carrying US addresses, and JP emits the same instruction count, so a JP walk
from the US base would "pass" while proving nothing. The harness instead
resolves the whole `.s` for JAPAN from its JP base `0x0230A2C8` and asserts the
file's one JP-only label `_0230CC20_JP` lands on `0x0230CC20` — an anchor ~2800
lines downstream, so every JAPAN-resolved instruction before it has to be
counted right. The negative control that matters: **JP target measured against a
NORTH_AMERICA context scores 10, not 0**, which is what says the JP score 0 is a
real JP measurement and not the US one wearing a JP label.

## Shared-type changes — read this section

Four type-level items. Three are changes made here; the fourth is a change
deliberately *not* made.

### 1. `struct unk_02324D8C` — a field split, size preserved

File-local to `src/overlay_11_02307334.c`; **fact**, it appears in no other file.

```
was:  u8 field_0x104[0x134];
now:  u8 field_0x104[0x32];
      char field_0x136[0x102];
```

**Fact.** `0x104 + 0x32 = 0x136` and `0x136 + 0x102 = 0x238`, which is where
`field_0x238` already started. Same size, same layout, same offset for every
member after it — and the three-region build confirms it rather than the
arithmetic alone.

**Fact.** The offset `0x136` is read off `ov11_02308DD8`, which materialises
`ov11_02324D8C + 0x136` three times (`add r0,r0,#0x36` then `add r0,r0,#0x100`
— `0x136` is not an ARM rotated immediate, hence the pair) and hands it to two
string writers and to its own return.

**Not a fact: the size `0x102`.** Only the *offset* is observable. `0x102` is
simply the rest of the padding run, chosen so the struct's total size is
unchanged. The buffer's real length is unknown.

**Inference:** `char` rather than `u8`, because the pointer reaches the caller as
`ov11_02324D8C->field_0xb4.strings[0]`, which `struct preprocessor_args` types
`char *`.

### 2. `struct unk_02324D90` — new, region-split

New file-local type for the previously untyped global `ov11_02324D90`
(**fact**: before this commit the symbol appears only in `asm/`, nowhere in
`src/` or `include/`). Three fields are facts, read off the two allocators:
`sizeof` `0x794`/`0x774`, a 4-byte field at `0x114`/`0xF4`, a 2-byte field at
`0x118`/`0xF8`, and a 4-byte field at `0x0`.

**Inference, flagged:** *where* the `0x20` that JP lacks actually sits is not
determined by these two functions. It is modelled as leading pad
(`field_0x4[0x110]` vs `[0xF0]`); any placement before `0xF4` gives identical
code. **Field names carry their US offsets in every region** — `field_0x114`
sits at `0xF4` under JAPAN — following the existing precedent in
`include/dungeon.h:1215`, where an `#ifndef JAPAN` drops two members and
everything after keeps its US name.

**This struct is a floor, not a total.** The very next function in the file,
`ov11_023090DC`, reads far more of it. Expect it to grow, and expect the
`0x20`'s modelled position to be revisited when something pins it.

### 3. `struct unk_02309DAC` and `struct unk_02308F4C` moved into a header

Both moved **verbatim** from `src/overlay_11_02307334.c` into
`include/overlay_11_02307334.h` (which now `#include`s `common.h`), because the
new prototypes mention them. No member changed.

**Fact.** At this commit `include/overlay_11_02307334.h` is included by exactly
one file — `src/overlay_11_02307334.c` — so the move has no fanout today. It
does mean these two placeholder types are now *publishable* to any future
includer, which is the usual argument for getting their names right before they
spread.

### 4. `include/common.h`'s `team_member::id` — **not** changed, and arguably should be

Restating the item from `ov11_02308F4C` above because it is the one genuinely
cross-cutting thing here: **a widely-included header declares a field `u16` that
this function's asm reads with `ldrsh`.** The workaround shipped in this commit
is a per-site reinterpret cast. Flipping `common.h` to `s16` was measured at
score 0 for *this* function and left alone because other translation units read
the field. A reviewer who wants the cast gone should ask for that flip as its own
commit with its own three-region build.

### Disagreements a reviewer should weigh

**`sub_02055894` — a live disagreement, knowingly left in place.**
`src/main_0205B008.c:6` declares `extern s32 sub_02055894(u32 b);`. This commit
adds `extern s32 sub_02055894(struct ground_monster *member);`. **Fact**, from
`asm/main_02055894.s`: the function walks `TEAM_MEMBER_TABLE_PTR->members` with
a stride of `0x44` = `sizeof(struct ground_monster)` and compares each entry's
*address* against `r0`, returning the index or `-1`. So the pointer spelling is
the one consistent with the asm and with this call site (which passes
`GetTeamMember`'s return value directly). The `u32` spelling was left alone
because it is in a different translation unit and fixing it is a separate
byte-neutral tidy-up.

**No build will ever catch this.** Two declarations in two translation units
never meet. It is exactly the class of thing CLAUDE.md's *"grep the tree for a
pre-existing extern"* rule exists for, and it is recorded here rather than
resolved.

**`sub_020564B0` — a duplicate where a header exists.** `include/main_020564B0.h`
declares `bool8 sub_020564B0(int idx);`, and the header is trivial (it pulls only
`util.h`). This commit nonetheless writes `extern bool8 sub_020564B0(int idx);`
into the `.c` rather than including the header — even though the wip's own
landing notes had said to add the `#include`. The text agrees exactly, so nothing
is wrong; but **why the include was not used is not recorded, and I did not
verify that adding it is harmless.** Worth a reviewer asking.

**`CreateDialogueBox` and `CloseDialogueBox` — neither has a header, and the tree
contradicts itself.** Before this commit: `CreateDialogueBox` appears as
`u32 (u32)` twice and `s8 (s8)` once; `CloseDialogueBox` as `void (s8)` three
times and `void (int)` once. This commit adds one more of the `s8` spelling of
each.

- For `CreateDialogueBox` the choice is **argued, not measured**: both spellings
  score 0 here, but the result is stored with `strb` into an `s8` field, so the
  `u32` spelling makes that assignment a narrowing conversion the scratch (no
  `-W` flags) cannot see and the real `-W error` build might.
- For `CloseDialogueBox` the choice is **a majority vote, not a measurement** —
  the argument arrives already sign-extended either way, so `int` is not
  contradicted by these bytes.

Both want one canonical header eventually. Adding a fifth and sixth call-site
declaration makes that slightly worse, and it is flagged rather than pretended
otherwise.

**`CloseTextBox2`** likewise has no header; the `s8` spelling used here comes
from the already-landed caller, and `src/overlay_31_02383880.c:16` carries the
empty-parameter `CloseTextBox2()`.

## Open questions

- **`team_member::id` should probably be `s16` in `include/common.h`** (see
  above). Until someone makes that change, `ov11_02308F4C` carries a reinterpret
  cast that exists only to work around the header.
- **`sub_02055894` is declared two contradictory ways in the tree** and this
  commit adds the second. Nothing but a grep will ever find it.
- **`sub_020564B0` is declared inline despite having a header.** Unexplained.
- **The size of `unk_02324D8C::field_0x136`** (`0x102`) is padding-fill, not
  evidence. Only the offset is known.
- **The size of `ov11_02308DD8`'s stack buffer.** `sub sp, sp, #0xc` fixes the
  frame at 12 bytes; `u8 name[12]`, `u8 name[11]` and `u8 name[10]` plus
  alignment can all produce it. 12 is what was measured; the others were not
  tried, because the frame size is all the target exposes.
- **Where the JP `0x20` really sits inside `struct unk_02324D90`** is not
  determined by the two functions that touch it here.
- **`ov11_0230901C` falls off the end of a non-`void` function** on its third
  path. That is what the target does; whether retail's source wrote it that way
  or had a `default` the compiler folded away is not determined.
- **Whether `ov11_02308EB4`'s parameters are `char *` or `u8 *`** is not
  determined by the bytes; three spellings all match.
- **Whether `ov11_02308DD8`'s `field_0x0 == 1` is the last case**, or whether the
  original was a `switch` with a `default` falling through to the same tail, is
  not determined.
- **All twelve keep their `sub_`/`ov11_`-style names, and every new struct and
  field is a placeholder.** This was decompilation, not identification. The
  cluster's behaviour reads as team-member summary/portrait plumbing hanging off
  the bag menu — `GetTeamMember` / `GetActiveTeamMember`, a recoloured name
  string, a dialogue box open/close pair — which is **inference** offered for a
  future naming pass, not applied here.
