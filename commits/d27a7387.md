28 functions land and **21 whole `.s` files clear**. Three things in it are worth
a reviewer's attention, and one of them is a mistake this branch made and had to
undo.

## 1. A function that had to get its own translation unit — and why the first attempt did not

`sub_02048C5C` was first merged into `src/main_02048BB4.c`, the adjacent landed
file. **Fact**: it then compiled to 27 words where the target is 23. The cause is
the documented one — `ReadStringSave` is *defined* 25 lines above it in that same
file, and at `-O4,s` MWCC folds a small visible callee into its caller. Re-landing
it with `extract_function.py -nm`, into `src/main_02048C5C.c` of its own, gives
92 bytes and 5 relocations, exact.

**This is the defect that a decomp.me score cannot see**, because a scratch
declares every callee `extern` and no body is ever visible. It is only findable
by comparing the emitted object against the original `.s`, which is what
`build-tools/landcheck.sh` now does.

*(Superseded on the 2026-09-18 rebase: upstream decompiled `sub_02048C5C`
independently and that version is what is landed. See §3.)*

## 2. Five shared types corrected from the asm rather than guessed

Each of these is a **fact** read off a load or store width, not a preference:

- `dungeon.h`: four `u8 field_0x2cb0c..f` become one `u32 field_0x2cb0c`. Retail
  emits `ldr`/`str` there; as four bytes the file still compiles and still
  *matches nothing*, because the accesses come out `ldrb`/`strb`.
- `window.h`: `struct unk_022A7A6C` extended past `0xC`, and `WindowBlock::unk24`
  `u32` → `void *`.
- `main_02029A50.h`: `unkStruct_02029A50` gains `u8 unk26` after `short unk24`.
- `dg_random.h` includes `dungeon_mode.h`, which declares
  `CalcStatusDuration(struct entity *…)`.
- `struct unk_022E9298` moved verbatim from `src/overlay_29_0231EDD8.c` into
  `dungeon_range.h`.

**26 stale call-site externs across 20 files** were replaced with includes.
Several were actively wrong, and a build can never catch that — two declarations
in two translation units never meet. `sub_0205B39C` was declared
`void (void *, void *)` where it is `u8 *(const s8 *, s32)`, and three files
declared `CalcStatusDuration` with `s32 *` where it takes `const s16 *`.

## 3. A two-symbol bss alias — correct, and superseded

**Fact**: MWCC keys literal-pool entries on `(symbol, addend)` and de-duplicates,
so two identical `.word _022AAE74` entries in the target require two distinct C
symbols. This commit added a zero-length `.global _022AAE74_2` at the same
address in `asm/main_bss_020B3380.s`; no `.space` changes, so the layout and the
ROM are untouched.

**On the 2026-09-18 rebase onto `a3d64122` this was dropped**, because upstream
had decompiled the same function and obtained the second pool key a lighter way:
`(u8 *)(&_022AAE78 - 4)`, a **negative addend on the next symbol**, which needs
no change to the assembly at all. Both forms match. Upstream's is strictly
preferable, and the alias and our version of the file went with it.

**Inference, and the reviewer-facing point**: adding a `.global` to a data file
should be the last option, not the first. The order worth trying is (1) a
different addend on a symbol already in the pool, (2) a neighbouring symbol with
a negative addend, (3) a new symbol — and only (3) when the two objects have
different sizes, as `TEAM_NAME` / `_022AB918` genuinely do in `c482e2df`.
