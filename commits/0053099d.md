## What the function does

**Fact** (read off the asm): it calls `ApplyDamage`, then — if the hit landed
and both entities are still valid monsters standing adjacent — runs three
further stages, re-checking validity between each: a Bide counter-boost; a
counter-damage stage (Reflect-class statuses, two exclusive items, two IQ
skills, Rough Skin) that builds a scaled damage block and applies it back to the
attacker; a contact-ability/exclusive-item stage that sets trigger bitflags on
the attacker; and finally a leech-seed/Destiny-Bond hand-off.

**Inference**: that reading of the flow is mine. The bytes name none of it.

## The match

Progression: 3965 (first draft) → 2490 → 1490 → 1095 → 520 → 350 → 325 → 290 →
95 → **0**. Local scratch `fmZYU`.

Five levers did the work, all written up with worked examples in
`docs/MATCHING_TIPS.md`:

1. **Control flow read off the branch targets.** The function has **two exit
   labels** — `0x02308F68` (bare epilogue) and `0x02308F64` (through a shared
   compare). **Fact**: the five entry gates branch to the former and return
   their raw tested value; the two `FALSE` gates and the three section joins
   branch to the latter, assigning `result` first. So the gates are early
   returns and the joins are inverted control flow, which is what the source
   shape had to reproduce. Four spellings (early-return gates, fully nested
   single-exit, flat `goto`, every-return-via-`result`) are **byte-identical**;
   the committed one is the early-return form.
2. **`s32` loop counter with an `(s16)` cast on the increment.** An `s16`
   counter produces the target's `lsl`/`asr` sign-extension but transposes two
   registers; `s32` fixes the registers and loses the extension; `s32` with
   `k = (s16)(k + 1)` gets both. Worth 7 register rows.
3. **A type-differentiated return pair** for the dead `cmp r0, #0` before the
   epilogue — see below.
4. **Block-scoped section-3 locals**, whose *in-block* declaration order selects
   the register colouring — see below.
5. **Two CSE-defeating spellings**: `(s16)a6` at the counter-attack loop call
   forces the per-arm reload retail has, and `*(u8 *)effect` as the effect-loop
   condition forces the body's reload.

## The tree change, and the evidence for it

### `ApplyDamage`'s 6th parameter: `enum damage_source_non_move` → `s16`

**Fact.** The caller loads it `ldrsh` and passes it in a register via `stmib`.
**Fact.** `enum damage_source_non_move` is all-positive (563…), so `-enum min`
makes it *unsigned* 2-byte, and passing an `s16` to it emits `ldrh` — measured
across eight candidate types for the caller's parameter, none of which produces
`ldrsh` against an unsigned 2-byte destination.

**Fact.** `s16` scores 0 on `ApplyDamage` *and* on this function; `u16` and the
enum also score 0 on `ApplyDamage` alone, so that function's own bytes cannot
distinguish them — only the call site can. **Fact.** Word types (`s32`/`int`)
score 60 on `ApplyDamage` (its prologue load of the parameter sinks eleven
slots), so the parameter is genuinely 2-byte.

**This modifies an already-landed matched function.** All three ROMs still
match, which is the evidence that it did not disturb `ApplyDamage`.

**Inference, and the open question**: the *representation* is settled (signed,
2 bytes); the *spelling* is not. A signed 2-byte enum would serve equally — I
tested a synthesised one and MWCC treats it identically to `s16`. If upstream
would rather keep an enum here, the honest fix is to give
`damage_source_non_move` a negative enumerator, not to revert to `s16`. The
tree's own `AftermathCheck`/`HandleFaint` already take `s32 damage_source`, so
the family is not consistent today either.

## The dead `cmp r0, #0`

**Fact.** The target ends with a compare no instruction consumes, falling
straight into the epilogue. Roughly forty constructs either materialise an arm
(one instruction too many) or let MWCC fold the arms and delete the test with
it (one too few). What produces exactly the target:

```c
    if (result) {
        return result;
    }
    return (u32)result;
```

**Fact.** Both arms return `r0` unchanged so neither emits anything, while the
cast keeps them syntactically distinct so the `if` survives to codegen and the
compare is emitted. Every *value*-level identical spelling of the second arm
(`+ 0`, `| 0`, `^ 0`, `<< 0`, `* 1`, comma, `-(-x)`) is constant-folded, the arms
become identical, and the whole `if` is deleted.

**Inference**: this is not claimed as retail's spelling. It is a stand-in for a
construct not yet found, in the same category as `ff65ac0e`'s `volatile` line.

## The register colouring

**Fact.** A two-column liveness table over all eight callee-saved registers
showed the two builds **identical everywhere** except one transposition:
`not_physical` and `amon` swapped homes. Same defs, same last uses, same
interference — so nothing upstream needed fixing and it was purely the
allocator's tie-break.

**Fact.** Function-scope declaration order cannot reach it: `not_physical` is
pinned to `r6` across every permutation of every local (~150 compiles, including
a 2-D sweep of both variables together). **Fact.** Declaring section 3's locals
in their **own block** does reach it, and the *in-block* order is the selector —
five orders produced five distinct register assignments, of which

```c
{
    s32 np3 = CategoryIsNotPhysical(damage_data->field_0xd);
    struct unk_023535DC *eff3;
    struct monster *amon3 = attacker->info;
    ...
}
```

is retail's. **Inference**: block-scoped section locals are plausible retail
style here — the leech-seed block already required one (`struct entity *bonded`)
— but the *order* within the block is a colouring device, not evidence.

## What the enumerators corroborate

Converting the raw constants to the tree's existing enumerators was required by
`-W error`, and every one landed somewhere that makes sense — which is
independent support for the decompilation being semantically right, not just
byte-right:

- `ABILITY_MAGNET_PULL` guards `MonsterIsType(attacker, TYPE_STEEL)` and uses
  `MAGNET_PULL_ACTIVATION_CHANCE`;
- `ABILITY_CUTE_CHARM` guards `GendersNotEqualNotGenderless` and uses
  `CUTE_CHARM_INFATUATE_CHANCE`;
- `EXCLUSIVE_EFF_COUNTER_PHYSICAL_DAMAGE` adds 4 to the multiplier where
  `EXCLUSIVE_EFF_COUNTER_25_PCT_PHYSICAL_DAMAGE` adds 1, against a
  `damage * mult / 4` formula;
- `EXCLUSIVE_EFF_MAY_POISON_PARALYZE_SLEEP_ATTACKERS` is exactly the
  `DungeonRandInt(300)` three-way split;
- the leech-seed field's `== 2` is `STATUS_LEECH_SEED_DESTINY_BOND`, and that
  branch damages the *bonded* monster.

**Note**: this is corroboration, not proof — the values were read off the asm
first and the names looked up afterwards.

## One logic error the branch targets caught

**Fact.** The Arena Trap grounding test was drafted as
`magnet_rise == 1 || (!HasTypeAffectedByGravity(...) && LevitateIsActive(...))`.
The target branches *into* the block when `HasTypeAffectedByGravity` is
non-zero, so it is three OR'd terms:

```c
if (amon3->magnet_rise == 1
    || HasTypeAffectedByGravity(attacker, TYPE_FLYING)
    || LevitateIsActive(attacker))
```

This was found by reading a single branch-offset row that had been written off
as length noise. It is a *behavioural* difference that a register-only reading
of the diff would have missed.

## Open questions for a reviewer

- **The `(u32)result` return**, above — the one construct here I would not
  defend as recovered source.
- **`(s16)a6` and `*(u8 *)effect`** — both CSE-defeating devices. `(s16)a6` on
  an `s16` variable is a semantic no-op that only works because MWCC treats the
  cast as a distinct value; the else-arm needs no cast (verified identical
  without), so it appears once.
- **The in-block declaration order** of section 3's locals is load-bearing.
- **`s16` vs a signed 2-byte enum** for `ApplyDamage`'s damage source, above.
- **`struct unk_023535DC`'s members.** Offsets `0x0` (u8 effect id), `0x4` (s32
  argument) and `0x8` (handler taking attacker, defender and a word) are read
  off the asm; the 16-byte stride is read off `add r5, r5, #0x10`. The padding
  bytes are never touched, and nothing says whether they are one field or four.
  The handler's third parameter is **word-sized**: `bool8` there emits a mask,
  and **the target contains no masking instruction anywhere** in 617
  instructions.
- **Parameters `a4`, `a5`, `a7`, `a8`** are unnamed on purpose. `a7` gates the
  entire post-damage effect chain; `a5`/`a8` are forwarded unchanged to the
  counter-attack `ApplyDamage` calls. Those are inferences from call sites.
- **Signature findings worth carrying to pmdsky-debug**: this function takes
  **8** parameters and returns a **word** (its gates return `attacker->type` and
  `a7` raw, untruncated — `bool8` would emit masks the target lacks);
  `ApplyDamage`'s damage source is signed 2-byte.
