## Two that needed a second reading

Three matched first try. These two did not, and both are worth recording because
the first candidate was *semantically correct* and still wrong.

**`DoMoveGust` — `add #0xF9`, not `sub #7`.** The move doubles its damage
multiplier when the defender's `bide_class_status.bide` is 7 or 8. Written as
`(u8)(bide - 7) <= 1` the compiler emits `sub ip, ip, #7`; the target has
`add ip, ip, #0xF9`. The two are the same value modulo 256 and behave
identically, but they are different encodings, so the source must have added
`0xF9`. One row, and no amount of restructuring the comparison would have found
it — only reading the immediate.

**`GenerateDungeonRngSeed` — operand order decides the schedule.** The function
runs the LCG (`*0x5D588B65 + 1`) twice, writes the second result back to
`prng_state::preseed`, and returns the halves recombined. Written
`(b & 0xFFFF0000) | (u16)(a >> 16)` the mask is scheduled before the shift;
written `(u16)(a >> 16) | (b & 0xFFFF0000)` it is not, and that matches. One
row, and purely the order the two operands appear in the source.

**Inference.** The reconstructed expression is
`(((u16)(a >> 16) | (b & 0xFFFF0000)) & 0xFFFFFF) | 1` — bit 0 forced on and the
top byte cleared, which is the same 23-bit shape `SetDungeonRngPreseed23Bit`
produces in [`25d5994b`](25d5994b.md). Whether the original was written this way
or with helper macros is not established; only the emitted arithmetic is.
