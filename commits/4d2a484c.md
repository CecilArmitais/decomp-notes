## `DoMoveWakeUpSlap` — a five-argument callee read from the call site

**Fact.** The move doubles its damage multiplier (`0x200` rather than `0x100`)
when the target is in any of the three sleep-class states, then ends the status.

**Fact, and the only real obstacle here.** The first candidate called
`EndSleepClassStatus` with four arguments and scored 135. The target sets `r2=0`,
`r3=1` **and** pushes a third flag on the stack — five arguments, not four. With
the fifth added it scored 0.

**Inference.** The three states are `STATUS_SLEEP`, `STATUS_NIGHTMARE` and
`STATUS_NAPPING`, read off the compare chain against
`GetEntInfo(defender)->sleep_class_status.sleep`. The names come from the
existing `enum status_sleep_id`; nothing new was named.

**Fact.** `EndSleepClassStatus` had **no** existing declaration anywhere in
`src/` or `include/` — grepped before landing, per the stale-declaration rule.
The five-argument prototype added here is therefore the tree's first, and it is a
guess about the *types* (all three flags spelled `bool8`) even though the *count*
is read from the bytes. A reviewer should push back on the types.

## `sub_020018A4` — a 64-bit round-up, not two 32-bit halves

**Fact.** The function opens with

```asm
	and r2, r1, #0
	and r3, r0, #0xff
	cmp r2, #0
	cmpeq r3, #0
```

**Inference, and the point of the entry.** `and r2, r1, #0` looks like dead code
— it can only produce zero. It is not: it is the **high half** of a 64-bit
`x & 0xFF`, with the low half in `r3`, and the `cmp`/`cmpeq` pair is the 64-bit
`!= 0` test. Reading it as a separate 32-bit test is what makes the function look
strange. The whole body is then:

```c
u32 sub_020018A4(u64 x)
{
    if ((x & 0xFF) != 0) {
        x += 0x100;
    }

    return x >> 8;
}
```

**Fact.** `s64` with a signed shift also scores 0 — the two are indistinguishable
here. `u64` was chosen because the target's shift is `lsr`; a wider value would
have separated them, and this one does not, so the signedness is **not**
established by the bytes.

**Fact.** Returning `u64` scores 200, so the return really is narrowed to 32 bits
in the source rather than being a 64-bit value the caller truncates.

## `sub_02009DCC` — branch order, not branch condition

**Fact.** Five byte arrays at `_022A37AC`…`_022A37B0`, each indexed by
`engine * 5`, each clearing one bit of a 5-bit mask when non-zero. The mask is
then merged into the display control register for the requested engine —
`0x04000000` for engine 0, `0x04001000` otherwise.

**Inference.** Five symbols sharing one index expression `i * 5` is five
*columns* of one 5-byte-stride table; the source may well have spelled it as one
array of structs. Left as five `extern u8 []`s because that is what the symbols
are, and inventing the struct would assert a layout nothing here checks.

**Fact.** The first candidate scored 1400 with every conditional suffix inverted
(`moveq` where the target has `ldrne`, and so on). Writing the *same* two arms in
the opposite source order —

```c
if (engine == 0) {
    /* 0x04000000 */
} else {
    /* 0x04001000 */
}
```

— scores 0. An early-return spelling of the same order also scores 0. So MWCC
predicates the first arm as written and the choice is purely which arm the
source puts first; the condition itself was never wrong.

**Fact.** `0x04001000` is not an ARM-encodable immediate and `0x04000000` is,
which is why the target loads one from the literal pool and materialises the
other with `mov` — the same encodability effect recorded on the region work, and
here it is what made the inversion visible at a glance.

## `sub_0200C4CC` — the member type sets the copy's shape

**Fact.** The body is one block copy: fourteen iterations of
`ldmia/stmia {r0,r1,r2,r3}` plus a trailing two-register pair = 232 bytes.

**Fact.** 232 is confirmed independently by the gap between `_02094C18` and the
next `.global`, `_02094D00`, in `asm/main_rodata_020925A0.s`
(`0x02094D00 - 0x02094C18 = 0xE8`).

**Fact, and the finding worth carrying forward.** The struct's *member type*, not
its size, decides the instruction shape:

| member | score |
|---|---|
| `u8 field_0x0[0xE8]` | 1225 |
| `u32 field_0x0[0x3A]` | **0** |

**Inference.** A `u8` array only guarantees byte alignment, so MWCC cannot use
the register-block form; the word array is 4-aligned and gets it. Written up in
`docs/MATCHING_TIPS.md` as *A whole-struct copy: the member type sets the
copy's shape*.

**Fact.** `const` on the source global is **not** what closes this. Tested
separately after the first write-up asserted otherwise: with the `u32` member,
`const` and non-`const` both score 0; with the `u8` member both score 1225. The
landed code still uses `const`, because the symbol genuinely lives in rodata —
not because it was needed.

**Fact.** `_02094C18`'s data carries an `#ifdef JAPAN`, but the *function* does
not, and the byte count is the same in both branches, so the `u32[0x3A]` member
holds for every region and US alone verifies it.

## Field types forced by access widths

**Fact.** Three edits in `include/main_02042AF8.h`, each forced by the width of a
load or store in `FreeUnkStorageStruct0x18c0` — none of them a naming or meaning
claim:

| struct | before | after | forced by |
|---|---|---|---|
| `unk_02043148` | `u8 field_0x0[4]` | `s32 field_0x0` | word compare against 6 |
| `unk_02043148` | `u8 field_0x7D5[0x13B]` | `s8 field_0x7D5`, `s8 field_0x7D6`, `u8 field_0x7D7[0x139]` | two separate `ldrsb`s |
| `unk_020AFEE0` | `u8 field_0xC[4]` | `s32 field_0xC` | `str r2, [r1, #0xc]` |

**Fact.** The third was the sole remaining differing row at score 5 — the
candidate wrote `field_0x10` because that was the nearest word-typed field.
Retyping `field_0xC` moved it to 0.

**Inference.** `field_0x7D6` is compared against `-2` rather than `-1`, which is
why it is `s8` and not `u8`. What a `-2` sentinel means here is not established.

## Open questions for a reviewer

1. **`EndSleepClassStatus`'s parameter types.** The count (five) is read from the
   bytes; `bool8, bool8, bool8` is a guess. This is the tree's first declaration
   of the function, so nothing contradicts it and nothing confirms it.
2. **`sub_020018A4`'s signedness.** `u64`/`s64` are indistinguishable at this
   size. A caller would settle it; the callers were not read.
3. **The five `_022A37A*` arrays.** Almost certainly columns of one 5-byte-stride
   table. Whether to introduce that struct is a naming decision, deliberately not
   taken here.
4. **`unk_02043148.field_0x7D6 == -2`.** A second sentinel distinct from `-1`
   suggests these two `s8`s are handles of different kinds, but that is
   speculation.
