## Decompiled

| function | address |
|---|---|
| `OverlayIsLoaded` | `0x02003ED0` |

**The branch's most involved commit.** The function matched early; the work was
making its *data* placeable.

**Fact.** A jump table over overlay group ids `0`-`0x24`. Group 0 is always
loaded; other ranges check one of the three `LOADED_OVERLAY_GROUP_0` slots, gated
on the parent slot holding the expected group. Out-of-range ids fail an assert
through `Debug_FatalError` with a `prog_pos_info` record.

**Fact.** The record decodes as `overlay.c` line 177 -- i.e. `__FILE__` /
`__LINE__` of the original assert.

## The finding: `extern` vs in-TU changes codegen

**Fact, established twice (scratch and ROM).** The function copies
`_02092558[2]` to the stack to pass its address. The copy's two loads:

- with `extern struct prog_pos_info _02092558[];` -> emitted **low-offset-first**,
  two instructions transposed against retail, and **immovable through ~30 code
  rewrites**;
- with the array **defined in the same TU** (initializers visible) -> emitted
  **high-offset-first**, matching exactly. Scratch score 20 -> 0 on that change
  alone, with **no change to the code**.

**Inference, well supported.** Retail's `overlay.c` necessarily defined this
array in-file -- it is that file's assert machinery -- which is why retail has
the other order.

So the five-record array moves into the C file as a `const` definition, with the
values decoded from the data: five entries sharing the `overlay.c` filename with
lines 887, 534, 177, 269 and 626.

## Why the neighbouring strings could *not* move -- three compiler facts

1. **Anonymous string literals go to writable `.data`**, not `.rodata` --
   verified with `readelf` on the object; the link placed them in the far data
   region (an 84,324-byte ROM diff).
2. **`-str readonly` does not exist** in mwccarm 2.0/sp2p2 -- the option accepts
   only `[no]reuse` and `[no]pool`, neither of which moves literals.
3. **A named `const u8 x[]` string *does* land in `.rodata`** -- but is emitted
   **before** the array regardless of definition order (both orders built and
   ROM-diffed: identical 53-byte result, string first).

So the two strings stay as assembly in a new `asm/main_rodata_02092580.s`, and
the C references them `extern` -- which is also the established convention
elsewhere in the tree.

## The three-way rodata split, and its traps

`asm/main_rodata_020908D4.s` now ends before `_02092558`; the C owns the array;
`asm/main_rodata_02092580.s` owns the strings; `asm/main_rodata_020925A0.s` owns
the rest. `main.lsf` orders them C -> strings -> rest, so rodata lands at retail
addresses (the linker groups sections by type in object order).

Two traps, both now in `docs/INSERTING_AND_BUILDING.md`:

- **The rodata `.inc` is a shared header.** Regenerating it per-file broke a file
  that was never touched. Leave it alone; new split files include it too.
- **The second part's `Object` line goes after the C object**, not after the
  first part -- rodata order follows lsf object order.

## The diagnostic that made this tractable

"Checksum FAILED" says nothing. Building **clean HEAD and the change in one
container and `cmp -l`-ing the two `main.sbin`s** turns it into exact byte
addresses. The first failure was 53 bytes (a 12-byte string/array swap plus 3
linker-updated literal pools -- and, decisively, **zero `.text` diffs**, proving
the compiled function already matched); the second was 84,324 bytes, all
downstream of the missing `0x20`.

**`cmp -l` prints octal.** Misread as decimal, the bytes look like nonsense.
