## I had claimed this was out of scope — that was wrong

An earlier assessment on this branch said overlay functions couldn't be landed
here because "the tree has no `src/overlay_11*` files". That check was real but
the conclusion did not follow: it established only that *overlay_11* hadn't been
started, not that overlays were unsupported.

What is actually true, and now written up in
`docs/INSERTING_AND_BUILDING.md`:

- **~110 `src/overlay_*.c` files already exist**, across many overlays.
- **`extract_function.py` supports overlays natively** — its own usage examples
  are overlay ones.
- **`main.lsf` lists every overlay** under `Overlay OVY_N`; the tool inserted
  both new objects into the correct section (verified in the diff).
- **`common.mk` has no overlay-specific handling.**

Being an overlay's *first* decompiled function is ordinary — it creates a new
`src/` file instead of merging, exactly as the first function of any `main_*.s`
does. The whole thing matched first try.

**Generalisable**: a negative result about one instance is not a negative result
about the category. Check the category.

## Two type choices, both deliberately minimal

- **`ov11_02324FA0` is `u8[0x20]`, not a struct.** The symbol is `.space 0x20`
  in the data — the size is a fact. Other functions in the overlay touch offsets
  `0x0`, `0xc`, `0x10`, `0x14`, `0x1c`, none of them decompiled, so a struct
  would have to invent a layout around the single field this function reads. The
  array asserts only the size.
- **Return type is `u8`, not `bool8`.** The `ldrb` fixes the width, and **all**
  candidate return types (`u8`, `bool8`, `int`, `u32`) produce byte-identical
  output here, so the type is a free choice. `bool8` would additionally assert
  the value is a truth value — an inference from the two callers testing it in a
  condition, not something the function establishes. `u8` says what is known.
