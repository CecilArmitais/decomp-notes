## Why a batch this size was tractable

**Fact, and it is the whole story.** `struct adventure_log` **already exists** in
`include/adventure_log.h` with every field these touch named and
offset-commented, and `struct dungeon_floor_pair` in `dungeon.h`. **Every offset
in the asm lands on a named field.**

So the modelling reduced to reading which field each function touches. **No new
types, no placeholders, no invented names.**

**The selection criterion is the reusable part.** The scan that found this
cluster ranked candidates by *how small the type surface is*, not by how many
small functions a file holds. Three denser files were rejected first:

- one whose wrappers index a global through **three overlapping strides**
  (`idx*0x20`, `idx*0x60+0xb0`, `+0x40`, `+0x58`) — modelling it would have
  dominated the batch;
- one of 2-instruction veneers whose argument lists would **all** have been
  guesses (the weakness recorded in [`6f907c68`](6f907c68.md));
- one whose accessors are scattered across 100+ functions, so extraction would
  produce ~40 separate source files.

**Function count is a bad proxy. Shared, already-named types are the thing to
look for.**

## 26 of 30 matched on the first candidate

The four that did not were **both instances of the ordering rule added to
`docs/MATCHING_TIPS.md` one commit earlier** — decent evidence that the rule
generalises rather than describing one function.

**`IsAdventureLogNotEmpty` (35).** Needed its loop index declared *before* the
pointer local. With the pointer first the two land in swapped registers; every
instruction was otherwise correct.

**The three `Set` functions (250 each).** Needed the completion-flag write placed
**before** the clamp rather than after. Written in the obvious order the clamp is
emitted ahead of the first pointer load *and* the two literal-pool words come out
reversed. Moving one statement fixed all three at once.

## Shapes reproduced rather than normalised

**Fact.** The counters clamp at `0x000F423F` (999999) and each sets one bit of
`completion_flags[0]`. **The exact shape differs per function and is copied, not
tidied:**

- three increment then clamp (`IncrementNbDungeonsCleared`, `...FriendRescues`,
  `...Evolutions`);
- two clamp then increment (`IncrementNbEggsHatched`, `IncrementNbFainted`);
- the three setters write the flag **before** storing the value.

A reviewer might reasonably expect these to be uniform. They are not, and the asm
is why.

**Fact.** The clamp comparisons are **signed** (`cmp`/`strgt`) even though the
fields are `u32`, so each is written with an explicit `(s32)` cast **rather than
retyping a struct shared with the rest of the tree**. A local, reversible cast
was preferred to a field retype that is neither.

## Declaration hygiene

**Fact.** `ADVENTURE_LOG_PTR` and `_022AB69C` move into `adventure_log.h`.
`src/main_0204FDFC.c` declared the pointer itself, from before any of this was
decompiled; that line is replaced by the header it **already included**, and the
object rebuilds unchanged.

## Open questions

  harder than their instruction counts suggest.
- `IsAdventureLogNotEmpty` returns word-sized (no `and r0, r0, #0xff`), so it is
  typed `s32` rather than `bool8` despite reading as a predicate. Same diagnostic
  as [`3fc19ec7`](3fc19ec7.md).
- `SetAdventureLogStructLocation` points the global at `_022AB69C`, a fixed bss
  address. Whether that symbol deserves a real name is an identification question
  this commit did not take on.
