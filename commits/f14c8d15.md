---

`GenerateExtraHallways` (`0x0233C9E8`, **356 instructions + 3 literal-pool words
= 0x59C bytes**) is dungeon generation: it picks `n_extra_hallways` random grid
cells, picks a random tile inside each, walks outward until it leaves the room,
and then carves a corridor that turns every few tiles until it runs into
something. Seven `Generate*Floor` functions call it, all still assembly.

**No region preprocessor directives** — fact, and mechanical rather than
argued: the wip's `mktarget.py` resolves the NA, EU and JP asm for this address
range to three **byte-identical** files (md5 `30110c3f…`). One source serves all
three. Two of the three pool words are relocations (`DIRECTIONS_XY`,
`FLOOR_GENERATION_STATUS`) and will of course resolve to different addresses in
the three linked ROMs; that is expected and is not region variance in the text.

## Landing shape — a split

**Fact.** The function sits in the middle of `asm/overlay_29_0233AE84.s`, so
both merge branches of `extract_function.py` are gated off and it **splits**:

* the function becomes `src/overlay_29_0233C9E8.c` + a new
  `include/overlay_29_0233C9E8.h`;
* the remainder of the `.s` becomes `asm/overlay_29_0233CF84.s` (next symbol
  `GetGridPositions`, at `0x0233CF84` — the address walk from `0x0233C9E8`
  closes there exactly, with every `_0XXXXXXX:` label asserted against the
  running address);
* `main.lsf` gains two objects where it listed one.

Seven paths change, which is exactly what the census predicted before the tool
was run, including the absence of an `Updating include/…` line — that absence
was its stated check that the tool had not silently chosen a merge.

**A reviewer should discount most of the `asm/include/overlay_29_0233AE84.inc`
diff.** 27 lines change there, but the file is regenerated wholesale by
`write_inc_file.py` and the regenerator sorts **ASCII** where the previous
content was sorted **case-insensitively** — so `_s32_div_f` and the two
`ov29_*` symbols move to the end without anything about them changing. Fact,
readable off the diff. The substantive change is the set of `.public` names that
crossed the cut.

## No landing debt

**Fact.** A tree-wide grep for `GenerateExtraHallways` before landing returned
exactly one file, `asm/overlay_29_0233AE84.s`, with seven `bl` sites. Zero hits
in `src/`, `include/`, any `.inc` or `main.lsf` — so, unlike
[`92335aeb`](92335aeb.md), [`2238fa7d`](2238fa7d.md) and
[`c4d14ec0`](c4d14ec0.md), there was **no stale `extern` to reconcile**. The
name itself is pre-existing in the tree (asm label, `main.lsf`, seven call
sites), so nothing was named here: this was decompilation, not identification.

All seven callers are in the truncated first half of the split and all seven
stay assembly, so **nothing in C calls this function**. The signature only has
to be ABI-compatible with those `bl` sites — which is why several of its types
are undetermined rather than wrong (see *Open questions*).

## Two new types, in the function's own header — flag these

The commit adds no field to and changes no offset in any existing shared type.
It does introduce two types the tree did not have, both in the new header, and
both have consequences past this file.

### `struct unk_0233C9E8` — the 30-byte grid cell

**Fact.** No struct of this shape existed anywhere in `include/` or `src/`
(grepped for `grid_cell`, `dungeon_grid`, size-30 structs and `[15]` arrays;
zero hits). The grid is a **stack local** in every `Generate*Floor`, so it has
no global to key a placeholder on — which, under the naming rules, makes it an
argument-named placeholder keyed on this function: `struct unk_0233C9E8`, fields
`field_0x<off>`.

**Fact — the size is read off the target, not chosen.** At `0x0233CA24`:

```asm
	ldr r1, _0233CF78 ; =0x000001C2
	mla r1, r4, r1, r0
	mov r0, #0x1e
	mla r6, sb, r0, r1
```

`0x1E` = 30 = `sizeof(struct unk_0233C9E8)`; `0x1C2` = 450 = 15 × 30, the row
stride of the `(*grid)[15]` parameter. **450 / 30 = 15 exactly**, so the
*second* dimension is arithmetic. The *first* dimension 15 is **inference** —
see *Open questions*.

**Fact — this function reads eight offsets and writes none:** `0x0`, `0x2`,
`0x4`, `0x6` as `ldrsh`; `0x8`, `0xa`, `0xb`, `0x10` as `ldrb`. The gates are
read off the predication: the attempt continues only when
`field_0xa != 0 && field_0xb != 0`, and then only when
`field_0x8 == 0 && field_0x10 == 0`. Everything from `0x11` to `0x1d` is a
`u8 field_0x11[0xd]` tail purely to make `sizeof` come out at `0x1E`; nothing
here establishes its shape.

**Inference, deliberately kept out of the tree.** `field_0x0/0x2` and
`field_0x4/0x6` look like two `struct position`-shaped corners of the cell's
room rectangle (the two `DungeonRandRange` calls then pick a random tile inside
it), and `GenerateOneRoomMonsterHouseFloor` hand-builds a 1×1 grid and loops
`for (x = f0; x < f4; x++) for (y = f2; y < f6; y++)`, which fits. Readings of
`field_0x8`, `field_0xa`, `field_0xb`, `field_0x10` as "excluded / usable /
has-room / maze" are weaker still. **None of that is in the header, and no field
name was ported from pmdsky-debug**, which was read for layout only.

**Shared-type consequence, for the PR note.** This placeholder did not stay
local: the very next commit, [`5ebe15c4`](5ebe15c4.md), declares
`CreateGridCellConnections` and `GenerateRoomImperfections` over the same type
and its header `#include`s this one. So `struct unk_0233C9E8` is now a
**cross-file type introduced by a commit that only needed eight of its
offsets**, and its field list is a floor, not a total. Anyone renaming it
(to `dungeon_grid_cell`, say, in a real pmdsky-debug sync) must touch both
commits' files.

### `struct unk_0237CFBC` + `extern FLOOR_GENERATION_STATUS` — deliberately partial

**Fact.** `FLOOR_GENERATION_STATUS` had **no C declaration anywhere in the
tree** before this commit. It is defined in
`asm/overlay_29_bss_0237CA18.s:85-87` as `.space 0x4`, and at the branch tip
there are 26 `.word FLOOR_GENERATION_STATUS` pool entries across six
`asm/overlay_29_*.s` files. Landing this function required writing the tree's
first declaration of it.

**Fact — and this is the part to flag loudly: the `.space 0x4` is not the
object's size, and this function reads past it.** It reads byte **+6**
(`ldr r0, =FLOOR_GENERATION_STATUS ; ldrb r0, [r0, #6]`, twice, compared against
`1` and `2`), which lies inside the *next* `.global`, `ov29_0237CFC0`. That the
bss splitter emitted an interior label rather than a separate object is
demonstrable: `ov29_0237CFC0` is written as `strb r2, [r0, #4]` off
`FLOOR_GENERATION_STATUS` in `asm/overlay_29_0233A248.s:412` while also being
read through its own symbol elsewhere. A whole-tree offset survey found accesses
up to a **word at +0x3c**, so the real object is **≥ 0x40 bytes**.

The declaration that shipped is **7 bytes**, sized to what this function uses:

```c
struct unk_0237CFBC {
    u8 field_0x0; … u8 field_0x6;
};
extern struct unk_0237CFBC FLOOR_GENERATION_STATUS;
```

**That is byte-safe for this function whatever the object's trailing shape** —
the access compiles to `ldr =SYM` + `ldrb [rX,#6]` regardless — and it is
honest about being a floor rather than claiming a size. But the census
recommended padding to the measured `≥ 0x40`, or
`extern u8 FLOOR_GENERATION_STATUS[];` read as `[6]`, as zero-cost insurance,
and **that recommendation was not taken.** A 7-byte declaration of a
≥ 0x40-byte object is a live trap the moment a second file includes this header
and writes through it. A reviewer should decide whether it stays.

**Inference, not in the tree:** that `+6` selects a floor-layout mode. The
values are facts — the same byte is written 0, 1 and 2 in
`asm/overlay_29_0233A248.s`, and this function uses it to refuse to let a
hallway run rightwards (`dir == 2`) past x = 32 in mode 1 or x = 48 in mode 2.
The word "mode" is a guess.

## The finding that closed the match: a `-1` delta must be a named local

Recorded in `LEDGER.md` round 2. The four 2×2 corner probes inside the carve
loop test `tx-1` / `ty-1` neighbours. Written inline, each is rematerialised
(`sub r1, r7, #1`) at every use; written as a local it lives in a register
exactly as the target does. **The definition point is what does the work:**

* `xm = tx - 1` sits **before** the C/D pair's first test;
* `ym = ty - 1` sits **inside** `if (first_test) { … }` in both B and D.
  Hoisting it above the `if` costs **+2** rows in B and **+36** in D — the
  overlapping live range forces `xm` to spill and grows the frame to `0x14`.

Editing only that region took the whole-function diff from REAL 207 to 96 and,
as a knock-on, produced the missing `sub sp, sp, #0x10` and drove four other
phases to zero. Round 1 had recorded "the frame is not yet reproduced" as a
consequence of live ranges rather than a thing to chase directly; that
prediction held.

## Falsified — what was tried and what it says about retail's source

Straight from `LEDGER.md`; these are measurements, and none should be re-run.

| change | REAL | what it establishes |
|---|---|---|
| CSE the shared `(tx, ty+1)` test into a local used by two probes | 220 | **No `GetTile` call may be hoisted.** 20 `bl GetTile` in the asm means 20 in the source; deleting one destroys alignment for the rest of the function, so the call table can be read as source order directly |
| one probe's three conjuncts reordered | 109 | MWCC keeps `&&` operands in source order, so the `bl` order in the asm **is** the source order |
| all four deltas declared together at the head of each pair | 134 | a uniform declaration block per pair is impossible — `ym` live across probe C spills `xm` |
| `ym` hoisted to the top of the C/D block | 132 | same mechanism, worst case |
| `xm` named but `ty-1` left inline | 105 | probes A and C go exact, B and D do not — this is the measurement that establishes the `-1` values are named locals |
| a distinct third name `ym2` for probe D | 137 | byte-identical to reusing the name. **Renaming does not steer the allocator; the definition point does** |
| a `const struct position *step` hoisted before the walk loops (round 1) | 221 | the target reads the two members through *two different* addressing forms — `ldrsh [base, index]` for `.x`, `ldrsh [element_ptr, #2]` for `.y` — and one pointer local gives one base for both |
| a plain `for (i = 0; i < n; i++)` with no zero pre-test | 221 → 207 when the pre-test is added | the `movs sl, r3 ; beq` early exit **is** source-level. MWCC's own guard for a signed `i < n` loop would be a `cmp`/`ble` against the bound, not a `movs`-flags/`beq` against zero |

**Measured and free, therefore not evidence either way:** `&&` versus three-deep
nested `if`s in all four probes (byte-identical), and
`GetTerrainType(t) == TERRAIN_TYPE_NORMAL` versus the raw
`(t->terrain_flags & 3) == 1`.

One claim from a parallel worker — that `ym` hoisted above probe B's `if` costs
only +2 — **did not reproduce** on re-measurement and is not in the table. A
second, that "the `+1`/`-1` asymmetry in the asm is an artifact of allocation,
not of retail's source", was flagged as overreach and is **not** recorded as
established. What is established is narrower: the `-1` values must be named
locals with the definition points above, and making the `+1` values locals too
is byte-neutral.

## Two `-W error` traps a scratch cannot see

Both surfaced only at build time, and both are the class the census warned
about — the preset-101 scratch flags carry no `-W` at all, so score 0 says
nothing about either:

1. an unused `const struct position *step;` left behind by the falsified round-1
   experiment;
2. `seg` left dead at function scope once the matching version moved its
   declaration into the loop body — **shadowing silently orphans the outer
   declaration**.

The function-scope locals block was trimmed to exactly `i, x, dir, k, oob, d`
and re-verified at score 0.

A third trap was avoided by construction: `dir` is typed `s32`, not
`enum direction_id`, because the asm computes the index arithmetically
(`add #2` / `sub #2` / `and #6`), and `dir = (dir + 2) & 6;` on an enum-typed
variable is an `int`→enum conversion — invisible on a scratch, fatal under
`-W error`. `docs/MATCHING_TIPS.md` carries the general form.

## Shapes that look wrong and are not

* **The 5×5 box scan reads no tile at all.** Fact. It is purely a bounds test of
  `x−2..x+2` × `y−2..y+2` against `[0, 56) × [0, 32)`, setting a flag and
  abandoning the attempt on the first out-of-range coordinate. Do not look for a
  missing `GetTile` there.
* **The four perpendicular-neighbour guards are compiled two different ways** —
  the pair outside the carve loop reloads the `DIRECTIONS_XY` pool word and uses
  `and r0,r0,#6`; the pair inside uses a cached base with
  `and r1,r0,#6 ; mov r0,r1,lsl #2`. Fact. Factoring all four into one helper
  would mismatch two of them.
* **The two walk loops assign the same three values to different registers**
  (base / byte offset / `&entry` permuted between them). Fact. A candidate
  reusing one spelling for both mismatches one loop.
* **`SetTerrainFlags` / `SetTerrainNormal` / `SetTerrainWall` are `static
  inline` in `src/dungeon_generation.c` and in no header**, so the split put
  them out of reach and the single read-modify-write is written out as two
  statements. Fact about the tree; whether retail's source called such a helper
  is not established.

## Re-verification, after the fact

A later pass (`wip/GenerateExtraHallways/STATUS.md`, 2026-09-11) re-measured the
landed source and found **no drift**: still score 0 in NA, EU and JP,
359/359 rows, zero structural and zero colouring differences. Two points from it
worth a reviewer's attention:

* **The scratch context was reduced from 12434 lines to 91 by deleting whole
  declarations, never by writing stand-ins** — which matters, because
  `docs/MATCHING_TIPS.md` records a case where a hand-written stand-in struct
  with individually-correct offsets still changed codegen and invalidated
  thirteen score-0 functions. Every surviving declaration was additionally
  checked to appear character-for-character in all three regions' full contexts.
* **The mechanical fixpoint is 88 lines and also scores 0 — and is wrong.**
  Dropping the `DungeonRandInt` / `DungeonRandRange` / `GetTileSafe` prototypes
  makes MWCC fall back to implicit `int`; the bytes still match because each
  call is a `bl` with the result already in `r0`, but the compiler emits
  `illegal implicit conversion from 'int' to 'struct tile *'` and the real build
  uses `-W error`. This is a concrete instance of "score 0 on a scratch is not
  the same test as the build".

A mutation suite of eleven deliberately-wrong variants was run against the
reduced context and all eleven behaved as declared, including one that is
*required* to score 0: `s32 oob` → `u8 oob`, because `oob` only ever holds 0/1
and is only tested for truth.

## Open questions for a reviewer

* **`struct unk_0237CFBC` is a 7-byte declaration of an object measured at
  ≥ 0x40 bytes.** Byte-safe here; a trap in a shared header. The census's
  padding recommendation was not applied. This is the single most likely thing
  in the commit to bite a later file.
* **The first dimension of `(*grid)[15]` is inference.** The second is
  arithmetic (450/30). The first rests on a 0x1A60 *upper bound* — the distance
  from the passed address to the top of the caller's frame — agreeing at nine
  holders across three frame sizes. An earlier corroboration from
  `GetGridPositions`' `s32[15]` arrays was **withdrawn**: it writes n+1 entries
  for a dimension of n, so a 15-word array bounds the dimension at 14. There is
  **no record that a flat `struct unk_0233C9E8 *grid` with explicit `x*15 + y`
  was ever compiled**; the two `mla`s do not discriminate the spellings, and the
  argument that the pool-loaded `0x1C2` favours 2-D indexing is dead (450 is not
  an ARM rotated-8-bit immediate, so the pool load is forced either way).
* **That the 450-strided index is `x` and the 30-strided index is `y` is
  inference**, and the parameter names `grid_size_x` / `grid_size_y` assert it.
  Worth stating because it is **asymmetric with the tile map in the same
  header**, which is `tiles[y][x]`. If the reading is backwards, the names are
  backwards and the bytes do not care.
* **Argument 4's width is undetermined.** `u8` and `s32` are equally consistent:
  all seven callers do `ldrb r3, [props, #0x13]` (fact — that is
  `floor_properties.extra_hallways`, an existing in-tree name at
  `include/dungeon_mode.h:888`), and the callee applies no narrowing, but this
  compiler never re-narrows narrow-typed parameters, so that absence
  discriminates nothing. The `blt` rules out `u32` only. `s32` shipped.
* **The `void` return is inference, strong but not proven.** Two paths reach the
  epilogue carrying unrelated `r0`, and all seven callers overwrite `r0` within
  two instructions — so no consistent return value exists, but `void` and an
  ignored `s32` are indistinguishable at these call sites.
* **`oob`'s type is undetermined** by the bytes, as the mutation suite shows
  directly.
* **Whether `r4` holding the `DIRECTIONS_XY` base across the carve loop is a
  source-level pointer local or compiler LICM was never settled.** The one
  spelling that was tried (a `const struct position *step` hoisted before the
  *walk* loops) is falsified; the carve-loop question is a different one and is
  still open.
* **Overlay 29's data sections were never censused**, so a global of the grid
  cell's type may exist — which would outrank the function-named key and mean
  `struct unk_0233C9E8` should be `unk_<GLOBAL ADDR>`. Low-priority housekeeping;
  it must never block a match, but it is why the key is a proposal.
* Every field *meaning* in both new structs is inference and none of it is in
  the tree. If a real pmdsky-debug sync brings `dungeon_grid_cell` and the floor
  generation status struct in, these two placeholders should be retired to it
  rather than reconciled with it.
* **Re-grep for a competing `extern GenerateExtraHallways` before merging.** It
  was clean at landing time, but another branch could add one and a two-TU
  declaration disagreement is invisible to every build.
