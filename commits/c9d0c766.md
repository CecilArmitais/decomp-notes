## The group that is not here, and why: a scratch cannot see inlining

**Fact.** Ten DWC functions from `asm/overlay_00_022DB1A4.s`
(`Dwci_Acc_GetFlag_DataType` … `Dwci_SetReverseBuddyFlag`) all scored **0**,
landed cleanly into `src/overlay_00_022DB0E0.c`, and broke the checksums of
`main.sbin` and `OVY_0`–`OVY_9` — eleven binaries.

**Fact, from `main.lsf`.** That set is not arbitrary. `OVY_0` is `After main`;
`OVY_1`/`OVY_2` are `After OVY_0`; `OVY_3`–`OVY_9` are `After OVY_1`. `OVY_10`
is separately `After main`, and `OVY_11`+ hang off it. The failures are exactly
main plus the whole `OVY_0` subtree — the signature of **`OVY_0` changing
size**, not of wrong code somewhere random.

**Fact, measured from one object file (no full build).** Compiling
`src/overlay_00_022DB0E0.o` and comparing each function's `st_size` against the
address deltas in the original `.s`:

| function | true | compiled | Δ |
|---|---|---|---|
| `Dwci_IsBuddyFriendData` | 56 | 48 | −8 |
| `Dwc_GetFriendDataType` | 12 | 16 | +4 |
| `Dwci_Acc_SetFlag_DataType` | 36 | 40 | +4 |
| `Dwci_SetBuddyFriendData` | 44 | 52 | +8 |
| `Dwci_SetReverseBuddyFlag` | 48 | 56 | +8 |

Net **+16** bytes, which is the shift.

**Fact, from the emitted bytes.** `Dwc_GetFriendDataType` is
`return Dwci_Acc_GetFlag_DataType(a);`. The target is an interworking tail call
(`ldr ip, =…` / `bx ip`, 12 bytes). What compiled is `ldr r0,[r0]` /
`mov r0,r0,lsr #11` / `and r0,r0,#3` / `bx lr` — **both accessors inlined**, no
call at all.

**CORRECTION (added after the commit).** This note first concluded that retail
kept these functions in **separate translation units**. **That was wrong**, and
the reviewer who pushed back on it was right.

**Fact.** The repo has two compile rules and they differ in optimisation level,
not just include paths:

| rule | objects | opt flags | other |
|---|---|---|---|
| `MW_COMPILE_SRC` (`common.mk:149`) | `src/**` | `OPTFLAGS := -O4,s` (`Makefile:7`) | `-enum min` |
| `MW_COMPILE_LIB` (`common.mk:150`) | `lib/**` | `OPTFLAGS_SDK := -O4,p` (`Makefile:8`) | `-enum int -stdinc` |

**Fact, measured.** The same two functions appended to a `src/` file and to a
`lib/` file, each built by `make` with its own rule:

| rule | `probe_caller` | |
|---|---|---|
| `-O4,s` | 16 bytes, **no `bl`** | callee inlined |
| `-O4,p` | 16 bytes, **`bl` present** | call kept |

Both 16 bytes — equal size is not equal bytes, which is why the size table
below under-reports the damage.

**Fact, decisive.** All twelve DWC functions (the ten landed plus the two
pre-existing callees) placed in **one** translation unit under the lib rule
come out at **exactly the right size, all ten of them** — including
`Dwc_GetFriendDataType` at 12 bytes, the tail-call veneer that was 16 when
inlined, and `Dwci_IsBuddyFriendData` at 56, which was 48. So a single file is
fine; the *optimisation level* was the variable, not the file boundary.

**Fact.** Nothing is marked `inline`, and there is no `#pragma auto_inline` or
`inline_max_size` anywhere in `include/` or `lib/`. `-inline on,noauto` is on
both rules and does not prevent it.

**Inference.** These are `Dwc_*`/`Dwci_*` — Nintendo Wi-Fi Connection library
code. It belongs to the **lib** rule, exactly as CLAUDE.md warns for SDK/Nitro
objects. `Dwci_Acc_SetFlags` was correct under both rules because its callee
`Dwci_Acc_SetMaskBits` does real shift/mask work and was too big to inline.

**Not established**: whether a lib-rule object can sit in an *overlay* section
of `main.lsf`. All 135 existing `Object lib/…` lines are under `Static main`.
That, and a real matching build, are what the landing still needs.

**Process note.** The wrong conclusion survived because every check I ran was
consistent with it and I never tested the competing hypothesis — that the flags
differed — even though CLAUDE.md names it explicitly and the answer was two
greps away in `Makefile` and `common.mk`.

## Types added and refined

**Fact, from the asm.** `struct unk_020AFF38` is 8 bytes — `_020AFF38` at
`0x020AFF38`, next `.global` `_020AFF40`. Its initial data is
`.word _0209CD3C` then four zero bytes, so `field_0x0` is a pointer and
`field_0x4` a word. **Inference**: `field_0x0` is `char *` because the only
readers pass it to `strncpy`/`strncmp`.

**Fact, and a caveat about the sizing rule.** `struct unk_022AAE74` does **not**
end where the next `.global` begins. In bss, `_022AAE74` is `.space 0x4` and
`_022AAE78` follows — but the target asm for `sub_02048CB8` loads `_022AAE74`
and reads at `+0x28`, which lands inside `_022AAE78`'s range. So `_022AAE78` is
an *interior label* of one 0x30-byte record, emitted because other code
references that address directly. Sizing a struct from the gap to the next
`.global` gives the wrong answer whenever that happens; the deciding evidence is
which symbol the target's literal pool actually loads.

**Fact.** Two pre-existing placeholders in `include/overlay_11_022E9A78.h` are
refined, both keeping their total size:

| struct | was | now |
|---|---|---|
| `unk_02388FC0` | `u8 field_0x4[8]` | `s32 field_0x4; s32 field_0x8` |
| `unk_023890A0` | `u8 field_0x0[0x44]` | `u8 field_0x0[0x14]; s16 field_0x14; u8 field_0x16[0x2E]` |

**Fact.** No pre-existing code read inside either byte array, and a `HEAD`-vs-now
comparison of the rebuilt objects shows no already-landed function changing
size. **Inference**: the refinement is byte-neutral, which the matching build
then confirmed.

## Landing tooling

**Fact.** Diagnosing the dropped group took roughly eighty minutes and
double-digit full builds, bisecting 48 → 40 → 20 → 10 → 1. That was the wrong
method. The measurement that actually identified the five bad functions —
compile the one object, compare each function's ELF `st_size` against the
address deltas in the original `.s` — takes about seventy seconds and was
available from the first failure.

**Fact.** That check is now a tool (`verify.py`) run before any build. It
compiles only the objects a landing touched, reports compile errors, flags any
landed function whose size differs from `next_addr - this_addr`, and rebuilds
the same objects from `HEAD` to catch a *pre-existing* function whose size
moved. On this batch it caught, in three ~70-second runs, what would otherwise
have been three separate eight-minute builds: a missing `struct unk_020AFF38`
definition, a `struct unk_02388FC0` layout conflict, and finally 36/36 clean.

**Fact.** Equal size is **not** equal bytes — an inlined 16-byte accessor and a
real 16-byte call both measure 16 — so the final matching build remains the
source of truth. Two functions (`ov29_022E41AC`, `ov29_022E456C`) are the last
in their `.s` and have no next address, so only the build checked them.

**Fact.** The root cause of two of this batch's build failures was a known,
already-documented bug left unfixed: the batch module derives its extern list by
keeping lines containing `extern`, which silently drops every
`struct X { … };`. `runbatch.py` now persists the whole context and
`land_from_json.py` carries the definitions across — adding a struct the tree
lacks, and *reporting* rather than guessing when the tree already defines it
with a different layout.

**Fact.** `land_from_json.py` also now runs `hdrcheck.py` over every header it
touches. That would have caught `struct entity` being declared inside a
parameter list in `overlay_29_022E406C.h` and `overlay_29_022E4338.h`, which
needed `#include "dungeon_mode.h"` and cost a build.
