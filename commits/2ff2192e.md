## `unk_020A68C8` — the table behind `DEMO_TEAMS`

**Fact.** 18 records × 4 bytes, two `u16` each, read with `ldrsh`. Decoded from
the initial data in `asm/main_rodata_020A2808.s` and resolved through the tree's
own `_MONSTER_ID_GENDERED` macro in `include/enums.h`:

| # | field_0x0 | field_0x2 | | # | field_0x0 | field_0x2 |
|---|---|---|---|---|---|---|
| 0 | BULBASAUR | CHARMANDER | | 9 | TOTODILE | TREECKO |
| 1 | CHIKORITA | SQUIRTLE | | 10 | MUDKIP | CYNDAQUIL |
| 2 | TREECKO | TORCHIC_SECONDARY | | 11 | PIPLUP | CHIMCHAR |
| 3 | TURTWIG | PIPLUP | | 12 | PIKACHU | CHIMCHAR |
| 4 | CHARMANDER | CHIKORITA_SECONDARY | | 13 | SKITTY | TURTWIG |
| 5 | CYNDAQUIL | TOTODILE | | 14 | RIOLU | PIPLUP |
| 6 | TORCHIC | MUDKIP | | 15 | VULPIX | PIKACHU |
| 7 | CHIMCHAR | TURTWIG | | 16 | PHANPY | MUNCHLAX |
| 8 | SQUIRTLE | BULBASAUR | | 17 | EEVEE | MEOWTH |

**Inference, but about as strong as this gets.** All 36 values resolve to
members of the playable starter/partner roster, in 18 hero/partner pairings with
no repeats of a pairing — exactly what a title-screen demo team table would
hold. `RandomizeDemoActors` picks `RandInt(18)` and stores the pair into the
`SPECIAL_ACTORS` demo hero/partner slots, which closes the loop.

**Worth noting for typing:** entries 2 and 4 use `_SECONDARY` ids (883, 752 —
base + `MONSTER_GENDER_ID_OFFSET` of 600). So the field carries a *full gendered*
`monster_id`, not a bare species index. That is evidence for typing it as the
enum rather than a plain integer — see the sentinel question below.

**Name suggestions** (offered, not applied): `struct demo_team` with `hero` /
`partner` members. pmdsky-debug describes this region as
`18*0x4 (Hero ID 0x2, Partner ID 0x2)`, which agrees. I would rate this
high-confidence; it is left unapplied only because naming wasn't the task.

**Caveat about `_020A68CA`.** A separate `.global` sits at `DEMO_TEAMS + 2`,
i.e. on the *partner* column of record 0. Something references the partner field
directly by its own symbol. That does not affect the layout, but it means a
future rename must keep both symbols resolving to the same address.

## `unk_020A7FF0` — the table behind `ENTITIES`

**Fact.** 12-byte records (stride confirmed by `smlabb r0, r0, #12, r2`).
Record 0 decodes as `{0x0001, 0x0000, &ACTOR_LIST, 0x0000, 0x02, 0x01}`.

| offset | type | evidence |
|---|---|---|
| `0x0` | `u16` | read `ldrsh` in `sub_0206549C` and tested against **3** and **0xa**; data shows **1**. A small-domain discriminator — **fact** that it is compared to those constants, **inference** that it is a "kind" field. |
| `0x2` | `u16` | `0x0000` in the entries inspected; no read located on this branch. Unanalysed. |
| `0x4` | `char *` | points into an ASCII pool. Record 0 → `ACTOR_LIST`, whose bytes are `50 4C 41 59 45 52 00 00` = **`"PLAYER"`**. The pool runs up to `NPC_METAMON_KIREIHANA` immediately before `ENTITIES`. **Fact.** |
| `0x8` | `u16` | returned by `sub_02065B14`; consumed as a string id — see below. |
| `0xa`, `0xb` | `u8` | `0x02`, `0x01` in the entries inspected. Unanalysed. |

**Observation worth a reviewer's attention.** The symbol `ACTOR_LIST` — a
pre-existing decomp name, not mine — labels the bytes `"PLAYER"`, i.e. it is the
*first string* in the entity-name pool rather than a list structure. Either the
name is scoped differently than it reads, or it is mislabelled upstream. I have
not changed it and am not asserting it is wrong; flagging it because a later
identification pass should resolve it.

**Name suggestions**: the record type looks like a script-entity descriptor
(pmdsky-debug: `struct script_entity`); `field_0x4` is the entity's symbolic
name; `field_0x8` a display-name string id (below). `field_0x0` is plausibly a
type/kind enum, but I have only three observed values and would not name it
without enumerating every `cmp` against it across both resolvers.

## `sub_02065B14`

```c
if (id == -1) return 0;
return ENTITIES[id].field_0x8;
```

**What it feeds — the strongest evidence chain on this branch.** Its one located
caller (`asm/main_020151E4.s`):

```asm
ldrsh r0, [sp, #0x94]
bl   sub_02065B14
movs r1, r0
beq  _02023F48                 ; 0 -> fall back
add  r0, sp, #0x42
bl   GetStringFromFileVeneer   ; (buf, string_id)
b    _02023F5C
_02023F48:
ldrsh r0, [sp]
bl   GetNameString
mov  r1, r0
add  r0, sp, #0x42
bl   strcpy
```

The in-tree header `include/main_0202593C.h` declares
`void GetStringFromFileVeneer(u8* buf, s32 string_id)` — **fact**, not
inference. So the return value is passed as a `string_id`, and **0 means "this
entity has no string of its own"**, in which case the caller falls back to a
name lookup and `strcpy`.

**Inference**: `field_0x8` is a display-name string id, and `sub_02065B14` is
its accessor, returning 0 both for "no entity" (`id == -1`) and "entity has no
string". **Name suggestion**: something like `GetScriptEntityNameStringId`.
Note the two zero-returns are indistinguishable to the caller, which is
consistent with the observed fallback and may be intentional.

**Matching note.** Writing `return ENTITIES[id].field_0x8;` directly scores
**905** — MWCC if-converts the body into predicated instructions and folds `+8`
into the literal pool (`ENTITIES+0x8`). Binding `&ENTITIES[id]` to a pointer
local first restores the target's `smlabb` + `ldrh [r0, #8]` + early `bxeq lr`:
**score 0**, and a matching build.

## Not included: `GetScriptEntityMonsterId` — best 600/900

Structurally matched; only the frame encoding differs. The target saves `lr`
alongside a dummy register as 8-byte alignment padding and reuses that slot as
the out-parameter scratch (`push {r3, lr}` … `pop {r3, lr}`); every candidate
emits `push {lr}` + `sub sp, #4`. Same 8-byte frame, different encoding, 300
points at each end.

Ruled out — **all scoring exactly 600**: out-variable as `s16` / `int` /
1-element array / struct member / with a second unused local (initialising it is
*worse*, 800); parameter as `s16` / `u16` / `int`; variadic; callee declared
`void` vs `s16` and with `void *` parameters; preset-101 flags, the real build
flags read off the actual `mwccarm.exe` invocation, ±`-fp soft`, ±`-g`; all five
`mwcc_20_*` builds on the instance; and `-O4,p`, `-O4`, `-O3,s`, `-O2`, `-O1`,
`-O0`.

**This function is matchable — I just didn't find the form.** Retail was
compiled from ordinary C with this toolchain, so a source that produces
`push {r3, lr}` exists by construction; the invariance above only says every
variant I tried was the wrong shape, which is a fact about my attempts and not
about the function.

Productive directions still untried:

- find a function **already in the tree** whose compiled form uses the
  dummy-register frame and copy how it is written — that is evidence rather than
  guesswork, and I never looked;
- vary the **callee's** declaration (`sub_0206549C`'s parameter types are my
  reconstruction, and the caller's frame may follow from them);
- a human eye on real decomp.me.

The flag sweep produced no information and should not be repeated.

## Open questions

1. **Should `enum monster_id` declare a `-1` sentinel?** The species are cast to
   `enum monster_id` on store because the enum has no negative enumerator, so
   under `-enum min` it is unsigned and cannot reproduce the signed (`ldrsh`)
   reads. The game *does* return -1 from `GetScriptEntityMonsterId`. Adding the
   sentinel was tested and builds — including when applied to `struct monster`'s
   own `id` — so this is a question of correct meaning, not feasibility. Left to
   upstream rather than diverging here.
2. **`field_0x2`, `field_0xa`, `field_0xb` of `unk_020A7FF0` are unanalysed.**
   Constant in every record I inspected; I did not chase their readers.
3. **`ACTOR_LIST`'s scope**, per the observation above.
4. **The two resolvers** (`sub_0206549C`, 349 lines; `sub_02065050`, 312 lines)
   remain asm. They are the real consumers of both tables, and decompiling them
   would settle `field_0x0`'s domain and much of the naming above.
