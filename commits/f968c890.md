## The two that are not here

**`SetPositionInitialLivePerformer` — 225.** Every instruction is present; the
`add rX, rY, #0x100` that forms the base for a byte-offset read is scheduled
two instructions earlier than the target places it. Tried: hoisting both
direction reads into locals, dropping those locals, reversing the comparison,
and swapping the order of the two zero stores. Six variants, no movement.

**`sub_020024E4` — 35.** A two-register swap in a zero-fill loop: the target
holds the counter in `r1` and the array base in `r0`, the candidate the other
way round. Tried: both declaration orderings, a block-scoped cursor, an extra
zero temporary, a `while` form, and assigning the cursor before the mutex
calls (worse, 245). Eight variants.

**Both are the limit of what was tried, not a property of the function.**

## Matching findings

### A two-word struct copy schedules both loads first

**Fact, measured on `GetCollisionBoxLivePerformer`:**

| form | score | what it emits |
|---|---|---|
| two field assignments | 60 | load, store, load, store |
| two initialised locals, then two stores | 310 | both loads, then `stm r1, {r0, r2}` |
| `*out = *(struct T *) &p->field_0x10;` | **0** | both loads, then two `str` |

**Fact.** This is not the `ldm`/`stm` width question already recorded — a
two-word copy emits four plain `ldr`/`str` in all three forms. Only the
schedule differs.

**Inference.** The original almost certainly had a two-field struct member at
`0x10`, and the cast stands in for a member this placeholder layout does not
name. The same fix in the writing direction took
`SetMovementRangeLivePerformer` from 430 to 0, which suggests members at `0x2C`
and `0x34` too.

### A bug in the candidate, not in the compiler

**Fact.** `sub_020023A8` first scored 215 because the candidate advanced `src`
and *then* read through the incremented pointer. The target reads
(`ldrsb r3, [r1]`), tests, and only then advances. Worth recording because the
diff looked like a scheduling difference (`ldrsb [r1, #1]!` versus
`add r1, r1, #1` / `strb`) rather than the logic error it was.

### Nitro declarations come from the prefix header

**Fact.** `OS_DisableScheduler` returns `u32`; the scratch declared it `void`,
and `-W error` rejected the redeclaration. Every TU already has nitro's
declarations through `-prefix global.mch`, so the local externs are removed.
`OS_ResetSystem` is the exception — it is declared in **no** reachable header
and keeps its own extern.

## Tooling

**Fact.** Three tool bugs surfaced, all from real failures:

1. **`split_src` required a single-line signature.** A long parameter list
   wraps, and the splitter then refused the source outright.
2. **The lander's placeholder search had the same blind spot**, plus a CRLF
   mismatch: the stored signature's newlines are `\n` while the file's are
   CRLF, so a wrapped signature never matched.
3. **`verify.py` ranked functions by `(asm file, address)`.** That breaks as
   soon as a landing splits a `.s` — two functions from one original file end
   up recorded under different file names, and the sort interleaves them,
   reporting a bogus out-of-order failure. Now ranked by address alone.

**Fact, a process note.** Landing before every function in a run has matched
splits the `.s` around the unmatched ones, which *moves the remaining functions
into new files*. Re-scoring them afterwards needs the new file name, and the
`asm` field recorded for them must still name the file they occupied at `HEAD`
or the size and order checks resolve against nothing.
