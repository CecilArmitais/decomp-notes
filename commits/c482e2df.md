# 1. `sub_02050CF8` / `sub_02050D84` in translation units of their own — and the hole in the method

## The defect

**Fact** (`git show c482e2df^:asm/main_020504BC.s:397`): `BitstreamDebug` is

```asm
	arm_func_start BitstreamDebug
BitstreamDebug: ; 0x020509BC
	bx lr
	arm_func_end BitstreamDebug
```

one instruction, four bytes, an empty body — and it is one of the other 26
functions of the same `.s`. **Fact** (`src/main_020504A4.c:166`): the landed C
is `void BitstreamDebug(struct bitstream *stream) { }`.

**Fact, from the commit message**: compiled *beside* it at `-O4,s`, mwcc inlines
the call away, each of the two functions comes out **two instructions short**,
the ROM shifts and **33 of 37 sbins stop matching**. Retail emits a real `bl`,
so separate objects are what reproduce it.

**Inference, and a small one**: the two instructions are the argument set-up and
the `bl` — the call site is `BitstreamDebug(&stream);` with `stream` a stack
local, so an inlined empty callee removes exactly an `add rN, sp, #…` and the
`bl`. Nothing measured this out; the arithmetic is consistent with it.

**Fact, corroboration nobody had to construct**: seven other call sites of
`BitstreamDebug` already exist in five other files
(`src/main_0204DA2C.c` ×2, `main_0204DD80.c`, `main_02059060.c`,
`main_02059A74.c`, `main_0205BD14.c` ×2), every one of them in a translation
unit where `BitstreamDebug` is only declared. All of those already match in the
ROM. So the only two call sites in the tree that could ever have shared a TU
with the definition are exactly the two that had to move.

**Inference** (stated as such in the commit message too): retail compiled these
two apart from `BitstreamDebug`. The bytes force *some* arrangement in which the
call is not inlined; they do not tell you retail's file layout. Two
one-function objects are the minimal arrangement that reproduces it, not a
reconstruction of retail's source tree.

## The meta-lesson, which is the transferable part

**A decomp.me score and a rendered diff row count are both blind to object
LENGTH.** That is not new — `wip/ov29_022E34A8_EU/LEDGER.md` L1 records the same
class of bug from the other side, where a broken row counter reported a
candidate that was **12 bytes short** as `SIZE OK`, and in both directions. What
is new here is worse, because the tooling was not broken:

**The candidate was measured in the only arrangement where the defect cannot
appear.** `wip/main_020504BC_all/LEDGER.md` §6 measures both functions against
`ctx_full_<REGION>.h` — the landed `src/main_020504A4.c` **preprocessed and cut
before its first function body**. In that context `BitstreamDebug` is a
prototype and nothing else, so there is no body to inline and the object cannot
be short. The ledger's verdict, verbatim, is *"The premise does not reproduce at
this base"*, with both functions at exactly 140 and 132 bytes — the target spans.

It was right about its base and wrong about the ROM. **A one-function scratch TU
is not a model of a multi-function object**, and every inter-function
optimisation — inlining first among them — is invisible to it by construction.

**An observation a reviewer should treat as a lead, not a conclusion.** The same
ledger section records *earlier* figures of **132 / 124** from a different,
stale context, and says plainly that *"How those numbers were produced is
**not** established; it is an open question."* Those are exactly 140 − 8 and
132 − 8, i.e. the two-instruction shortfall. The arithmetic coincides. It cannot
be the *same* mechanism — a scratch has no `BitstreamDebug` body to inline — so
either there is a second way to lose those two instructions, or it is a
coincidence. **Nothing here separates the two, and I did not try.**

**Not recorded anywhere but the commit message.** No `wip/*/LEDGER.md` or
`STATUS.md` carries the 33-of-37 measurement or the object dump it came from,
and `docs/MATCHING_TIPS.md` has **no entry** for this failure mode (its nearest
neighbour, *"A same-object `bl` can never match in a multi-function decomp.me
target"*, is about a diff-rendering artifact with no byte consequence — a
different thing). The three matching builds are what stand behind the claim.
Someone should write the tip.

# 2. Two objects of different size share `0x022AB918`

## The change

`asm/main_bss_022AB0AC.s` gains **one label** (**fact**, the whole hunk):

```diff
 	.global TEAM_NAME
 TEAM_NAME:
+	.global _022AB918
+_022AB918:
 #ifdef JAPAN
 	.space 0x8
 #else
 	.space 0xC
 #endif
```

**Fact**: no `.space` changes, no later symbol moves, so the bss layout is
untouched. The commit message reports that this one-line change was **built
alone against the previous commit** to prove it byte-neutral; that build is not
something this note re-ran.

## Why one symbol cannot work

**Fact**, from `wip/main_020504BC_all/STATUS.md` §"data change": four functions
reference `0x022AB918` twice and the target's literal pool holds **two** entries
for it:

```
StoreDefaultTeamData      pool = [TEAM_NAME, TEAM_NAME]
GetMainTeamNameWithCheck  pool = [TEAM_NAME, TEAM_NAME, 0x00000237]
sub_02050CF8              pool = [TEAM_NAME, _022AB924, TEAM_NAME]
sub_02050D84              pool = [TEAM_NAME, _022AB924, TEAM_NAME]
```

Any C naming one object emits **one** entry and re-loads it — the function is
then 4 bytes short, which shifts the ROM. That is a size defect, not a score.

**Fact, and it is a proof rather than a survey** (`LEDGER.md` §1,
`tools/poolmatrix*.py`, 26 spellings on a stand-alone TU with an asserted
control case that must and does report 2): **MWCC keys pool entries on
`(symbol, addend)` and de-duplicates globally within a function,
unconditionally.** Array decay, `&struct`, `&elem[0]`, a pointer cast, index
arithmetic, a local pointer, predication, an intervening call, an intervening
different constant, an inner-scope `extern` redeclaration and `volatile` all
collapse to one entry. A **non-zero addend does** get its own entry
(`f(&G.m); G.n = 0;` → `['G+0xc','G']`; `f(A - 0xc)` → `['G','G-0xc']`, so
negative addends fold too). With one symbol both keys are `(TEAM_NAME, 0)`.

**Fact, ROM-wide**: 98 of 9059 functions have a duplicated *symbolic* pool word,
so the pattern is neither rare nor special to this file. `sub_02048C5C` is the
clean worked example.

## Why nesting in C does NOT create the second key

This is the part worth spelling out, because it is the obvious objection.

Declaring the name buffer as a **member** of the record — `struct { u8 name[0xc];
s32 points; u8 flag; } TEAM_NAME;` and reaching the buffer as
`TEAM_NAME.name` — produces **one** pool key, `(TEAM_NAME, 0)`, because
`&TEAM_NAME.name` has addend 0 and **a struct member has no linker symbol of its
own**. The de-duplication is at the relocation level, not the expression level:
mwcc has one `R_ARM_ABS32` against one symbol at one addend, so it emits one
word. `LEDGER.md` §1 measures this directly — `extern u8 TEAM_NAME[]` plus a
cast to the struct, `&TEAM_NAME`, `&TEAM_NAME.field_0x0[0]`, a local `u8 *`
bound to the name first, and a `*(s32 *)&TEAM_NAME[0xc]` pointer pun are **all
105**, i.e. all one entry.

What creates the second key is a second **symbol**. Hence the extra `.global`.

## What actually landed, and how it reads

**Fact**, `src/main_020504A4.c:19-24` (and repeated in the two new files):

```c
extern struct unk_022AB918 TEAM_NAME;      /* the 0x14-byte record (0x10 under JAPAN) */
#ifdef JAPAN
extern u8 _022AB918[8];
#else
extern u8 _022AB918[0xc];                  /* its leading name buffer */
#endif
extern s32 _022AB924;
```

Note this is **not** what `STATUS.md` planned — that had both symbols typed as
the struct. The landed shape types the alias as the buffer it actually is, which
is the better reading of the two.

**Fact, and it surprises on first reading**: the record's declared extent (0x14)
is larger than the `.space` under its own label (0xC). The remaining 8 bytes are
`_022AB924`'s own `.space 0x8`, so `TEAM_NAME.field_0xc` **is** `_022AB924` and
`TEAM_NAME.field_0x10` is `_022AB924 + 4`. Three C declarations now describe
overlapping bss. That is legal and byte-neutral — bss is reserved space and
nothing range-checks a declared type against it — but it is the kind of thing a
reviewer should see stated rather than discover.

**Fact, the asymmetry in the bodies is forced, not sloppy.** Which of a
function's two uses gets the alias is decided by the **order the target's pool
words appear in**. So `StoreDefaultTeamData` writes the name through
`_022AB918` and the record fields through `TEAM_NAME`
(`src/main_020504A4.c:236-243`), while `GetMainTeamNameWithCheck` — whose two
uses are *both* the name — tests `TEAM_NAME.field_0x0[0]` and passes
`_022AB918` (`:249-254`). Swapping either pair moves the differing row without
removing it.

## What is fact, what is inference, what was not checked

* **Fact**: `TEAM_NAME` is at `0x022AB918`; `_022AB924` is at `TEAM_NAME+0xC`
  (NA/EU) / `+0x8` (JP); the code reaches `0x022AB924`/`0x022AB928` as
  `[base, #0xc]` / `[base, #0x10]` off a base of `0x022AB918`.
* **Fact**: the target holds two pool entries with the same value, and this
  compiler cannot produce that from one symbol.
* **Inference**: retail therefore had **two objects** at `0x022AB918` — most
  plausibly a name buffer and a record spanning name + points + flag.
* **Not determined by anything measured**: *which* of the two retail's symbol
  table called `TEAM_NAME`. The assignment above was chosen because it keeps
  five other functions at score 0. **This is the single item in the commit most
  worth pushing back on.**
* **Not checked upstream**: pmdsky-debug has no data symbol anywhere in
  `0x22AB910..0x22AB930` (its `data:` list was searched), so there is no upstream
  name and `_022AB918` is the ordinary `_0<ADDR>` placeholder, claiming nothing.
* **The alternative that needs no bss change, recorded so nobody re-derives it**:
  declare `extern u8 _022AB924[];` and reach the record as
  `((struct unk_022AB918 *)(_022AB924 - 0xc))`. It produces the same two entries
  (the `A - 0xc` fold is measured) and scores the same. Rejected as strictly
  uglier.
* **Two derivations behind the field types, both fact**: `field_0x0` is `u8[]`
  and not `char[]` because `GetMainTeamNameWithCheck` reads it with `ldrbne`
  (under `-char signed` a `char` member gives `ldrsb` — measured 413 vs 5);
  `field_0x10` is `u8` because `sub_02050CF8` tests the stored value with
  `tst r0, #0xff`. `_022AB924`'s **sign is unobservable** — it is only ever
  `&_022AB924` handed to `CopyBits*` with `nbits = 0x20` — and `s32` was chosen
  to agree with the `field_0xc` that aliases the same storage.
* **Fact, stack frames were measured, not read off `sub sp`**:
  `StoreDefaultTeamData`'s `u8 buf[0x14]` scores 5 while `[0x10]` and `[0x18]`
  score 413; `GetMainTeamNameWithCheck`'s `u8 name[0x40]` scores 5 while
  `[0x3c]` and `[0x44]` score 43.

The four functions' residual score of **5** is the literal-pool alias class
(`docs/MATCHING_TIPS.md` → *"A literal-pool symbol name can differ while the
bytes are identical"*): the instruction stream is byte-identical and one `.word`
names a different symbol at the same address. The three ROM builds are what
settle it.

### 4.1 `MONSTER_DATA_TABLE_PTR` — a pointer becomes a struct (`include/monster_data.h`)

**The widest-reaching change in the commit.** **Fact**, the diff:

```c
/* before */ extern struct monster_data_table *MONSTER_DATA_TABLE_PTR;

/* after — and the header gains #include <file.h> for struct iovec */
struct unk_020B09B4 {
    struct monster_data_table *field_0x0;
#ifdef EUROPE
    void *field_0x4;
    struct monster_file_contents *field_0x8;
#else
    struct monster_file_contents *field_0x4;
    void *field_0x8;
#endif
    struct iovec field_0xc;
};
extern struct unk_020B09B4 MONSTER_DATA_TABLE_PTR;
```

**Why it is forced (fact)**: `LoadMonsterMd` loads **one** pool word,
`.word MONSTER_DATA_TABLE_PTR`, and then reaches the iovec at `[r0, #0xc]`. MWCC
folds a displacement like that only when both addresses belong to one object;
two separate `extern`s each get their own pool word. The same function also
carries `.word _020B09C0` — `&OBJ` **and** `&OBJ.member`, which is what taking
the address of a member emits.

**Fact, the size is measured, not assumed**: `tools/datawalk.py` walks
`asm/main_rodata_020A2808.s` byte by byte (1355 symbols, every `_0XXXXXXX` label
asserted equal to its own address) and puts `MONSTER_DATA_TABLE_PTR` at
`0x020B09B4` with the next symbol at `0x020B09C8` — **0x14 bytes =
4 + 4 + 4 + sizeof(struct iovec)**, with `_020B09C0` at `+0xc` inside it.

**Fact, the `#ifdef EUROPE` member swap is read off the EU target**:
`str r1, [r0, #8]` where NA/JP have `[r0, #4]`. It is the same shape
`struct item_tables` already carries for `ITEM_DATA_TABLE_PTRS`.

**Blast radius, fact**: **29 call sites in four files** gain `.field_0x0` —
`src/main_020526EC.c` (4), `src/main_020527A8.c` (2), `src/main_0205283C.c`
(19), `src/main_02052B28.c` (4). Those four are the *complete* set: they are the
only files that `#include "monster_data.h"`, and no other C declaration of the
symbol exists.

**Layout-preservation proof, measured not asserted**: `tools/objcheck.sh`
compiles each of the four files twice in one container — once from an untouched
clone, once with the new header — with the real `-O4,s` + `MWCFLAGS`, and diffs
the disassembly. **IDENTICAL for all four, in all three regions.**

**Knock-ons: none reach a signature.** `field_0x0` keeps its
`struct monster_data_table *` type, so no accessor's return type or parameter
moves; the 29 sites change spelling only.

**The naming call, flagged.** `struct unk_020B09B4` + `field_0x<off>` follows
CLAUDE.md's placeholder rule. Its cost is 29 call sites gaining `.field_0x0`
**and** `LoadMonsterMd` needing an `#ifdef EUROPE` in its **body**, because the
member name encodes an offset that moves between regions. The tree's own
precedent for this construct (`struct item_tables`) uses meaning-bearing member
names, which would remove the body `#ifdef` entirely. Naming was out of scope, so
the placeholder form is what shipped; swapping is mechanical and a reviewer's
call.

### 4.2 `struct unk_0209C850` — a new type in `include/item.h`

**Fact**, the whole hunk: eight members, `s32` at 0, `u8` at 4 and 5, `s16` at 6,
`u8` at 8, 9, 0xa, 0xb.

| offset | evidence (**fact**, off `asm/main_0200D1F0.s`) | width |
|---|---|---|
| `+0x0` | `ldr r0,[r8]`; switched over 0…4; tested `cmp r0,#1 / cmpne r0,#3` | 4 |
| `+0x4` | `ldrb r0,[r8,#4]`, tested against 0 only | 1 |
| `+0x6` | `ldrsh r1,[r4,#6]`, **sign**-extended, printed with `%d` | 2 |
| `+0x8` | `ldrb r0,[r8,#8]`, tested against 0 only | 1 |

**Fact, size 0xC**, the gap from `_0209C850` to the next `.global` (`_0209C85C`).
Its initialiser bytes `00 00 00 00 | 00 00 00 00 | 01 00 00 00` decode under the
candidate type as `{0, 0, 0, 1}` over the four fields the asm touches —
corroboration for the widths, not proof of meaning.

**Inference, deliberately not in the field names**: `+0x0` selects buy vs sell vs
no price; `+0x6` is a column position handed to `[CLUM_SET:%d]`. Nothing depends
on either reading.

**Name**, per the collision rule: three globals have this layout;
`_0209C850` wins on uses (5, all in `src/main_0203D538.c`, against one each for
`OVERLAY25_UNKNOWN_STRUCT__NA_238B498` and
`OVERLAY31_UNKNOWN_STRUCT__NA_2389EF0`) **and** on lower address.

**Why `item.h`**: `item.h` carries **no prototypes**, so a type there drags
nothing into the 370 files that include it and can collide with nobody's
call-site `extern`.

**Layout-preservation proof**: `tools/layoutcheck.sh` compiles **ten unmodified,
`item.h`-heavy translation units** twice and requires every function to be
byte-identical, relocations included — **102 functions, all identical**. That is
strictly stronger than a `sizeof`/`offsetof` assertion, which only checks members
somebody thought to name. **Honest limit**: the comparator enumerates globally
visible `STT_FUNC` symbols, so `static` functions are not counted, which is why
two of the ten show a count of 1.

### 4.4 `struct bitstream::ptr` becomes `u8 *` (`include/save.h`)

**Why (fact, measured)**: `CopyBitsTo` and `CopyBitsFrom` read the byte at
`stream->ptr` with `ldrb`. Under `-char signed` a `char *` member yields

exactly one row (`ldrbne r6,[r7]` vs `ldrsbne r6,[r7]`); with `u8 *` they score

alone, so a cast at the read site is inert** — this is a header fix, and it is
falsified as a *class*, not as a case.

**Layout preserved, measured**: `sizeof` `0x10` before and after; `end`,
`bit_idx`, `bit_count` all emit identical code. The only change in the whole

**Blast radius, fact**: `struct bitstream` is reachable from many files via

`src/main_02071A14.c`'s `loop->end` is a `struct dse_sub_loop *`, not a
bitstream — checked by resolving the type inside the enclosing function, not by
a file-wide name match.

**A documentation casualty, flagged and not fixed** (CLAUDE.md forbids authoring

the "moved verbatim" exception): the member's comment `// Current byte` is gone
with the old declaration. `end`, `bit_idx` and `bit_count` keep theirs. **A
reviewer with full context should decide whether it comes back.**

**A deliberate non-change, recorded so nobody re-runs it**: `bitstream::end`

# 8. `FixedPoint64ToInt` — the only function of the whole effort still unmatched

**It is not in this commit** (`asm/main_02001CB0.s` still holds it), and it is
the reason the branch is not "all callees done". Recording where it stands, so
the next person starts from the limit of the attempts rather than from scratch.

**Fact**: 9 instructions, 0 pool words, span `0x02001CB0..0x02001CD4` = 36 bytes,
identical in all three regions (the `.s` carries no region directives).

```asm
ldm   r0, {r1, r2}
mov   r0, #0x10000
rsb   r0, r0, #0
lsl   r1, r1, #0x10
and   r0, r2, r0
orr   r0, r1, r0, lsr #0x10
tst   r2, #0x8000
addne r0, r0, #1
bx    lr
```

**Fact, where it stands**: best *correct* candidate **225**, 9 instructions,
36 bytes — the exact target span, so **this is not a length problem**. Best
*probe* (semantically wrong, used only to localise) **200**, with **all nine
target rows byte-exact**, `ldm r0, {r1, r2}` included.

**Fact, the residue is a single scheduling question.** The candidate's
instruction multiset is exactly right — same nine mnemonics, same immediates, the
same folded `lsr #0x10` on the same operand of the same `orr`. The one structural
defect is that `and` and `lsl` are **transposed**, which cascades into the
colouring: the target's `and` overwrites `r0`, the mask constant's own register,
so the constant dies there and only `r0..r2` are needed; the candidate writes the
`and` to a fresh `r2` while `r0` is still live, needs `r3`, and the `ldm` pair
shifts.

**Fact, the emission rule, measured on nine distinct chain shapes.** For
`A | B` → `orr Rd, Rn, Rm, <shift>`, MWCC emits
`[constants hoisted] [Rn's chain except its last op] [Rm's chain] [Rn's last op] [orr]`,
and the fold goes to the source-**first** operand when its top node is a shift.
**The target breaks this**: its last pre-`orr` instruction produces `Rm`.

**Inference, tightly constrained**: `x->upper << 0x10` was **already
materialised** when the `|` was evaluated — it is not an operand MWCC evaluated
as part of that expression tree.

**Fact, the only mechanism found that materialises it inside one basic block** is
a **second use that cannot fold a shift** (a `cmp`/`tst`). A second use that
*can* fold re-derives and costs an extra instruction. Two earlier entries were
**corrected** by this: an extra basic block alone does nothing, and a single use
in a later block does not pin the order either — the earlier probe worked because
its variable was *reassigned* in a conditional block, i.e. multiple definitions.

**What is dead — do not re-run** (~510 spellings across four sessions, each
recorded with its base): `+` instead of `|`; `^`; the mask via a shift pair, a
local, `%`, `/`, and every spelling of the constant; six spellings of the upper
term; every declaration order; every type and **the whole signature axis**
(`int`/`s32`/`u32`/`unsigned`, the return type, `const`, by-value struct, `s32 *`
/ `u32 *` indexing, an extra unused parameter); sixteen wrapper nodes intended to
stop the shift being the operand's top node (all folded by the front end);
every zero-cost block boundary (`do{}while(0)`, `goto`, unreferenced label,
`while(0)`, `for(i=0;i<1;i++)`, `switch(0)`); every inline-helper form; every
branchy form (11-15 instructions — MWCC duplicates the tail rather than CSE-ing
it); both 64-bit routes, with a mechanism (the right-shift template folds the
*high* word's `lsl` — the mirror image of the target); and `register` storage.
**Flags were the preset-101 string throughout and were never varied**, and that
was re-verified against `main.lsf` and `common.mk` rather than assumed: this
object's neighbours are ordinary `src/` objects built with `-O4,s`.

**Still untried**, which is the honest form of the answer:

1. A **zero-cost, semantically exact second use** of `x->upper << 0x10` that
   cannot fold a shift. This is the entire remaining gap. Nobody has constructed
   one that is also correct — the rounding test reads `x->lower`.
2. Any materialise-vs-sink driver other than use count. Statement **distance**
   was measured and does not matter; an aliasing barrier and an argument temp
   have not been tried.
3. **Compiler introspection** (`docs/COMPILER_INTROSPECTION.md`) — the question
   is now single and sharp: *which MWCC pass forward-substitutes this local, and
   on what predicate?*
4. Find a **landed** function whose retail `orr Rd, Rn, Rm, shift` also emits the
   non-folded operand first, and read the C that produced it.

**This is a statement about the search, not about the function.** Retail was
compiled from ordinary C by this exact toolchain, so a matching source exists;
~510 spellings have not found it.
