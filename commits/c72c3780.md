Decompiles eight ground-mode setters and identifies the global they write,
`_020B0B08`, as a table of "special actor" slots.

## What the identification rests on

Each slot is claimed on **two independent pieces of evidence**, and I would not
trust a slot supported by only one:

1. a **writer** — one of the setters storing to that offset;
2. a **reader** — a resolver that reads the same offset when handling a
   specific `script_entity_id`, which is what ties an offset to a *symbolic* id
   rather than to a guess.

The readers are `sub_0206549C` (reached from `GetScriptEntityMonsterId`) and
`sub_02065050` (reached from `GetActorMatchingStorageId`). Both are still asm on
this branch; both are jump-table dispatchers keyed by entity id.

Corroboration: the initial `.byte` data at the definition decodes as
`ENTITY_NPC_HERO` (60) and `ENTITY_NPC_PARTNER` (61) in the slots where those
are the sensible defaults. That is consistent with the mapping rather than proof
of it.

Size — 28 bytes — is taken from the gap to the next `.global` in
`asm/main_rodata_020A2808.s`, so it is a fact, not an inference. The trailing
`u8 padding[2]` exists to make the struct span that gap; nothing observed writes
it.

## Naming

This branch was an **explicit identification task**, which is what licenses
naming here at all. Absent that, the default is to leave `_0<addr>` alone.

- `_020B0B08` → **`SPECIAL_ACTORS`**, `struct special_actors`. pmdsky-debug has
  neither a name nor a struct for this global, so this is a fresh, contributable
  name rather than a port.
- **Field names are inferences.** They come from which `script_entity_id` each
  resolver branch handles (`ENTITY_TALK_MAIN` → `talk_main`, and so on). The
  *offsets* are facts; the *names* are my reading of what those ids mean. This
  is the part of the diff most worth challenging.

## Field typing, and the `-enum min` trap

Fields are typed as the real enums (`script_entity_id`, `monster_id`) rather
than `s16`. That is deliberate and was verified, because the reasoning is easy
to get backwards:

`-enum min` sizes an enum to the smallest type spanning its **entire**
enumerator range — not to the values a particular field happens to use. The
redirect slots use ids 46–59, all under 128, which *looks* byte-sized; but
`script_entity_id` runs to `ENTITY_NPC_PINPUKU = 385`, so the enum is 2 bytes
and matches the target's `strh`.

Verified on a scratch: the full enum gives `strh`, **score 0**; the same enum
truncated to max 61 collapses to 1 byte, gives `strb`, **score 200**. So `s16`
and the real enum are byte-identical here, and the enum carries more meaning.

I initially documented the opposite of this and was wrong.
