## Decompiled

| function | address | fade |
|---|---|---|
| `DseTrackEvent_VolumeFade` | `0x020723C0` | `channel->volume` @ `0x2c` |
| `DseTrackEvent_PanFade` | `0x02072668` | `channel->pan` @ `0x3c` |

Both were **deferred near-matches** carried since the DSE work.

**Fact.** Each reads a signed byte as the fade target and a little-endian pair as
its duration in ticks, writes the target, then either snaps `current` to it when
the duration is zero, zeroes the duration when there is nothing to travel, or
divides the distance by the duration (via `_s32_div_f`) to get the per-tick
delta.

**Fact.** The two differ *only* in which `struct dse_fade` they address. Both
already exist in `dse.h`; no new types.

## What closed them, and it is backwards

**Fact, with a measured cost.** The target loads `ptr_next_byte[2]` first, then
`[0]` and `[1]`. Writing the target expression first — so that its load comes
first *in the source* — leaves the loads in ascending address order at **620**.
Declaring `ticks` first and `target` second emits the target's order and scores
**0**.

```c
    /* 620 */                                  /* 0 */
    s32 target = ...ptr[2]...;                 u16 ticks  = ...ptr[0], ptr[1]...;
    u16 ticks  = ...ptr[0], ptr[1]...;         s32 target = ...ptr[2]...;
```

**So the later-declared initialiser's loads are issued first**, and the rule is
to write the declarations in the *reverse* of the order the asm reads them.

**Fact about the search, and this is what makes the finding trustworthy.** Seven
other spellings of the same two statements were tried and **every one stayed at
exactly 620**: explicit locals for each byte in the target's load order,
`s8`/`s16`/`s32` intermediates, an inline cast, and a pointer-cast subscript.
Only the declaration swap moves it. A finding that survives seven null results is
worth more than one that worked first try.

Now in `docs/MATCHING_TIPS.md`, with the caveat that it does **not** generalise to
statement order — reordering assignments rather than declarations made these
worse, at 560.

## A `lib/DSE` landing detail

**Fact.** The headers `extract_function.py` generates for `lib/DSE` do **not**
include `dse.h`, so the build fails with *"illegal use of incomplete
struct/union/class 'struct dse_channel'"*. Every other header in that directory
already includes it; both new ones were given it.

That is the third `lib/DSE`-specific landing fixup, after the `main.lsf` prefix
and the `.include "include/..."` path recorded in
[`3046c8b0`](3046c8b0.md).

## Three deferred DSE functions remain, and this commit does not close them

**`DseTrackEvent_TuningFade`** — the same family plus a bend fade and the
`SetTuning` tail. Hoisting `container` out of `channel` **before** the flag test
takes it from **935 to 760**. That is progress and not a match. Its `bend.target`
is `(u16)((bend.current >> 16) + (b2 << 8)) << 16`, and the target computes the
`b2 << 8` as `lsl #24` then `lsr #16`, which no spelling tried here reproduces.

**`DseTrackEvent_SetupKeyBendLfo`** — unchanged in substance. Its instructions
have matched for some time; **only register assignment differs**.

This is the one worth being precise about, because
[`59fad373`](59fad373.md) and the branch note both named exhaustive permutation
as *the untried move*. **It has now been tried.** All **120 orderings** of its
five byte locals, plus **eleven structural variants** — `s16`/`s32`/`u32` byte
locals, explicit amplitude and phase temporaries, a pointer local for the
sub-struct, inline subscripts, a named constant for the repeated `1`, and two
statement orders. **Best is 55**, down from 65.

**That is a negative result, and it is useful.** It rules out the hypothesis this
branch had been carrying, and it means the remaining difference is driven by
something other than the order the locals are introduced. **It is not evidence
that the function cannot be matched** — retail was compiled from ordinary C by
this toolchain, so a matching source exists by construction. Directions still
untried: the shape of the `(s16)` conversion on the amplitude, whether the two
`1` stores come from one variable or two in the original, and whether the
function originally shared a body with its siblings through a helper.

**`DseTrackEvent_SetLfoParameter`** — not attempted this batch; the recorded lead
is that its duplicate-value cases need merging.

## A tooling fix made along the way

`probe.py`'s error reporting returned nsjail sandbox startup logging instead of
the compiler diagnostic, because the wrapper prefixes the whole blob with
`Compiler error:` and a naive grep for "error" matched every line of it. It now
slices at the `### mwccarm.exe Compiler:` banner. Three round trips were wasted
guessing at context errors before that was fixed.
