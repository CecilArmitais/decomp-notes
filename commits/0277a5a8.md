## What the function does

**Fact.** A jump table over overlay group ids 0–0x24. Group 0 is always loaded;
the other ranges check one of the three `LOADED_OVERLAY_GROUP_0` slots, each
gated on the parent slot holding the expected group (1/2 at `[2]`, 4/0xd/0xe at
`[1]`). Out-of-range ids hit `Debug_FatalError` with a `prog_pos_info` record —
**fact**: the record decodes as `{"overlay.c", 177}`, i.e. `__FILE__`/`__LINE__`
of the original assert.

## Why data had to move: extern vs in-TU changes codegen

The function copies `_02092558[2]` to the stack (the callee takes a non-const
pointer, so the copy is obligatory). The copy's two loads:

- with `extern struct prog_pos_info _02092558[];` → loads emitted
  **low-offset-first** — two instructions transposed vs retail, immovable
  through ~30 code rewrites;
- with the array **defined in the same TU** (initializers visible) → loads
  emitted **high-offset-first**, matching retail exactly. Scratch score 20 → 0
  on that one change, with *no* change to the code.

**Fact**, established twice over (scratch + ROM). The compiler schedules a
struct copy differently depending on whether it can see the source data's
definition. Retail's overlay.c necessarily defined this array in-file (it is the
assert machinery of that file), which is why retail has the other order.

## Why the strings could NOT move: three compiler facts

Retail's layout is array (0x92558), `"overlay.c"` (0x92580),
`"check group error"` (0x9258C). Reproducing the strings from C failed for
reasons worth keeping:

1. **Anonymous string literals go to writable `.data`**, not `.rodata` —
   verified with `readelf` on the object: each literal became its own `.data`
   PROGBITS section, and the link placed them at `0x020B3360`, the far data
   region (84,324-byte ROM diff).
2. **`-str readonly` does not exist** in mwccarm 2.0/sp2p2 — the option accepts
   only `[no]reuse, [no]pool`, and neither moves literals to `.rodata`.
3. **A named `const u8 x[]` string does land in `.rodata`** — but is emitted
   *before* the array **regardless of definition order** (both orders built and
   ROM-diffed: identical 53-byte result, string first).

So the two strings stay as assembly, in a new 32-byte
`asm/main_rodata_02092580.s`, and the C references them `extern` — which is
also exactly the established convention in every matched file
(`script_variable.c` passes `&EVENT_FLAG_EXPANSION_ERROR`, an extern).

## The three-way split, and its two traps

`asm/main_rodata_020908D4.s` now ends before `_02092558`; the C owns the array;
`asm/main_rodata_02092580.s` owns the strings; `asm/main_rodata_020925A0.s` owns
the rest. `main.lsf` orders them C → strings → rest, so rodata lands at retail
addresses (the linker groups sections by type in object order — precedent:
`src/script_variable.o` followed by `asm/main_rodata_0209CECC.o`).

Two traps hit on the way, both now in `docs/INSERTING_AND_BUILDING.md`:

- **The rodata `.inc` is a shared header.** `main_rodata_0209CECC.s`'s second
  line includes `main_rodata_020908D4.inc`. Regenerating that inc per-file broke
  a file that was never touched. Leave it alone; new split files include it too.
- **partB's `Object` line goes after the C object**, not after partA — rodata
  order follows lsf object order.

## The diagnostic that made this tractable

"Checksum FAILED" says nothing. Building **clean HEAD and the change in one
container and `cmp -l`-ing the two `main.sbin`s** turns it into exact byte
addresses: the first failure was 53 bytes (a 12-byte string/array swap + 3
linker-updated literal pools — and, decisively, **zero `.text` diffs**, proving
the compiled function already matched); the second was 84,324 bytes all
downstream of the missing 0x20 (strings gone to `.data`). Each diff pointed
directly at its cause. (`cmp -l` prints **octal** — misread it as decimal and
the bytes look like nonsense.)
