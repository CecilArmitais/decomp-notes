**Fact.** All five merged into an adjacent existing source; none split a `.s`.
**Fact.** **Four** of the five carried a region conditional in the asm, so all
three ROMs were built. Two of those needed an `#ifdef JAPAN` in the landed C —
`DoMoveReviver`'s message id and `sub_02027AA0`'s slot swap. The other two
(`DoMoveRapidSpin`, `TryActivateIqBooster`) differ only in a field offset that
`dungeon_mode.h` and `dungeon.h` already absorb, so their C is region-neutral and
only the JP build demonstrates it. `sub_020568DC` has no region conditional at
all and US alone would have covered it.

**Fact.** `DoMoveReviver` was one of the six functions listed as *stalled* on
[`4d2a484c`](4d2a484c.md). It was never actually attempted — it was set aside for
needing region-conditional C, which turned out to be one `#define`. The list was
wrong about it, and two of the remaining five (`sub_020568DC`,
`TryActivateIqBooster`) were likewise untried rather than stuck.

## `TryActivateIqBooster` — declaration order *does* move registers here

**Fact.** Every candidate scored **60**, and every differing row was the same
instruction at the same address with callee-saved registers rotated one place:
the target holds the IQ value in `r6`, the count in `r7` and the loop index in
`r8`; the candidate had them in `r8`, `r6`, `r7`.

**Fact.** Moving one declaration takes it to **0**:

```c
/* 60 */
struct entity *members[4];
s32 n;
s32 i;
s16 iq = DUNGEON_PTR[0]->floor_properties.iq_booster_value;

/* 0 */
struct entity *members[4];
s16 iq;
s32 n;
s32 i;

iq = DUNGEON_PTR[0]->floor_properties.iq_booster_value;
```

**This contradicts an existing entry in `docs/MATCHING_TIPS.md`**, which recorded
that declaration order has *no* effect on callee-saved assignment — 65 compiles,
all byte-identical. Both measurements are real; the reconciliation is **function
size**. That sweep was `SetLeaderAction`: ~75 locals, frame `0xDC`, where
register pressure decides the colouring and a declaration move changes nothing.
`TryActivateIqBooster` has four locals and no pressure at all, so first-definition
order is what is left to decide it. The tips entry now carries this qualification;
the cheap permutations are worth trying *first* on a small function.

**Fact.** Nothing else about the candidate changed — `while` instead of `for`
(60), a nested-`if` instead of early returns (60), and `i` declared before `n`
(45) were all tried and none of them is the lever.

**Fact.** `floor_properties::iq_booster_value` is at `0x1E` within
`floor_properties`, which starts at `0x286B2` — `0x286D0`, the offset in the asm.
Its own comment already says "IQ increase from the IQ booster item upon entering
the floor", which independently corroborates the function name.

**Fact, and the same scratch-vs-build gap as last sweep.** The candidate passed
the item as the literal `0x44` and scored 0, but the real build rejected it:
`-W all -W pedantic -W error` refuses the implicit `int`→`enum item_id`
conversion. The literal is `ITEM_IQ_BOOSTER = 68` in `include/item.h` — a second
independent corroboration of the function's name, and the third time in three
sweeps that a scratch score of 0 was necessary and not sufficient (see
[`8cfb04e1`](8cfb04e1.md) and [`19c62d4b`](19c62d4b.md)). The scratch does not
use the build's warning flags, so any int-where-an-enum-is-expected argument gets
through it.

## `DoMoveRapidSpin` — the result is whether damage landed

**Fact.** The target sets its return value to 1 **before** the random-outcome
call, so a failed random check still returns TRUE:

```asm
	mov r4, #1
	bl DungeonRandOutcomeUserAction
	cmp r0, #0
	beq _023279A0          @ -> returns r4, which is 1
```

**Fact.** The early-return spelling (`if (DealDamage(…) == 0) return FALSE; …
return TRUE;`) scores **570**; an explicit `result` variable set inside the
damage branch scores **0**. Same funnel shape recorded on `DoMoveBubble` and its
relatives, but here the two spellings are *not* interchangeable.

**Fact.** The bit tested is
`struct monster::contact_ability_trigger_bitflags & 2` at `0x192`. That field's
existing comment says "One exception is the move Rapid Spin which sets one of the
flags for the user" — written by someone else, about this function, before it was
decompiled.

## `sub_02027AA0` — two bytes whose roles swap between regions

**Fact.** The region difference here is not an offset shift. The same two byte
slots are written in the *opposite order*:

```asm
	cmp r0, #1
	...
#ifdef JAPAN
	streqb r1, [r0, #3]
#else
	streqb r1, [r0]
#endif
```

and the mirror image for `r0 == 2`. So JP writes slot 3 where the others write
slot 0, and vice versa.

**Fact.** This is corroborated by the rodata a few symbols away, where
`_020AFD94` and `_020AFD98` are *defined in swapped order* under `#ifdef JAPAN`
in `asm/main_rodata_020A2808.s`. Whatever the two slots represent, the regions
disagree about which is which.

**Inference.** Two screens or two windows, with JP numbering them the other way
round. Nothing here establishes that, and no name was introduced — the code keeps
`_020AFD4C.field_0x0[0]` / `[3]` under a plain `#ifdef JAPAN`.

## `sub_020568DC` — the house idiom was already there

**Fact.** The count is reached as
`(&t->number_active_team_members_main)[team]` — taking the address of a scalar
field and indexing past it, because `struct team_member_table` declares the three
per-team counters as separate `s16`s rather than an array.

**Fact.** This is **not** a new invention: `src/main_020564B0.c`,
`src/main_020568A4.c` and `src/main_02056914.c` already spell it exactly that
way. `GetAppointedLeaderMemberIdx`, which lives in the very file this function
merged into, is the same function specialised to the active team, and the landed
code follows its shape line for line.

**Fact.** Both an early return and a `result` variable score 0. The early return
was kept to match the neighbour.

## Region-varying message id

**Fact.** `DoMoveReviver`'s id is `0xF09` (US) / `0xC4B` (JP), a delta of −0x2BE
— the same delta as `DoMoveSwallow` and `DoMoveHelpingHand` in
[`19c62d4b`](19c62d4b.md), and still not the −0x2C0 that
`src/move_orb_effects.c`'s `JPN_MSG_OFFSET` uses. Spelled as its own
`#ifdef JAPAN` define, as in the previous sweep.

## Naming

**Fact.** No function renamed; `sub_02027AA0`, `sub_020568DC`, `_020AFD4C`,
`_020AFD94` and `_020AFD9C` keep their placeholder names. The one name introduced
is the `REVIVER_LOG_MESSAGE` macro, following the existing convention. No new
struct or field was added anywhere.
