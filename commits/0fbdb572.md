## Decompiled

| function | address |
|---|---|
| `GetMissionTargetEnemy` | `0x02349620` |
| `ov29_02349688` | `0x02349688` |
| `SetTargetMonsterNotFoundFlag` | `0x023496C4` |
| `GetTargetMonsterNotFoundFlag` | `0x023496D8` |

The first three read and write the two dungeon flags at `0x1` and `0x3`;
`GetMissionTargetEnemy` returns `enemy_species[0]`. No new types.

**Each was verified by a matching build, not by the scratch** — three alone,
`GetMissionTargetEnemy` alone, then all four together. That distinction is the
whole point of this note.

## The cause of the previous commit's failure, found

[`dfbb8236`](dfbb8236.md) left thirteen functions unlanded: all had reached
score 0 on a scratch, all failed four checksums with no compile error.

**Bisecting produced a one-function reproducer** — `GetMissionEnemyMinionGroup`,
seven instructions — and disassembling the object the real build emits gives the
answer.

**Fact.** For `enemy_species[index + 1]`:

| context | emitted |
|---|---|
| the scratch's cut-down `struct dungeon` | `add r0, r0, #1` · `add r0, r1, r0, lsl #1` · `add #0x700` · `ldrsh [r0, #0x6e]` — **matches the target** |
| the real `dungeon.h` | `add r0, r1, r0, lsl #1` · `add #0x700` · `ldrsh [r0, #0x70]` — one instruction shorter |

**Same compiler, same flags, same C.** Both compute the same address. The real
header lets the compiler fold the `+1` into the load displacement; the cut-down
struct does not.

## Why this matters more than one function

**The scratch verification for the entire cluster is invalid**, not just for this
function. Score 0 against an invented struct says nothing about a build that uses
the real one.

**And the cut-down struct was not wrong.** Every offset and size in it was
independently confirmed correct by the compile-time assertions in
[`dfbb8236`](dfbb8236.md) — `mission_destination` at `0x760`, `enemy_species` at
`0xE`, `sizeof(enum monster_id) == 2`, and five more. It was merely *different*
from the real header, and that was enough to change a fold.

That is the uncomfortable part: **"every offset checks out" does not make a
context faithful.** The assertions retired the layout hypothesis correctly, and
were still compatible with the real cause.

**Inference, and it is the reason the failure looked structural.** Six functions
emitting one instruction less than the target shortens `OVY_29`, which changes
an overlay-table entry held outside it — which is why `main.sbin` failed
alongside three overlays and made this look like a linker or `.public` problem
rather than a codegen one. The structural hypothesis in the previous note was
wrong, and the byte-diff it recommended would have found this faster than the
bisect did.

## The rule, now in MATCHING_TIPS

**Build scratch context from the real headers.** Concatenating header text is
enough for a self-contained one — that is what fixed the DSE work in
[`59c4a95e`](59c4a95e.md), and the same mistake was made again here, which is
why it is now written down as a rule rather than an anecdote.

For a header with a deep include tree, preprocess it inside the build image with
`mwccarm -E` (which needs `LM_LICENSE_FILE` set, or it fails a license check
before doing anything). That yields ~9,200 lines reproducing the real build's
view. **It is not finished**: the output does not yet compile as decomp.me
context, failing on a `typedef s32 fx32_8;`, so the recipe is a starting point.

## What this cost

Roughly ten builds across the two commits. The bisect was mechanical and correct
but slow; the disassembly that actually answered it took one container run and
should have come first, once "no compile error, four checksums" was on the table.
**That is the third time this session the decisive test was available earlier
than it was reached for** — see [`b6faa493`](b6faa493.md) and
[`59c4a95e`](59c4a95e.md).

## Open questions

- **The thirteen are not near-matches to iterate on.** They need re-verifying
  against a faithful context before any of their C is judged; some may already be
  correct and some may need a different spelling.
- **Whether the target's non-folded form is even reachable from plain C under the
  real header is unknown.** It was never tested against a faithful oracle, which
  is exactly the gap this note is about.
- Four others (`IsCurrentMissionType`, `IsCurrentMissionTypeExact`,
  `GetItemToRetrieve`, `GetItemToDeliver`) never reached 0 even against the
  unfaithful context, so their scores are doubly uninformative.
