`CreateGridCellConnections` carves the hallways between the cells of a
dungeon-generation grid, and then — gated by its last argument — randomly merges
some adjacent cells into single larger rooms. **573 instructions + 1
literal-pool word = 574 words = `0x8F8` bytes** (fact; the address walk closes
exactly on the next symbol, `GenerateRoomImperfections` at `0x0233ED34`, with
zero label mismatches, in all three regions).

**One wording in the commit message is loose.** It calls this "the immediate
neighbour of `GenerateExtraHallways`". They are neighbours in *workflow* — this
is the next function taken out of the `.s` file that the `GenerateExtraHallways`
split created — but not in address. **Fact:** the function immediately before it
is `AssignGridCellConnections` (its pool word `_0233E438` is the last thing in
the truncated `.s`), and the one immediately after is `GenerateRoomImperfections`.

## The signature, argument by argument

```c
void CreateGridCellConnections(struct unk_0233C9E8 (*grid)[15], s32 grid_size_x,
                               s32 grid_size_y, s32 *arg4, s32 *arg5, bool8 arg6);
```

**Fact — arity is 6**, established from both sides. Caller side
(`asm/overlay_29_0233AE84.s:185`): four register arguments plus two `str`s to
`[sp]` and `[sp,#4]`. Callee side: the prologue pushes ten registers (`0x28`)
and subtracts `0x48`, so the first incoming stack argument is `[sp,#0x70]` and
the second `[sp,#0x74]` — and the body reads **exactly those two, once each**.
No slot at or above `0x78` is ever read, which closes the arity.

**Fact — `void`.** The two exit paths leave *different, unrelated* values in
`r0` (a byte flag on one path, `grid_size_x` on the other), so no consistent
return value exists, and no caller reads `r0`. *(Worth recording how this
survived: a census owner gave the reason as "the callee sets `r0` on neither
exit path", which is **false** — both do. The conclusion is right on corrected
evidence, which is exactly why the wrong reason mattered: nobody downstream
could have re-checked it.)*

**Fact — the element widths.** `arg4` and `arg5` are loaded as
`ldr rX, [base, rIdx, lsl #2]` → 4-byte elements. `arg6` is read once with
`ldrb` → one byte, hence `bool8`.

**Inference, and thin** — the *signedness* of `arg4` / `arg5` is not
discriminated by the bytes. `s32 *`, `u32 *` and `int *` all emit `ldr … lsl #2`
here, and nothing in the function compares an element against zero in a way that
would separate them. `s32 *` was chosen to match `grid_size_x` / `grid_size_y`.

**Fact — `arg6` gates the whole merge phase.** A single `bne` skips **324
instruction rows**, cross-checked against the phase table
(P3..P8 = 42+69+66+70+67+8 = 322, plus 2 rows the phase tool attributes to P2).
What the flag *means* is open; every one of the nine call sites was read and
they do not settle it.

## `CreateHallway` — a provisional prototype, and it is the riskiest line here

`void CreateHallway(s32 arg1, s32 arg2, s32 arg3, s32 arg4, bool8 arg5, s32
arg6, s32 arg7);` is added to the new header. It is the **first C declaration of
this symbol anywhere in the tree** (fact, grep at the parent commit).

**Fact — arity 7**, read off `CreateHallway`'s own prologue at `0x0233F120`: it
pushes ten registers and, **with no `sub sp`**, reads `[sp,#0x28]`,
`[sp,#0x2c]` and `[sp,#0x30]` — stack arguments 5, 6 and 7. Argument 5 is read
`ldrb` (a byte → `bool8`); argument 7 is read `ldr` (a word).

**Fact — it is 193 instructions** (`EnsureConnectedGrid` at `0x0233F424` minus
`0x0233F120` = `0x304` = 193 words, no literal pool), with 14
`ldmia sp!, {…, pc}` exits, none of which sets `r0` — hence `void`.

**Everything else about it is inference and should be read as "the loosest types
that compile".** The parameter names are positional placeholders on purpose (see
below). Per CLAUDE.md's rule on provisional declarations, this line is expected
to be **replaced** when the callee lands, not maintained.

**It was.** `0ee40140`, later on this branch, decompiles `CreateHallway` into
this same `src/overlay_29_0233E43C.c` and rewrites the prototype to
`void CreateHallway(s32 x, s32 y, s32 end_x, s32 end_y, bool8 vertical, s32
turn_x, s32 turn_y)`. A reviewer looking at the branch tip will not see the
placeholder form at all; a reviewer looking at *this* commit in isolation
should treat those seven types as unverified.

## How the match was actually reached

The work ran as a census plus three rounds with parallel owners on disjoint
phases of the function, each behind an adversarial verifier. The whole thing is
in `LEDGER.md`; the parts a reviewer should care about:

**The function was carved into 9 phases against control-flow seams** — 573 rows,
50 labels, 14 back edges = **seven nested loop pairs**, one 4-arm dense jump
table (`cmp r0,#3` / `addls pc, pc, r0, lsl #2` after `DungeonRandInt(4)`).
The big double loop (P2, 191 rows) was deliberately kept whole rather than cut
in half, so that one defect could not read as two phases' worth.

**Round 1 composed to 567/573 rows.** Round 3 closed it.

**The entire residue was ONE register-allocation fact**, and three owners
attacking P2 from different angles converged on it independently, which is what
makes it worth believing:

> **MWCC hoists the bare product `j*30` into a register.** That evicts another
> value to the stack → a 19th stack word (`sub sp,sp,#0x4c` against the target's
> `#0x48`) → the push loses its alignment register → every later slot shifts by
> 4. That one fact explained P2's 52 REAL **and** ~24 REAL scattered across five
> other phases.

**Fact, as the ledger records it** (the constants are re-verified here —
`mov sl, #0x1e` at row 28 and nine `mla`s in the target — but the four-plus-one
split was not independently re-counted while writing this note): the target
never keeps the product; it re-derives `row + j*30` in-block, fused as `mla` at
four sites and as a local `mov #0x1e` + `mul` at the fifth, where an offset-0
field lets it address `[r4, r0]` directly.
**Inference (explicitly not verified in the compiler):** `grid[i-1][j]`
canonicalises to `grid + (i-1)*450 + j*30`, whose only common subexpression with
`cell` is the bare product, so GCSE promotes it; both sides keep exactly 8
callee-saved values live across the inner loop and the candidate wanted a ninth.

### Two negative results worth more than the positive ones

**A conclusion drawn on a stub is not a conclusion.** Owners were measuring
their fragment against a scaffold whose *other* phases were empty. One verifier
showed what that costs: four candidate sources for P2 that the scaffold
separated by **3 REAL** (509/510/512/512) were separated by **59 REAL**
(60/103/104/113) once the real function was compiled around them. This
generalises the ledger's standing "a lever measured while the candidate was the
wrong shape has not been measured" from *length* to *surrounding context*.

**A retracted "finding".** "Flipping an `== 0` test's arm order changes codegen
here" was proposed as measured fact and nominated for `docs/MATCHING_TIPS.md`.
Its verifier rebuilt both flips under real pressure and got **row-for-row
identical** output. MWCC canonicalises `if (x != 0) A else B` and
`if (x == 0) B else A` identically **when both arms are present**; the
arm-order rule governs a *single* predicated arm. Retracted before it shipped.

Three further Round-2 claims a verifier **could not reproduce** are recorded so
nobody builds on them: that forcing `j*30` to lose the race yields the target's
entire P2 register assignment verbatim (re-ran at 145/191 exact rows); that P3's
source shape is not a lever (the owner's own variant differs in 331 of 602 rows);
and that a dense jump table only appears for a `switch` (one negative instance is
not a property of the compiler).

## Four shapes in the landed C that look wrong

Three of them a reviewer should push on. Two were later removed.

### 1. Eight `(u32)j` casts — recorded as load-bearing, and they were not

**Fact:** the landed source carries `(u32)j` at **8 occurrences on 4 lines**, all
of them inside `CreateHallway` argument lists, none in the loop body.

The reason given at the time was that the target needs **two** CSE classes — the
loop body's cell pointer, and the `CreateHallway` argument lists whose base is
rematerialised in-block — and that four attempted removals each cost 305 rows.

**Round 5 retracted that**, and the retraction is the most useful thing in this
wip. The measurement was sound; the inference from it was not. *"Removing X
costs 305 rows" means that particular removal costs 305* — four spellings were
tried and reported as a property of the casts. The evidence that a plain-C form
had to exist was not a measurement at all: **pret/pmd-red carries a matched
sibling of this function written in plain C with no index casts.**

What the mechanism actually is (now in `docs/MATCHING_TIPS.md` → *"Retail
RECOMPUTES an index address your candidate reuses"*, cited to this function):
MWCC keys CSE on the address expression **including integer conversion nodes**,
so what splits the use-set is *the presence of a conversion*, not its
signedness or its spelling. Three controls:

| variant | result |
|---|---|
| `(s32)j` — a cast to `j`'s **own** type, semantically a no-op | score **0**, byte-identical to `(u32)j` — so "unsigned" was never the mechanism |
| the cast applied at **every** site instead of four | byte-identical to **no** casts — the target needs the *split*, not the cast |
| `int jj = j;` (different type, no cast) | score **0** |
| `s32 jj = j;` (same-type copy) | score **8354** — copy propagation erases it |
| `+j`, `0 + j`, `(j)`, `j * 1`, `-(-j)`, `(j \| 0)`, `*(&j)` | all fold back to plain `j` |

`bbbc4e70`, later on this branch, replaces all eight casts with one `int jj;`
alias at score 0 in all three regions, `320 → 278` lines.

**The honesty point survives the fix and belongs here:** retail's reason for a
recomputed index at the call sites and a reused one in the loop head is **not
established by the bytes**. The `int` alias is a device that reproduces the
codegen; it is not recovered source, and it asserts nothing about retail's types
— which is precisely why it is preferable to an unsigned cast on a signed index,
which does.

### 2. `cell[-15]` and `cell[-1]` — formally out-of-bounds, disclosed not hidden

**Fact:** switch cases 0 and 1 reach their neighbour through
`cell = &grid[i][j]` and then `cell[-15]` (15 occurrences) / `cell[-1]` (15
occurrences), which is pointer arithmetic outside the 15-element inner array
object. Cases 2 and 3 spell the **same kind of neighbour** as
`grid[i + 1][j]` / `grid[i][j + 1]`. Two spellings of one idea, in one function.

`LEDGER.md` discloses this rather than shipping it silently, and justifies it by
measurement: the UB-free spelling was recorded as costing **59 REAL**.

**A reviewer should treat that justification as untested for the landed source,
and I am saying so rather than tidying it.** The ledger entry is from **Round
1**, describes the construct as sitting in **P2** and spells it `cell[15]`,
whereas what landed has it in the **switch cases** as `cell[-15]` / `cell[-1]`.
The draft it was measured on is not the source that shipped, and `59` is also
the figure from the unrelated stub-environment demonstration on the same page,
so the two may be conflated. Given that Round 5 retracted *exactly this class of
reasoning* for the casts, the honest reading is "no spelling tried in Round 1
replaced it", not "it is load-bearing".

**`bbbc4e70` removes it** — every neighbour access becomes `grid[i - 1][j]` /
`grid[i][j - 1]`, the `cell` local disappears, and the function still scores 0.
So on the branch tip the UB is gone; it is present only in this commit and one
after it.

### 3. `int x1;` among `s32 x0, y0, y1;` in cases 0 and 1 only

**Fact:** cases 0 and 1 declare `s32 x0, y0, y1;` and then `int x1;`, while
cases 2 and 3 declare all four `s32`. This is not a typo — it is the same
`int`-vs-`s32` distinctness the tips file documents
(`s32` is `typedef signed long`, so the two are different types with identical
representation, and a copy between them survives copy propagation). **Inference:**
it is doing the same job as the casts above — supplying a conversion node.
Whether it is still needed once the casts are gone is not recorded; `bbbc4e70`
drops it along with everything else.

### 4. Declaration order is doing real work

**Fact:** the frame is `sub sp, sp, #0x48` = 18 word slots, **all eighteen
touched**, three of them argument homes — so **fifteen locals reach memory**,
against exactly one in `GenerateExtraHallways`. The declaration-order rule
(first-declared local gets the highest address) therefore constrains this
function heavily, and orderings that look arbitrary — `s32 y, x;` with `y`
before `x`, `s32 x0, y0, y1;` before `int x1;` — should be assumed load-bearing
rather than tidied. This was not individually re-measured per declaration; it is
the standing rule plus a frame that leaves no slack.

## Two owner decisions worth copying

Recorded because they are the opposite of the usual failure:

- **`R3_TAIL` owned seven phases with 14 missing rows and shipped no change**,
  having proved by experiment that all 14 were collateral of the one P2 slot.
  Once P2 landed, every one of those phases went to zero untouched. Inventing
  work in a nearly-closed phase costs more than it gains.
- **`R3_P2B` found the whole function matched with one extra edit in P1, a phase
  it did not own.** It verified `REAL 0`, then deliberately left its own overlay
  *without* the edit, parked it as a probe file, and told the integrator. That
  is why integration was a two-file copy with no ambiguity about authorship.

And one that is not: two agent-delivered fixes **did not compose as delivered**
— one reintroduced 12 out-of-bounds accesses while removing the casts, and both
halves had to be re-read and recomposed by hand. *A candidate reported as "score
0" is a claim about the score, not about the rest of the source.*

## What happened to this wip afterwards

Not part of this commit; useful for anyone re-running the harness.

- **Round 4 (drift detection)** re-verified the tree source at score 0 in all
  three regions and found **no codegen drift**. It also found that `ae.py` had
  been loading the NA context for **every** region — and the three `mkctx.sh`
  outputs are *not* the same file (`EUROPE` reorders two `struct item` pointers;
  `JAPAN` changes a struct's size). Harmless here because neither type is
  reachable from this function — but that had been assumed, not measured.
- **A stale context, found only because it was regenerated.** The stored
  `ctx_base.h` predated the landing and had been built from a different include
  set. Keeping a generated context around and trusting it is not enough.
- **Stage 2 (context minimisation)** took the scratch context from 12449 lines
  to **74** (10380 non-blank C lines → **43**), holding score 0 after every cut,
  with two new controls added because source-side controls cannot see a
  degenerate context: **NC3** widens a struct field *in the context* (score
  15461, proving the retained lines still pin the layout) and **NC4** fails on
  any compiler warning. Only *removal* was performed — no declaration was
  replaced by a hand-written stand-in, which is the line
  `docs/MATCHING_TIPS.md` → *"A cut-down scratch context can make wrong C score
  0"* draws.
- **A smaller context existed and was refused.** Deleting the prototypes of
  `DungeonRandInt`, `DungeonRandRange`, `GetTileSafe` and `CreateHallway` also
  scores 0 — mwcc falls back to an implicit `int` and a callee returning 32 bits
  in `r0` emits identical code. Four lines, in exchange for a context that could
  never notice a callee whose signature had drifted. Rejected on purpose.
- **The bisect lied about what is load-bearing.** Its first run reported six
  large unrelated enums as required; each had been referenced by a declaration
  the same pass removed *later*, and nothing retried them. Believing it would
  have shipped a 1076-line context and recorded fictional compiler behaviour.
  The general form: *a negative result from a dependency-sensitive probe expires
  the moment a dependency moves.*

## Open questions for a reviewer

1. **`arg4` / `arg5` signedness is not discriminated by the bytes.** `s32 *`,
   `u32 *` and `int *` all produce the `ldr … lsl #2` the target has. Their
   *meanings* are likewise open — all nine call sites were read and do not
   settle it.
2. **`arg6`'s meaning is open.** Fact: it is a byte that gates 324 instruction
   rows. Everything past that is inference and the parameter is a placeholder.
3. **`CreateHallway`'s seven parameter types are inference.** Arity 7 and the
   widths of arguments 5 and 7 are facts; the rest is "the loosest that
   compiles". Superseded by `0ee40140` — check the types there, not here.
4. **The `cell[-15]` / `cell[-1]` out-of-bounds arithmetic in this commit is
   justified by a Round-1 measurement on a draft that differs from what landed.**
   Treat it as untested, not as established. (Gone by `bbbc4e70`.)
5. **The eight `(u32)j` casts in this commit were recorded as load-bearing and
   are not.** Retracted in Round 5; replaced by an `int` alias in `bbbc4e70`.
   A reviewer seeing this commit alone should know the casts are not the
   mechanism, and that retail's reason for the split use-set is not established.
6. **The GCSE mechanism behind the `j*30` residue is inference**, not verified in
   the compiler. The *behaviour* is measured; the explanation is a model.
7. **EU and JP ROM builds are expected, not recorded** for this commit. The
