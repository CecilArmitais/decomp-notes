# 1. Shared-type change: `struct unk_0202AAA8` gains four members

`include/main_0202AAA8.h`. Four offsets that were inside `u8` padding arrays
become typed members. **Fact**, the exact edit:

```c
/* before */                    /* after */
    u8 field_0x0[8];                u32 field_0x0;
                                    u8 field_0x4[4];
    u8 field_0xFC[8];               u32 field_0xFC;
                                    s32 field_0x100;
    u8 field_0x108[0x90];           u8 field_0x108[0x58];
                                    u8 *field_0x160;
                                    u8 field_0x164[0x34];
    u8 field_0x1A8[4];              s32 field_0x1A8;
```

### The evidence per member

All **fact**, read off `asm/main_0202AB94.s` (the wip keeps a frozen copy at
`wip/main_0202AB94_all/asm_src/`, since the landing deletes the original).

| offset | new type | instruction that fixes it |
|---|---|---|
| `0x0` | `u32` | `ldr r0,=UpdateSimpleMenu` / `str r0, [r4]` — a 4-byte store of a function address (`CreateSimpleMenuInternal`) |
| `0xFC` | `u32` | `ldr r0,[r4,#0xfc]`, `str sl,[r4,#0xfc]`, tested with `tst #0x800000`, `#1`, `#0x200`, `#0x400000`, `#0x80000000`, cleared with `bic r1,r1,#0x800000` |
| `0x100` | `s32` | `str fp, [r4, #0x100]` — a 4-byte store of the initial selected index |
| `0x160` | `u8 *` | `ldr r8,[r5,#0x160]`, then `ldrb r0,[r8]` / `add r8,r8,#1` — loaded as a word, dereferenced a byte at a time, incremented |
| `0x1A8` | `s32` | `ldr r0,[r4,#0x1a8]` / `cmp r0,#0` / `ble` — 4-byte load, **signed** compare |

**The naming is not invented.** *Fact:* `field_0xF8` and `field_0x104` are
*already* declared `u32` in this struct and are *already* used as flag words, by
`src/overlay_10_022BCC60.c:27,128` and `src/main_020307A4.c:22`. `field_0xFC` is
a third menu kind's flag word at a third offset in the same conflated struct.

### Layout preservation was measured with the real compiler, with a negative control

This is the part that makes the edit safe, and it is the part most worth
copying. **Fact**, `wip/main_0202AB94_all/tools/layout.py`: one compile-time
assertion per member of the form

```c
u32 z_field_0x160(void) { return (u32)&((struct unk_0202AAA8 *)0)->field_0x160 == 0x160; }
```

compiled by **mwccarm** with the preset-101 flags, and the folded constant read
back out of the emitted `mov r0, #N`. Both contexts were probed — the tree's
header as it stood (`ctx_base_NORTH_AMERICA.raw.h`, 28 probes) and the landing
header (`ctx_base_NORTH_AMERICA.h`, 32 probes).

Every run compiles a **negative control** alongside: one probe asserting
`sizeof(struct unk_0202AAA8) == 0x1C9`, which must come back `0`. *(Fact —
`layout.py:56`, `want = 0 if n == "NEGATIVE-CONTROL"`.)* Both runs reported all
probes as expected, control included, so "nothing moved" is an outcome the
harness was demonstrably capable of failing to produce. There is a second
self-check: the tool asserts it read exactly as many constants as it compiled
probes, so a silently-dropped probe is an error rather than a pass.

Result: **`sizeof` is `0x1C8` before and after, and all 30 members sit at the
offsets their names state.**

### Blast radius

* **Fact:** nothing in the tree read any of the four offsets before this commit
  — the union of `field_0x` offsets referenced by every user of
  `struct unk_0202AAA8` was `0x8, 0x20, 0xA0, 0xF8, 0x104, 0x198, 0x19C, 0x1A0,
  0x1A1, 0x1A4, 0x1AC, 0x1B0, 0x1BC, 0x1C0, 0x1C2, 0x1C4` (checked by grepping
  every includer). So the edit cannot change an existing translation unit's
  codegen except through layout, which the probes rule out.
* **Fact:** 20 files include `main_0202AAA8.h`, directly or via
  `include/main_0202C5E0.h`.
* **Fact:** `asm/` never names a struct member, so no asm file needed changing.

### One harness fault worth recording

**Fact**, `wip/main_0202AB94_all/LEDGER.md` §E: `patchctx.py`'s first version
replaced `u8 field_0x0[8];` **file-wide** in the generated context. *Three*

would have been measured against a fiction. It now edits inside the

# 2. Shared-type change: `struct struct_2` moves headers

`struct struct_2` moves verbatim from `include/overlay_31_02382820.h` to
`include/window.h`. **Fact:** the diff is a delete of six lines from one header
and an identical insert into the other — no member, order, type or name change.
The name is pre-existing in `pmd-sky` and is used verbatim per the naming rules.

### Why it had to move

**Fact.** `CreateSimpleMenuInternal` copies its third argument as a **whole
struct**: `ldmia sb!,{r0,r1,r2,r3}` ×9 plus `ldmia sb,{r0,r1}` = 152 bytes,
which is `0x98` after padding. So the parameter needs a type of exactly that
size, and the tree already had one:

```c
struct struct_2 {
    u32 b;        /* 0x0  — the id CreateSimpleMenuInternal matches against */
    u8 PAD1[92];
    u8* c;        /* 0x60 — and 0x100 + 0x60 = 0x160, the byte array sub_0202AF78 walks */
    u8 PAD2[50];
};
```

4 + 92 + 4 + 50 = 150, padded to 0x98 (fact). **Independent corroboration,
fact:** it is the `field_0x1c` member of `ov11_02324D8C`'s struct at
`src/overlay_11_02307334.c:163`, spanning `0x1c .. 0xb4` — 0x98 bytes.

A `src/main_*` file cannot include an `overlay_31` header, so the definition had
to move somewhere both reachable.

### Why `window.h` and not the wip's recommendation

`wip/main_0202AB94_all/STATUS.md` §4.2 recommends `include/main_0202AAA8.h`. The
landing chose `window.h` instead, and the commit message gives the reason:
`main_0202AAA8.h` would have dragged `main_0202AB40.h`'s prototypes into
`src/overlay_31_02382820.c`, where they collide with that file's own
declarations of the same functions.

**That reason is checkable and checks out.** *Fact:* `overlay_31_02382820.c`
still carries `extern void sub_0202AB94(s8, u32);`,
`extern void sub_0202B030(s8);` and
`extern struct struct_1* GetSimpleMenuResult__0202AEA4(s8);` at lines 47/48/50,
all of which now contradict `include/main_0202AB40.h` — see §5.

**And the move is free for that header's consumers.** *Fact:*
`include/overlay_31_02382820.h` **already** had `#include "window.h"` on line 4
before this commit (checked against `76558112^`), so nothing there loses a
declaration.

**Blast radius, fact:** 24 files include `window.h` directly, plus transitive
includers. `struct struct_2` is a new name in that header, not a redefinition —
so the risk is a name collision, not a layout change, and all three builds pass.

**Inference, not fact:** that `window.h` is the *right* long-term home. It is a
menu-configuration block, and `window.h` is where `WindowTemplate` and friends
live, so it is a reasonable place — but this was a reachability decision, not a
taxonomy one, and a reviewer may prefer somewhere else.

# 3. Four data symbols retyped away from `extern s32`

All four had been declared `extern s32 X;` and passed as `&X` to a parameter
declared `void *`. With `CreateSimpleMenuFromStringIds`'s real prototype landing
(`WindowTemplate *`, `struct unk_0202A5CC *`), `void *` is gone and the
declarations had to become honest.

| symbol | was | now | where |
|---|---|---|---|
| `_0209C85C` | `extern s32` | `extern WindowTemplate` | `src/main_0203D538.c:109` |
| `_0209C86C` | `extern s32` | `extern struct unk_0202A5CC []` | `src/main_0203D538.c:110` |
| `ov11_02322CC8` | `extern s32` | `extern WindowTemplate` | `src/overlay_11_02307334.c:192` |
| `ov11_02322CF0` | `extern s32` | `extern struct unk_0202A5CC []` | `src/overlay_11_02307334.c:194` |

### The size evidence — and one arithmetic correction to the commit message

**Fact, the window templates.** `WindowTemplate` is 16 bytes
(`u32` + 4×`u8` + `u8`+`s8`+`u16` + `u32`, `include/window.h:45-55`).
`_0209C85C` runs from its own `.global` to `.global _0209C86C` — `0x0209C86C −
0x0209C85C = 0x10` (`asm/main_rodata_020925A0.s:7072-7077`). `ov11_02322CC8`
runs to `.global ov11_02322CD8` — also `0x10`
(`asm/overlay_11_022ECD24_data.s:1624-1629`). Both are exactly one
`WindowTemplate`.

**Fact, the item arrays.** `struct unk_0202A5CC` is 8 bytes
(`u16` + 2 pad + `s32`, `include/main_0202A66C.h:4-8`). The two symbols measure:

* `_0209C86C` → `_0209C884` = **0x18 = three 8-byte records**:
  `{0x2A7, 0}`, `{0x2A8, 1}`, `{0, 1}`.
* `ov11_02322CF0` → `ov11_02322D10` = **0x20 = four records**:
  `{0x2AF, 0}`, `{0x2AE, 1}`, `{0x2B0, 2}`, `{0, 2}`.

**The commit message says the record counts match "the element counts the call
sites pass". Read literally that is off by one** — the call sites pass `2` and
`3` respectively, and the arrays hold `3` and `4` records. **Fact:** in both
cases the extra record has a zero id.

**Inference, and it is supported by the tree rather than proved here:** the last
record is a terminator. The sibling arrays in the same rodata blocks —
`ov11_02322CD8`, `ov11_02322D10`, `ov11_02322D60`, `ov11_02322D88`, all already
declared `struct unk_0202A5CC[]` before this commit — are passed to
`CreateParentMenuFromStringIds`, which takes **no count at all**
(`src/overlay_11_02307334.c:346,348,350,392,718`), so those arrays must be
self-terminating. Each also ends in a zero-id record (fact, read off the same
`.s`). `CreateSimpleMenuFromStringIds` takes a count *and* the data is
terminated; that is redundancy, not a contradiction, but nothing here proves the
callee actually reads the terminator.

**Fact, blast radius:** each of the four had exactly one user, so retyping them
touched exactly two files.

### The cast that went with them

`src/overlay_11_02307334.c:656` loses a `(s32)`:

```c
/* before */ CreateSimpleMenuFromStringIds(&ov11_02322CC8, 0x33, (s32)&ov11_02324D8C->field_0x1c, &ov11_02322CF0, 3);
/* after  */ CreateSimpleMenuFromStringIds(&ov11_02322CC8, 0x33, &ov11_02324D8C->field_0x1c, ov11_02322CF0, 3);
```

**Fact:** `field_0x1c` was **already** declared `struct struct_2` in that file
before this commit, so the cast existed only to squeeze a pointer through an
`s32` parameter that the real prototype never had. `src/main_0203D538.c:336`
loses an `&` for the same reason — `_0209C86C` is now an array, so it decays.

This is the rule in MEMORY as *fix the declaration, not the cast*, applied: the
cast was a symptom of a wrong declaration two hundred lines above it.

### The sibling that was NOT fixed — flagged, not resolved

**Fact.** `src/main_0203D538.c:110` still reads `extern s32 _0209C884;` and line
256 still reads
`CreateParentMenuFromStringIds(NULL, 0x11, NULL, (struct unk_0202A5CC *)&_0209C884)`.
`_0209C884` sits in the *same* rodata block, immediately after `_0209C86C`, with

It is out of scope in the strict sense — nothing this commit landed forced it —

# 4. Region arms — three shapes in three files, and one that needed its own

Every region delta in the four cleared files is either a **header-driven struct
displacement** (which needs nothing from the C) or a **message id** (which
needs a real arm). **Fact**, asserted per run by each group's `mktarget.py`,
which resolves the `.s` for all three regions and enumerates every differing
line:

| group | EUROPE | JAPAN | what the C needed |
|---|---|---|---|
| `main_0202AB94` | **byte-identical** — the file contains **zero** preprocessor directives | byte-identical | **nothing**; `match.c` carries no `#ifdef` at all |
| `overlay_29_022E7EC4` | byte-identical | 5 lines, all displacements, all in `DisplayTeamStatsSprite` | **nothing** |
| `overlay_29_023055B0` | byte-identical | 15 lines: 10 displacements + **5 message ids** | one `JPN_MSG_OFFSET` block |
| `overlay_29_02314810` | byte-identical | 33 lines: 3 displacements + **13 message ids** + 1 size change | `MESSAGE_ED0/ED1` in `move_orb_effects.c`; five `MESSAGE_*` in `overlay_29_02315118.c` |

The EUROPE assertion is not an assumption in any of the four: each
`mktarget.py` asserts `texts["EUROPE"] == texts["NORTH_AMERICA"]` and fails if
an EU arm ever appears after a sync (fact).

### The case that earned its own arm

**Fact.** In `asm/overlay_29_02314810.s`, eleven of the thirteen JP message ids
shift by `-0x2C0` — which is exactly `src/move_orb_effects.c`'s **existing**
`JPN_MSG_OFFSET`, so those are spelled `0xNNN + JPN_MSG_OFFSET` and cost
nothing. **The two `TryInflictGrudgeStatus` ids shift by `-0x2BE` instead**
(`0xED0 → 0xC12`, `0xED1 → 0xC13`), which `JPN_MSG_OFFSET` cannot express. They
landed as named defines in both arms of the file's existing block:

```c
#ifdef JAPAN
#define JPN_MSG_OFFSET -0x2C0
#define MESSAGE_ED0 0xC12
#define MESSAGE_ED1 0xC13
#else
#define JPN_MSG_OFFSET 0
#define MESSAGE_ED0 0xED0
#define MESSAGE_ED1 0xED1
#endif // JAPAN
```

**This is guarded against a later "simplification", which is the durable part.**
`mktarget.py` asserts per run that `MESSAGE_ED0/ED1` do **not** follow the flat
shift and that the other named ids **do** — so if someone folds them into
`JPN_MSG_OFFSET`, the harness fails rather than the ROM (fact, recorded in
`wip/overlay_29_02314810_all/STATUS.md` §5).

**One size difference, and only one.** *Fact:* `TryInflictGrudgeStatus` is **4
bytes longer in JAPAN**, because `0xED0` is ARM-encodable as an immediate but
`0xC12` is not, so JP spends an extra literal-pool word. The address walk
asserts exactly that `+4` and no other size change anywhere in the file.

### The third shape: named defines with no offset constant

`src/overlay_29_02315118.c` has no `JPN_MSG_OFFSET`, so its five ids landed as a
`#ifdef JAPAN` block of `MESSAGE_CFE`…`MESSAGE_DBA`. **Fact:** those five *do*
follow the flat `-0x2C0`; they are named rather than offset only because of
which file they land in, and the tree's precedent for such a file is
`src/overlay_29_0231EDD8.c:23` and `src/overlay_29_02311010.c:38`.

**The alternative was not falsified, just not chosen** (`LEDGER.md` §4 of that
group): defining a second `JPN_MSG_OFFSET` in that file would compile to the
same bytes. It was rejected because it puts two copies of one magic number in
the tree that must stay in sync. A reviewer may prefer it; nothing breaks.

**Every id literal was scraped by the tooling out of that region's own resolved
pool words / immediates**, not typed by hand (fact). The macro names carry the
NA literal and nothing else, deliberately, since the message text is unknown.

### Region *scoring* coverage is uneven — the honest record

* `main_0202AB94` — **NORTH_AMERICA only.** No EU or JP context was ever built.
  The case rests on the "zero preprocessor directives, all three texts
  byte-identical" assertion plus the builds.
* `overlay_29_022E7EC4` — **25/25 score 0 in all three regions.**
* `overlay_29_023055B0` — **4/4 score 0 in all three regions**, twice over:
  against the model context, and again against the *real preprocessed landed
  translation unit* (§6 below).
* `overlay_29_02314810` — **NORTH_AMERICA scores only.** Its EU/JP evidence is
  stronger than a score instead: a byte-level object comparison against the real
  assembler in all three regions (§6).

The three matching builds are what settle all three regions. The scratch scores
are the stronger evidence only where they exist.

Both files that lost the `main_0202*` declarations **already included** the
headers that now carry them (`main_0202AB40.h`, `main_0202B4C4.h`), so five of
the nine needed no new `#include` at all (fact). Three needed one added; one —
`TryActivateQuickFeet` — is in the *same* translation unit as its own new

### Two of them a build genuinely could not have caught, and one it must

**Fact.** `extern void TryActivateQuickFeet(...)` sat in `src/move_orb_effects.c`
itself, i.e. the same TU as the `bool8` definition being appended. That is a
hard compile error, measured before landing:
`src\move_orb_effects.c:41: … redeclared` (`altcheck.sh`, real flags with
`-W error`).

**The other eight never meet their definitions.** Two declarations in two
translation units never collide, every affected caller ignores the return value
or passes a literal, and the ROM matches either way. *Fact:* the three
overlay_29 caller swaps were shown byte-neutral by compiling each file twice —
tree version and swapped version, real build rule — and comparing every function
in the object: **identical in all three regions** (`objcheck.sh` step [3]).

### Why the return-width errors matter even though nothing broke

**Fact:** a declared `s8` return makes the *caller* sign-extend `r0`. So
`extern s8 CreateSimpleMenuFromStringIds(...)` is not cosmetic — it changes
codegen in whichever object holds it. The three sites that were fixed all
happen to be byte-neutral (measured, and the builds agree), but the class of
error is one where a fix can move bytes, which is exactly why
`wip/main_0202AB94_all/STATUS.md` §7 recommends landing the definitions first
and doing the declaration swaps as a separately-built step.

### The four that were deliberately left — and the contradiction one of them creates

**Fact**, still in the tree at `76558112`:

| file:line | declaration | contradicts |
|---|---|---|
| `src/overlay_31_02382820.c:47` | `extern void sub_0202AB94(s8, u32);` | `include/main_0202AB40.h:10` — `(s32, s32)` |
| `src/overlay_31_02382820.c:48` | `extern void sub_0202B030(s8);` | `include/main_0202AB40.h:14` — `(s32)` |
| `src/overlay_31_02382820.c:50` | `extern struct struct_1* GetSimpleMenuResult__0202AEA4(s8);` | `include/main_0202AB40.h:11` — `s32 (s32)` |
| `src/overlay_25_init.c:40` | `extern s8 CreateSimpleMenuFromStringIds(void*, s32, s32, void*, s32);` | `include/main_0202B4C4.h:9` — `s32 (WindowTemplate *, u32, struct struct_2 *, struct unk_0202A5CC *, s32)` |

**The third one is not just a width disagreement — the tree now says this
function returns two different kinds of thing.** *Fact:*
`src/overlay_31_02382820.c:221` assigns its result straight into
`OVERLAY31_UNKNOWN_POINTER__NA_238A260[1]`, a pointer. *Fact, from the
function's own body:* the epilogue is `mov r0, r6` where `r6` is
`NewWindowScreenCheck`'s result, with no truncation or sign-extension, and the
value ultimately comes from `struct unk_0202A75C::field_0x100`, an `s32` — which
is why the header says `s32`.

**Inference:** the overlay_31 declaration is a call-site guess that happens to
work because a 32-bit value is a 32-bit value, and the "pointer" is being used
as an index or handle. **Not checked**, and a reviewer should not take my
reading of it as settled. What *is* settled is that the two declarations
disagree, they are in different translation units, and no build will ever say
so.

**Why they were left:** including `main_0202AB40.h` in `overlay_31_02382820.c`
would be a conflicting redeclaration under `-W error` (a compile error, not a
silent difference), so fixing them means editing that file's own code and

A decomp.me score is one function compiled without any of the build's `-W`
flags. Three of the four groups closed part of that gap without running a ROM
build. **This section is about what those checks do and do not support.**

### `overlay_29_02314810` — byte-level object comparison, all three regions

**Fact.** `tools/objcheck.sh` compiles the landing-shaped files with the real
flag set (`-O4,s … -W all -W pedantic -W noimpl_signedunsigned -W noimplicitconv
-W nounusedarg -W nomissingreturn -W error`), assembles the untouched
`asm/overlay_29_02314810.s` with the real assembler for the same region, and
compares:

| region | pre-existing fns in the merge targets | the 9 new bodies vs the assembled asm | caller swaps |
|---|---|---|---|
| NORTH_AMERICA | 16 + 2, byte-identical | all 9 **byte-identical** | 3 files, byte-identical |
| EUROPE | 16 + 2, byte-identical | all 9 **byte-identical** | 3 files, byte-identical |
| JAPAN | 16 + 2, byte-identical | all 9 **byte-identical** (grudge 33 words vs NA's 32) | 3 files, byte-identical |

NA-assembled target — **fails**, on 4 words of `TrySealMove`: the

comparison that cannot fail proves nothing; this one demonstrably sees a region
difference.

**Shared-header blast radius, fact:** `tools/includers.sh` compiles all **38**
other `.c` files that include either changed header, twice each, and compares
every function. **38 × 3 regions, all byte-identical.**

### `overlay_29_023055B0` — the landed translation unit re-scored

**Fact.** `tools/compilecheck.sh` compiles the finished `.c` under the real
`-W error` set: **COMPILE OK in all three regions**. Then `mkctx_landed.sh` runs
the real compiler's `-E` over the landed file and `land_score.py` re-scores each
function against its target from *that*: **0/0/0/0 in NA, EU and JP.** This
removes the model — what is scored is exactly what the real include set
produces, so an `#include` pulling a declaration that differs from `ctx_extra.h`
cannot hide.

**Negative controls, fact:** changing `IqSkillIsEnabled(entity, IQ_ABSOLUTE_MOVER)`
to `(entity, 13)` makes `compilecheck.sh` fail with
`illegal implicit conversion from 'int' to 'iq_skill_id'` — the exact trap a
scratch cannot see. And changing a call site from `ov29_023055B0(0)` to `(1)`
makes `objcheck.sh` report `DIFFERS`.

### What none of it proves

* **Link-time placement.** Every check is per-object. That the bodies land at
  the right ROM addresses with `main.lsf` correct is only settled by the build.
* **The other ~2000 objects.** Only the rewritten files and the includers of
  changed headers were recompiled.
* **`main_0202AB94` and `overlay_29_022E7EC4` had none of this.** Those two
  groups rest on scratch scores plus a hand audit of the `-W` flags. The
  matching builds are what carry them.

### Two harness failures worth carrying forward

Both produced a **plausible wrong answer**, which is the dangerous kind.

**1. A comparison that was reading a compiler serial number.**
`includers.sh` reported `WeightWeakTypePicker` in `src/dungeon_damage.c` as
changed by the added prototypes. A 20-variant bisect said **every** variant with
≥1 added prototype differed, at any position and any count — which already
smelled wrong for a colouring tie-break. **Diagnosis, fact:** exactly one word
of 246 differed and the *instruction* was identical (`00000000` both sides).
Only the **relocation's symbol name** moved: `R_ARM_ABS32 @2529` vs `@2504` —
MWCC's own names for an **anonymous local** data object, both `STB_LOCAL`,
`STT_OBJECT`, size 16, alone in their section, both sections the same 16 bytes
`00 00 00 00 01 00 00 00 02 00 00 00 04 00 00 00`. The linker discards local
names. **The landing did not change that file; the tool was wrong.**

The fix is the durable part: `objcmp.py` now compares two differently-named
relocation targets by resolving both symbols and comparing
`(value, size, section bytes, section relocations)` — so a relocation retargeted
at a *different* local table is still a difference. **Exempting "any name
starting with `@`" would have hidden exactly the bug the tool exists for.**

**2. `mwasm` mapping symbols are typed `STT_FUNC`.** `objcmp.py` resolved an
intra-object `bl` by taking the first `STT_FUNC` symbol at the target address
and got `$a` — ARM's code/data mapping symbol — instead of the function name.
The tell was that `TrySealMove`'s call to
`ExclusiveItemEffectIsActiveWithLogging` failed while its call to
`TryActivateQuickFeet` eight words later passed: same code path, opposite
answers. Fixed by returning the *set* of names at that address and dropping
`$`-prefixed ones.

**3. A context containing a function DEFINITION reports a bogus score.**
(`wip/overlay_29_023055B0_all/LEDGER.md` L11.) Scoring the four functions against
the preprocessed landed TU with the context cut *immediately above each
definition* gave **900 / 6600 / 16200 / 20600** — because the context still held
the earlier definitions, so the object carried several functions and decomp.me
diffed all of them against a single-function target. Cutting at the **first**
definition gives 0/0/0/0. `land_score.py` now asserts that cut. The same effect
is why every group scores each function in **its own** scratch and never against
a concatenated target.

**4. `set -o pipefail` reported a working negative control as broken.** (L13.)
`compilecheck.sh` exits non-zero *because* it detected the injected defect, and
`pipefail` handed that status to `if`, so a matching grep still read FAIL. Both
controls reported FAIL for a full `verify.sh` run while being perfectly
functional. **A check whose *pass* path is untested is worth no more than one
whose fail path is.**

# 7. The matching findings — what actually closed each function

Only the ones that generalise. Every score is NORTH_AMERICA, `mwcc_30_137`,
preset-101 flags; **the flags were never varied in any group, not even to test
one** (fact, stated in all four ledgers).

### The transferable one: an undeclared trailing parameter is invisible at the call site

`UpdateParentMenu`, stuck at **15** with `STRUCT 0 + COLOUR 3` and an exactly
matching instruction count. The whole difference was three rows, one value:

```
base  1fc: ~> ldr r1, [sp, #8]     cur  1fc: ~> ldr r0, [sp, #8]
base  200:    tst r1, #1           cur  200:    tst r0, #1
base  26c: ~> tst r1, #2           cur  26c: ~> tst r0, #2
```

**What closed it, fact:** `sub_0203250C` takes **two** arguments. Its body
(`asm/main_02030A90.s`) opens `ldr r3, [r0, #0x10]` and then tests `r1` —
`tst r1, #0x1000`, `tst r1, #0x2000`. The call site sets up *neither* register
(`r0` was computed before the branch, `r1` has held the button word since
`0x1fc`), so the second argument costs **zero instructions** and is completely
invisible from the call site. Declaring it and writing
`sub_0203250C((void *)menu + 4, buttons)` pins the word to `r1`. **15 → 0.**

**What it cost to find, fact:** 30 source-level variants (`cand/upm_v*.c`) —
every declaration permutation, case-scope declarations, named temporaries for
the tested value and for three different call results, six condition spellings,
`int` vs `s32` vs `u32`, three address spellings of `menu + 4`, a merged
`u32 st[10]`, an inverted ladder — **all 15, all `r0`**. None of it could reach
the answer, because the answer was not in this function's source.

**The two diagnostics that ended the search** are the method worth copying:

1. **Strip the upstream.** `upm_v45.c` (cases 0–3 deleted) and `upm_v46.c`
   (case 4 alone) both still produced `r0`, ruling out every other cause in two
   compiles.
2. **A 20-line minimal reproduction** (`cand/min1.c`) reproduced the exact
   `ldr r0, [sp]` / `tst r0, #1` / `tst r0, #2` shape, and seven variants on it
   — including a ladder with **no calls at all in any arm** — were all `r0`.
   That last is the useful fact: **MWCC's choice here is not about call
   clobbering.**

**Generalisation:** when a value is already sitting in a register at a `bl` and
the call site sets up fewer argument registers than its position implies, **read
the callee's body**. Also in `docs/MATCHING_TIPS.md`.

### A 2-case `switch` will not produce retail's jump table; naming every enumerator will

`CheckNonLeaderTile`, **1105 → 0**, everything else already byte-identical.
A two-case `switch` over `enum entity_type` emits a compare chain
(`cmp r0,#2 / beq / cmp r0,#3 / beq`); retail has a 7-slot table
(`cmp r0,#6 / addls pc, pc, r0, lsl #2`). **What closed it, fact:** naming every
enumerator, including the ones whose body is empty. Value 4 has no enumerator,
and it is exactly the slot the table fills with `default`.

**This is the converse of an existing `MATCHING_TIPS.md` warning** ("adding a
contiguous run of cases goes too far — it tipped into a jump table"). Here the
jump table is what retail has, so the run is the fix. The lever is real and runs
both ways.

### The cheaper layout is evidence against your source shape

`DisplayTeamStatsSprite`, the last **335 → 0**. The candidate if-converted a
one-statement `if` arm into `moveq r6, #0` before the branch, then fell through
— **one instruction cheaper than the target**. That is the tell. Inverting the
condition so the long body is the `if` and the one-statement arm is the `else`
puts the short arm out of line past the whole then-block, with the then-block
ending in `b <join>` — exactly the target. **Score 0.**

**Fact:** MWCC lays the arms out in **source order**. `MATCHING_TIPS.md` already
frames this as a polarity lever rather than a one-way "write the failure arm
first" preference; what this confirms is that **reading the polarity off the
target's `b <join>` + out-of-line block is enough to pick the direction on the
first try.**

### Statement order inside a predicated block colours, it does not schedule

`EndNegativeStatusCondition`, **65 → 0**, 0 structural + 12 colour rows. The
block is if-converted to `tst / bicne / movne / movne / strhne`. All six
permutations of the three source statements were measured:

| source order | score |
|---|---|
| `bic`, `result`, `log_sealed` | 65 |
| `bic`, `log_sealed`, `result` | 75 |
| **`result`, `bic`, `log_sealed`** | **0** |
| **`result`, `log_sealed`, `bic`** | **0** |
| `log_sealed`, `bic`, `result` | 10 |
| `log_sealed`, `result`, `bic` | 10 |

**Fact:** the emitted order stays `bic / mov / mov / strh` in every variant —
MWCC schedules the block its own way and only **colours** in source order.

Two related facts from the same function. **Declaration order closed exactly
half the colouring** (340 → 265, 24 colour rows → 12) by moving one local, and
did nothing to the other pair — so the residue was *two* problems, and the
additivity showed as an exact halving. And **five different spellings of an
explicit temporary were all byte-identical at 65**, so the temporary was not the
lever in that shape.

### Three smaller levers, each one edit

* **`*p++` folds to a post-indexed load; retail does not fold it.**
  (`sub_0202AF78`.) `ldrb r0, [r8], #1` vs the target's `ldrb r0, [r8]` +
  `add r8, r8, #1`. **Writing the read and the increment as two statements does
  not help** — `v = *p; p++;` still folded (measured). Moving `p++` **below the
  `if` that reads `*p`** unfolded it; the scheduler then hoists the `add` back
  between the load and the `tst` to cover the load-use stall, reproducing the
  target exactly.
* **Zero-constant reuse follows SOURCE order, not scheduled order.** Same
  function, residual score 10. `i = 0;` written *before* a `p = NULL` if/else
  gave the immediate to the wrong variable; the scheduler had already moved
  `mov r7, #0` up into a stall slot, which made the *emitted* order misleading.
  Moving `i = 0;` below the if/else — **no instruction moves** — swapped which
  zero got the immediate. 10 → 0.
* **MWCC gives the first-declared aggregate the highest stack address.**
  (`CreateSimpleMenuInternal`, 2066 → 0 with two edits.) The target has `tmpl` at
  `sp+0x1C` and `rect` at `sp+0xC`; declaring `tmpl` first fixes nine rows at
  zero instruction-count delta. Note the rule reads as violated if you include
  scalars in the sort — `count` sat at `sp+8` regardless of where it was
  declared.

### Two return-type facts that are easy to get backwards

**Fact, measured in `EndNegativeStatusCondition`:** in this toolchain a
**locally computed** `bool8` is tested with `tst rX, #0xff`, while a **word** is
tested with `cmp rX, #0`. That is what settles the return type as `s32` here
(`mov r0, r4` where `r4` is tested `cmp r4, #0`), and it agrees with the two
pre-existing in-tree declarations.

**The caveat, also measured, so this is not over-generalised:** a `bool8`
arriving **through the ABI** — a parameter, or a `bl`'s return value — *is*
tested with `cmp rX, #0` too. **The `tst #0xff` signal only distinguishes a
local byte from a local word.** So `bool8` vs `s32` on a *parameter* is not
pinned by the asm at all; several parameters in `overlay_29_023055B0` are typed
`bool8` from the *callers'* `ldrb`, which is real evidence of byte width but not
proof of the declared type, and every one is byte-identical either way.

### Where nothing was falsified, said plainly

* **`overlay_29_022E7EC4`: 24 of 25 functions reached score 0 on the first
  compile.** *Inference on why, and it is the group's own reading:* the shared
  declarations were pinned before any C was written — the five repeated
  overlay-10 entry points, `struct unk_022DC694` (already in-tree, and its 0x14
  size matches a `sub sp, sp, #0x14` in four different bodies), and the
  per-offset widths of `struct unk_02353554` read off each `strb`/`str`/`ldrsh`.
* **`overlay_29_02314810`: all nine were already at score 0** when the session
  opened the wip; a previous pass had matched them. That group's work was
  verification, not search — which is why its ledger is short on "tried X,
  scored Y" and long on landing and tooling.
* **`ov29_023055B0` and `ov29_02305814` both reached 0 on the first candidate
  compiled.** Recorded so nobody assumes a search happened.
* **A harness fault, not a C question:** `ov29_023055B0` would not compile at
  first because `DUNGEON_MAX_POKEMON` and `DIRECTION_MASK` are object-like
  macros that `mkctx.sh`'s `-E` had eaten.

Every landed file compiles clean under the real
`-W all -W pedantic -W noimpl_signedunsigned -W noimplicitconv -W nounusedarg
-W nomissingreturn -W error` set, so none of these is a warning the build
rejects. They are listed because a reviewer might prefer a different underlying

### Four casts that each stand in for a type decision not taken

1. **`*(u8 *)&menu->field_0x1B0`** (`src/main_0202AB40.c:182`). *Fact:* the
   parent menu and the simple menu genuinely disagree about the width at 0x1B0.
   Byte: `ldrb [r4,#0x1b0]` here, `strb [r4,#0x1b0]` in `CreateParentMenuInternal`
   and `CreateParentMenuWrapper`. Word: `str r2, [r4, #0x1b0]` in

   and cast at the one byte read, so no landed file changed.
2. **`*(struct struct_2 *)&menu->field_0x100`** (`src/main_0202B4C4.c:167,181`).
   *Fact:* `menu + 0x100` is where the `struct struct_2` argument is copied, and
   `InitWindowInput` is handed the same address (`add r2, r4, #0x100`). It cannot
   simply *be* a member at 0x100, because the struct spans `0x100..0x198` and
   `src/main_020307A4.c:22` already reads `w->field_0x104` — an offset inside it
   — through this same type. **Note the interaction with §1:**
   `menu->field_0x100 = sel;` on the very next line overwrites the first word of
   the copy, which is why `field_0x100` has to exist as an `s32` member *and* be

3. **`(s32) TOP_SCREEN_STATUS_PTR->field_0xb8`** (`src/overlay_29_022E869C.c:69,128`).
   `ov29_022DC694` / `ov29_022DC738` are declared taking `s32 a` in

   call site was chosen over widening the header's parameter, which would cascade

4. **`(s16) entity->sprite_index`** (`src/overlay_29_022E869C.c:191`). *Fact:*
   `entity::sprite_index` is `u16` in `include/dungeon_mode.h`, so the plain read

### The conversions left in place

* **`(u32)UpdateSimpleMenu`** (`src/main_0202B4C4.c:128,164`) — a

* **`(void *)menu + 4`** — `void *` arithmetic, a GNU extension enabled by

  `src/main_0202B4C4.c:38,43` already do `GetWindowContents(window_id) + 4`.
* **`sub_020263C8`'s fifth parameter is `u8` and the local is `s32`, and that is
  load-bearing.** *Fact, measured:* with a word parameter and a `u8` local MWCC
  elides the `and r1, sb, #0xff`, because it can prove `0x42`/`0x44` is in range.
  Byte parameter + `s32` local reproduces the mask. The obvious first guess —
  `u8` local, `u32` parameter — was measured and does **not** produce it.
* **Narrowings with in-tree precedent**, all silenced by `-W noimplicitconv`:
  `u8 cringe_turns = CalcStatusDuration(...) + 1` (precedent
  `src/move_orb_effects.c:594`), `u8 terrified_turns = ov10_022C4618` (precedent
  `src/overlay_29_02311010.c:355`), `tmpl.x -= tmpl.width`,
  `female = GetPlayerGender() == 2`.
* **Signed/unsigned mixes**, silenced by `-W noimpl_signedunsigned`:
  `menu->field_0x1A4 = buttons;` (`s32` lvalue, `u32` value, ×3),
  `w->unkB8 = -1/-4/-5;` (`u32` lvalue, negative int),
  `menu->field_0xFC &= ~0x800000;`.

**Both traps that cost earlier batches a cycle are absent by construction**
(fact, audited per group): no integer literal is assigned to an enum-typed
lvalue, and no narrower type is passed to an enum-typed parameter. In

(`IQ_ABSOLUTE_MOVER`, `IQ_TRAP_SEER`, `ABILITY_KLUTZ`, `ITEM_MOBILE_SCARF`), and

**One spelling a reviewer may want to change, flagged not fixed.**
`overlay_29_022E869C.c` compares four enum-typed status fields against integer
literals — `frozen_class_status.freeze == 1 / == 6 / == 2`,
`burn_class_status.burn == 4`, `invisible_class_status.status == 1`. These are
*comparisons*, never assignments, so not the trap above. Integers were used
deliberately (naming was not the job) and substituting the `STATUS_*`
enumerators later is byte-neutral, since the widths come from the header.
Contrast `TryInflictTerrifiedStatus`, which writes `terrified = 1` rather than
`= TRUE` **because** `monster::terrified` is declared `u8`, not `bool8`, and the
header's own comment says the field takes values other than 0/1.

**Method**

* **`objcheck.sh` / `includers.sh` are generic and were only pointed at one
  group.** Running them against the other three wips would catch the same class
  of landing defect there. The `--subset` handling and the local-symbol
  comparison are the two pieces that make them work on a merge rather than a
  straight before/after.
* **`main_0202AB94` and `overlay_29_022E7EC4` have no object-level check at
  all** — their `-W error` exposure was audited by hand, not compiled. The
  builds are what carry them.
* **Nothing in any of the four wips ever varied a compiler flag**, in either
  direction, at any point (fact, stated in all four ledgers). No diff in this
  batch produced a mechanism that pointed at a named flag.
