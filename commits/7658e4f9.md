## Shape of the batch

**Fact.** Fifty functions, located as five groups of ten *before* any matching
was attempted, then all fifty matched, then **one** build, then one commit.

**Fact.** None of the fifty carries a region conditional — checked per function,
not per file, which matters here: five of the nine source files contain
`#ifdef JAPAN` somewhere, but none of it falls inside a block taken by this
commit. US alone therefore verifies it.

**Fact.** Every group was chosen as a *contiguous run at a file boundary* (head
or tail), so `extract_function.py` merges each function into an adjacent source
instead of splitting a `.s`. That was deliberate: the eleven preceding cleanup
sweeps exist to undo exactly the fragmentation a careless 50-function batch
would create.

## The interworking tail-call veneer

**Fact, and the finding that gated the batch.** Twelve of the fifty are veneers
of the form

```asm
	ldr ip, _0233CA90 ; =MemZero
	ldr r0, _0233CA94 ; =ov06_0233EEE0
	mov r1, #0xc
	bx ip
```

**Fact.** That comes straight out of an ordinary forwarding call — no special
spelling, no attribute:

```c
void ov06_0233CA80(void)
{
    MemZero((u8 *) &ov06_0233EEE0, 0xC);
}
```

MWCC turns a call in tail position into `ldr ip, =f; bx ip` under
`-interworking`. It also survives argument shuffling (`GenerateStandardItem`
reorders three arguments into `GenerateItem`'s four and still tail-calls) and a
computed argument (`sub_020483B8` loads a struct field first).

**Inference, and why this was worth proving before writing forty-nine other
candidates.** Nothing in the tree had a veneer decompiled — grepping `src/` for
"Veneer" returns only *call sites* — so the shape was unverified. Had it needed
something exotic, a quarter of the batch would have been unlandable.

**Fact.** The veneers' *parameter lists* are guesses. Since a veneer forwards
registers untouched, the emitted code is identical for any arity, so the match
constrains nothing. Arity was read off each target's asm by a read-before-write
scan of `r0`–`r3`; the widths are all `s32` placeholders. See the open questions.

## `sub_020483D8` — the register allocation was the evidence

**Fact.** The obvious reading scored a stable **40** across five spellings
(direct `if`, `!= 0`, early return, a result local, a pointer local):

```
T   c: ldrne r1, [pc, #0x10]     C   c: ldrne r0, [pc, #0x10]
T  10: movne r2, #0              C  10: movne r1, #0
```

Everything is correct except that the target uses `r1`/`r2` where the candidate
uses `r0`/`r1` — the target never reuses `r0` after the call.

**Inference that closed it.** A register the compiler declines to reuse is a
register that is still live. `r0` holds the call's return value, and the only
thing that keeps it live to the end is the function **returning** it:

```c
bool8 sub_020483D8(void)
{
    bool8 ok = sub_0204771C();

    if (ok) {
        _020AFEF4->field_0x31B2 = 0;
    }

    return ok;
}
```

Score 0. The epilogue is `ldmia sp!, {r3, pc}` with no `mov r0, …` because the
value is already in place, which is why the return is invisible in the asm and
easy to miss.

**Fact.** `s32` and `bool8` both score 0; `bool8` was chosen to agree with the
declared return type of `sub_0204771C`.

## Two type corrections found by probing

**Fact.** `AreOrbsAllowed` and its two siblings compare the dungeon id
**unsigned** — the target branches `bcc`/`blo`, and a signed parameter emits
`blt` and scores 200. The parameter is `u32`.

**Fact.** The ten register setters need a **`u32`** intermediate. Spelled with a
`u16` local — the natural choice, since the register is 16-bit — MWCC inserts a
`lsl`/`lsr` pair to truncate and the function scores 615:

```c
/* 615 */                                  /* 0 */
u16 v = (*(vu16 *) A & ~0x3F00) | ...;     u32 v = (*(vu16 *) A & ~0x3F00) | ...;
```

The store is `strh` either way; the truncation the `u16` local forces is what
the target does not have.

**Fact.** The two register-setter shapes differ in whether the address is
materialised once or twice, and that follows from the source: the simple form
written as one expression reuses one register, while the flag form (which needs
a statement between the read and the write) loads the pool entry twice. Both
score 0 as written.

## Four landing failures — two of them a repeat

**Fact.** All fifty scored 0 and landed. The build then failed **four times**,
and not once because a candidate's C was wrong:

1. **Truncated includes.** The spec generator built include names with
   `x[len('#include "'):-2]`, stripping the closing quote **and the `h`** —
   `#include "main_0202AAA8."` in ten files. A plain bug.
2. **`GenerateItem` redeclared.** `GenerateStandardItem` merged into
   `overlay_29_02344BE4.c` *above* the `extern void GenerateItem(...)` that file
   already carried for `GenerateCleanItem`.
3. **A cleanup regex that overreached**, removing unused `ATK_STAT_IDX`
   declarations from **eleven files unrelated to this batch**. Each removal was
   correct in isolation; in a fifty-function commit it is scope creep. Reverted.
4. **`PlaySeByIdVolume` redeclared.** `src/main_02017C80.c` already declared it
   `(s32 se_id, s32 volume)`; this commit added `(u16 se_id, …)`. Re-scored
   against the tree's `s32` spelling, both affected functions still match, so
   the tree's declaration was kept and this commit's dropped.

**Failures 2 and 4 are not new.** The landing script inserting an `extern` that
the destination file already declares in another spelling is recorded on
[`901ba2aa`](901ba2aa.md) (`IsCurrentMissionTypeExact`) and again on
[`ba4d07a4`](ba4d07a4.md) (`struct StatIndex`). Writing it down twice did not
stop it happening a third and fourth time, because the cause is in the tool:
its guard was an exact string comparison, so a declaration spelled *differently*
sailed past it.

**The actual fix, applied to the tooling rather than to a note.** The landing
script now extracts the declared symbol from each `extern` it is about to insert,
searches the destination file for any file-scope declaration of that symbol, and
refuses to add a second one — printing what it found so the disagreement is
visible rather than silent:

```
  SKIP PlaySeByIdVolume    already declared as: void PlaySeByIdVolume(s32 se_id, s32 volume);
```

**Fact worth keeping about the mechanism**, since it makes the error message
misleading: a function appended at a file *boundary* can land above a mid-file
`extern` it needs. The call then compiles against an implicit `int (...)` and the
collision is reported as a *redeclaration* of the later, correct line — so the
error points at the good declaration, not the new code.

**What this stress test measured.** The batch size did not make the *matching*
harder — all fifty matched, forty-nine on the first candidate. It made the
*landing* harder. But three of the four failures were tooling that a five-function
batch would have survived only because a human reads five landed files and does
not read fifty; the fourth was a check run too narrowly. Scale exposed them; it
did not cause them.

## Open questions for a reviewer

1. **The twelve veneers' signatures.** Arity was inferred from each target's asm
   by a read-before-write scan of `r0`–`r3`; widths are `s32` placeholders. The
   match cannot confirm any of it, because a veneer forwards registers untouched
   and emits the same code for any signature. `sub_02018460` in particular showed
   `r0`, `r1`, `r3` live and `r2` not, which is not a legal AAPCS argument
   pattern — it is declared with four parameters on the assumption that `r2` is
   overwritten before use, and that assumption is unverified.
2. **`PLAY_TIME_SECONDS`** is declared `extern u8 []` and passed by decay to
   three timer functions. It is almost certainly a struct; nothing here shows
   its shape.
3. **The register addresses** in G2 are bare literals (`0x0400004A` etc.). The
   tree has no named constants for the 2D engine registers; whether it should is
   a separate question.
4. **`ov10_022C6C75`/`77`/`78`/`79`** are four byte columns of one 12-byte-stride
   table, the same shape as `_022A37AC` in [`4d2a484c`](4d2a484c.md). Left as
   four `extern u8 []`s rather than inventing the struct.
5. **`sub_020483D8`'s return value** is used by no caller that was read. The
   return is inferred from register liveness alone.
