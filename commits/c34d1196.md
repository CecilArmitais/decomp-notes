## `--n != 0` fuses to `subs` only on an unsigned counter

**Fact, and the finding worth carrying forward.** The two 8-byte copy loops
(`sub_0206C144`, `sub_0206C164`) sat at **505** through four loop spellings. The
target is:

```asm
	mov r2, #8
_0206C14C:
	ldrb r1, [r3], #1
	subs r2, r2, #1
	strb r1, [r0], #1
	bne _0206C14C
```

Every `s32` counter produced a separate `sub` **and** a `cmp`. The only change
that closes it is the counter's *signedness*:

```c
/* 505 */                      /* 0 */
s32 n = 8;                     u32 n = 8;
do { *dst++ = *src++; }        do { *dst++ = *src++; }
while (--n != 0);              while (--n != 0);
```

**Inference.** On a signed counter MWCC must preserve overflow semantics that the
flag-setting form would not give it, so it declines to fuse; unsigned wraps
predictably and the fusion is safe. Not verified beyond the observation.

**Fact.** A struct assignment through a cast —
`*(struct unk8 *) dst = *(struct unk8 *) _020B0B74;` — also scores 0. The loop
was kept because it needs no new type. **Falsified** (670–730): a pointer-bound
loop (`while (src != end)`) and an index loop (`for (i = 0; i < 8; i++)`), both
of which restructure the loop entirely.

## `EntryOverlay13` is called with an argument it does not take

**Fact.** `ov11_0230CB88` saves `r0` into `r4` across the `InitMenu` call and
restores it immediately before `bl EntryOverlay13`:

```asm
	mov r4, r0
	ldr r0, _0230CBAC ; =OVERLAY11_OVERLAY_LOAD_TABLE
	bl InitMenu
	cmp r0, #0
	ldmeqia sp!, {r4, pc}
	mov r0, r4
	bl EntryOverlay13
```

**Fact.** `EntryOverlay13` is **already decompiled and matching** in this tree, in
`src/overlay_13_EntryOverlay13.c`, as `void EntryOverlay13(void)`.

**Fact.** Calling it with no argument scores **220** — the `mov r4, r0` and
`mov r0, r4` both disappear. Declaring it locally as `extern void
EntryOverlay13(s32 a);` and passing the argument scores **0**.

**Inference.** Retail's *caller* had a prototype that its *definition* did not
match. That is legal and invisible across translation units — the compiler never
sees both — and it is the same mechanism behind every stale provisional
declaration this branch has had to retire, occurring here in the original source
rather than in the decompilation. Reproducing it requires the two declarations to
disagree, so `src/overlay_11_0230CB88.c` carries its own `extern` and does not
include `overlay_13_EntryOverlay13.h`.

**This one should be flagged to a reviewer**, because it is the only place in
this branch where two declarations of one function are deliberately in conflict.
The alternative — changing `EntryOverlay13`'s definition to take an ignored
parameter — was not attempted and might also match; it would touch an
already-landed function, which is why it was left alone.

## Two 64-bit returns, identified by a no-op

**Fact.** `Dwci_Acc_GetUserId` and `Dwci_Acc_GetFriendKey` end with a pair of
instructions that do nothing:

```asm
	orr r1, r1, #0
	orr r0, r0, #0
```

**Inference.** That is MWCC assembling a `u64` return value across `r0`/`r1`;
the `orr … #0` pair is the register-pair move it emits and then fails to
eliminate. Reading these as two separate `u32` returns would miss it entirely.

**Fact, corroborating.** `GetUserId`'s high half is `field_0x0 & 0x7FF`, and
`Dwci_Acc_SetUserId` passes that same `0x7FF` as the mask argument to
`Dwci_Acc_SetMaskBits` — the getter and setter agree on the field width without
either being consulted for the other.

## Landing: the three recurring failures are gone

**Fact.** The previous two 5×10 batches failed to build four times each, always
in tooling. This batch failed **once**, and not from any of those classes:

- **Externs sprayed across files** — fixed in `land2.py` *before* this batch:
  each function's externs are now filtered to the symbols its own signature and
  body mention. The landing output shows every G4 and G5 function skipping the
  7–8 externs it does not use.
- **Duplicate declarations in another spelling** — the guard repaired on
  [`e865b697`](e865b697.md) (it had contained a literal backspace byte and never
  matched anything). No occurrences here.
- **Non-self-contained headers** — `hdrcheck.py` was run on all five new headers
  *before* building and reported them clean.

**Fact.** The one failure was a transcription slip: `ov11_0230CB88`'s
`EntryOverlay13(a)` fix was found during matching but not carried into the
landing spec, so the landed body called with no argument while the extern
declared one.

**Inference, and the remaining structural weakness.** The matched source and the
landed source are transcribed by hand between two files. Everything that has gone
wrong in three batches of fifty has been at a hand-off the tooling does not
own — this one included. The fix is to have the landing spec consume the matched
sources directly rather than a retyped copy.

2. **`sub_0206C184` and `sub_0206C19C` ignore their first parameter.** Both

   it, which is indistinguishable from `void` in the emitted code.
4. **`struct unk_023890A0`'s size** (`0x44`) is a guess sufficient to compile —
   nothing in these ten functions reads past offset 0.
