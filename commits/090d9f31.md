## Group selection: most 10-runs are not ten functions

**Fact.** The first two candidate groups picked were not decompilable, in two
different ways, and neither is visible without looking at the block bodies.

- **A `.global` sitting mid-body splits one function into two blocks.**
  `ov05_0233CAC8` ends on `bl sub_02046A9C` with no return; `ov05_0233CAD8` is
  the bare epilogue `ldmia sp!, {r3, pc}`.
- **No `.global` on a later entry point merges several functions into one
  block.** `sub_0200A2F4` is three functions: the second and third are
  unreachable from the entry.

**Fact.** Labels cannot separate the merged case from an ordinary loop — a
back-edge branch appears *after* its label, exactly like an unreachable entry
point. Deciding it needs forward reachability from the block entry. A
label-based filter first measured 17.3% "merged"; reachability gives 6.5%, and
classifies correctly the four cases checked by hand (a legitimate loop, a
three-way merge, a fragment, and the `ov05` half-function).

**Fact, tree-wide over 9,758 blocks**: 93.1% clean, 0.4% fragments, 6.5%
merged. Before the classifier only 8 candidate 10-runs looked viable; after it,
**3,643 across 82 files** — the earlier filters were rejecting good work, not
the tree being poor.

## Matching findings

**Fact.** Four functions needed a second pass; three were existing entries in
`docs/MATCHING_TIPS.md` applied unchanged.

| function | from | to | what |
|---|---|---|---|
| `ov18_0238C9B8` | 385 | 0 | arms emitted in source order — write the `<= 0` arm first |
| `sub_02002878` | 500 | 0 | the short `return 0` first gets if-converted; put the long body in the `if` so the target's branch-to-tail survives |
| `ov29_022DC78C` | 435 → 40 → 0 | | needed `mul` + `add`, not a fused `mla`, then a declaration permutation |
| `sub_020028B0` | 235 | 0 | the target reloads a global that any ordinary spelling CSEs |

**Inference, and the reason `ov29_022DC78C` is written oddly.** The target keeps
the byte offset live (`mul ip, lr, r1`, then `add r3, r4, ip`, and later
`add r0, r4, #4` / `add r0, r0, ip`) because it is used twice. Array indexing
(`&p[i].field_0x4`) lets MWCC fold base and offset into one `mla`. What matches
is an explicit offset:

```c
off = i * 0x50;
if (base[off + 4] != 0 && *(s32 *) &base[off + 8] == id) {
    return base + 4 + off;
}
```

This reproduces the bytes but reads unlike ordinary source. **Flagged as a
recovered shape, not a confident reading** — if someone finds a natural spelling
with the same two-use offset, it should replace this.

**`sub_020028B0` matches only with `_0229B0E0` declared `volatile`.** The target
loads `field_0x0` three times where `x++; if (x > y) y = x;` loads it once; with
`volatile` the emitted sequence is instruction-for-instruction identical.
**Inference**: the pair looks like a mutex-guarded current/max counter, which is
a plausible place for `volatile` in period source — but per the honesty rule in
`MATCHING_TIPS.md` this is recorded as a **stand-in**, not recovered code.
Nothing else in the tree reads this global, so the declaration is not forced on
any other translation unit.

## Types

**Fact.** New placeholder structs: `unk_022DC694`, `unk_02353518`,
`unk_0238C950`, `unk_020027E8`, `unk_0229B0E0`.

**Fact.** `struct unk_02353518` is exactly `0x50` bytes, which is the stride the
target multiplies by. `struct unk_0238C950` carries no array stride, so its size
is not load-bearing and the padding between named fields is arbitrary.

**Fact.** The OS wrappers use nitro's own `OSThread` and `OSMutex`. The scratch
used a private `struct OSThread` tag, which is byte-identical (pointer only) but
is a *different type* from `typedef struct _OSThread OSThread` and is rejected
in-tree by `-W error`. Nitro's declarations reach every translation unit through
`-prefix global.mch`, so the correct landing declares none of them locally.

## Tooling

**Fact.** The per-object check (`verify.py`) now also verifies **emission
order**, after `1dea0a25` where every function was the right size *and*
byte-identical while sitting at the wrong address. It reported this batch clean
— size, order, and no pre-existing function changed — in **51 seconds**.

**Fact.** Two tool bugs this batch surfaced, both fixed:

1. The struct-carry regex required `};`, so `typedef struct X { … } X;` made the
   non-greedy body run on to the next `};` and swallow the struct after it. That
   is why `struct unk_020027E8` silently failed to land.
2. `hdrcheck.py` indexes only `include/`, so it reports nitro types as "no
   definition found anywhere". Not a bug to fix, but a false positive to know.
