## Decompiled

**Nothing.** This is a repair commit for damage this branch's own tooling did.

## What happened

**Fact.** Earlier commits stripped `; =VALUE` annotations off loads that survived
a file split, because `precommit.py` **discarded the removals its rule 2 matches
against** -- so a line that was legitimately moved looked like a newly added
comment.

**Fact.** Four such lines remained in the tree. The rest were on code that has
since been extracted to C, so **they left legitimately with their functions**.

| file | line |
|---|---|
| `asm/main_020108B4.s` | `ldr r5, _02010AC4 ; =0x0000270F` |
| `asm/main_02010BC0.s` | `ldr r5, _02010DC8 ; =0x0000270F` |
| `lib/DSE/asm/main_02072054.s` | `ldr r1, _02072140 ; =0x04000208` |

## Why these are exact and not reconstructed by guess

**Fact.** They are **regenerated from each file's own literal pool**, not
recovered from history: the annotation is the `.word` of the label the
instruction references, so it is **derivable and exact**.

**Two earlier attempts were discarded rather than committed.** Both tried to
restore comments by **matching instruction text**, and repeated instructions made
them paste annotations onto unrelated lines -- one restored 384 comments from a
158-comment parent, another reported 205 phantom losses. Neither was landed.

Recording the discarded attempts matters: the successful method is only
trustworthy *because* the failed ones were rejected for a stated reason.

## The convention, measured

**Fact.** Across the two files sampled, **263 of 263** pool-referencing loads
carry an annotation and none lack one. So the convention is unambiguous upstream
and the restoration is not a judgement call.

## Scope

These are **restorations of upstream's own annotations**, not anything authored
here -- which is why they are permitted under the no-comments rule's mechanical
exception.
