## The function

```c
BOOL UFixedPoint64CmpLt(u32 a_hi, u32 a_lo, u32 b_hi, u32 b_lo)
{
    if (a_hi < b_hi) {
        return TRUE;
    }
    if (a_hi > b_hi) {
        return FALSE;
    }
    return a_lo < b_lo;
}
```

A lexicographic compare of two 64-bit values held as high/low word pairs. The
name is pre-existing in the tree; parameter names describe *which word*, not what
the value means.

## The interface, and how each part was established

Three properties of the signature are **facts read off the target**. Each was
tested on its own, with the other two held fixed, against the target asm
(scratch `49HLU`, compiler `mwcc_30_137`):

| property | alternative tested | score | what appears |
|---|---|---|---|
| four separate parameters | two 2-word structs by value | 1115 | `push {r0,r1,r2,r3}` + four `ldr`s |
| parameters unsigned | `s32` high words | 800 | `movlt`/`movgt` instead of `movlo`/`movhi` |
| return word-sized | `bool8` / `u8` | 100 | trailing `and r0, r0, #0xff` |

The matching form scores 0. `BOOL`, `int`, `s32` and `u32` returns are all
word-sized and all score 0 — the bytes cannot separate them.

**`BOOL` over `int` is a choice, not a fact, and is the one line here a reviewer
should feel free to overrule.** It is `typedef int BOOL` in
`lib/include/nitro/types.h:39`, so it is codegen-identical to the `int` this
commit originally used, while naming the function's actual semantics. Likewise
`TRUE`/`FALSE` are `#define`d to `1`/`0` — textually identical to the compiler,
so they change nothing in the output. Both are available in every TU without an
include, since `include/global.pch` force-includes `<nitro.h>` via `-prefix`.

`bool8` was suggested and is **wrong**: it is `typedef u8`, and the truncation it
forces is visible in the table above.

### A correction to this note's earlier version

The first version of this note, and the original commit message, stated the
return was `int` on the grounds that a byte-sized return appends
`and r0, r0, #0xff`. **The conclusion was right and the evidence for it was
not.** It came from a test in which the parameters had *also* been changed to
structs by value, so two variables moved at once and the trailing `and` could
not be attributed to either. The table above is the isolated re-test. The
practice worth keeping: when a note states a byte-level fact, it should come
from a run that changed exactly one thing.

## The caller's stale prototype

`src/main_02001BB4.c` carried its own declaration of this function, written
upstream in `15bc9a91 Decomp IntToFixedPoint64` when only the call site was
available:

```c
extern s32 UFixedPoint64CmpLt(s32, u32, s32, u32);
```

This commit deletes it in favour of including `main_020018D0.h`.

Two observations for a reviewer, one of them a fact and one an inference:

- **Fact:** those signed high words do not describe this function. Compiled
  against the target, `s32` high words yield `movlt`/`movgt` where the target
  has `movlo`/`movhi` (score 800, second row of the table). The name's `U` and
  the unsigned condition codes agree.
- **Inference:** the disagreement was invisible because the two declarations
  never met. They live in different translation units, so no compiler ever saw
  both, and the build could not have flagged it. This is the failure mode the
  workspace's provisional-prototype rule exists to prevent, and it was missed
  when the function first landed — the header was added without removing the
  extern it superseded.

Replacing the declaration changes what the *caller's* TU sees (`u32` where it
saw `s32`), so it is a real change to `main_02001BB4.o`, not just tidying. It is
byte-neutral, and that is verified rather than assumed: both objects recompile
in the build below and the ROM still matches.

## Why this one is worth recording

Its previous writeup in `docs/MATCHING_TIPS.md` claimed the compiler would not
reuse a compare's flags across two same-operand early returns, and listed the
plain "two `if`s" form — the one above — as tried and failed. That conclusion was
produced on compiler `mwcc_20_82`, which is **not** this project's compiler; on
the correct `mwcc_30_137` the same form matches at score 0 immediately.

It was the second entry in that file to blame a compiler limitation and be wrong
for the same reason. The general lesson, now recorded there: when a mismatch is
structural and completely insensitive to changes in the C, suspect the harness
before concluding anything about the compiler.

## Extraction shape

`asm/main_02001A30.s` held only this function, so the file and its `.inc` are
removed rather than split; the function merges into the adjacent
`src/main_020018D0.c` and `main.lsf` drops `asm/main_02001A30.o`.

Note for anyone verifying: `build-tools/build.sh` copies changed files into a
clean clone but does **not** replicate deletions, so that build still assembled
the orphaned `asm/main_02001A30.o`. It was not linked — `main.lsf` drives
linking and no longer lists it — and had it been, the duplicate
`UFixedPoint64CmpLt` symbol would have failed the link rather than passing
silently. The matching ROM therefore took the function's bytes from the C above.
