## `DeleteWindow` explains `_022A7A74`

[`7f6977e2`](7f6977e2.md) landed `sub_0202825C` and `sub_02028270` as a
setter/getter pair over `_022A7A74[2]` **without knowing what it held**, and
named the parameter `index` precisely because that was unknown.

**Fact, read off `DeleteWindow`.** On deleting a window it walks the other
nineteen and, for every active one on the **same background**, computes
`base_tile + width * height`, keeping the largest, with a floor of 1. It then
stores that at `_022A7A74[bg_id]`.

**Inference, and a strong one.** The pair is a **next-free-tile watermark per
background**, and the index is a `bg_id`, not a screen. That also explains
something left unexplained last commit: `NewWindowScreenCheck` sets the entry to
1 when a background has no windows left — **it resets the tile allocator.**

Two commits' worth of unexplained behaviour resolved by one function body. This
is the argument for decompiling callees and their siblings together.

## Four of the eight return their callee's result, and only one shows it

**Fact.** `sub_020280C0` **never touches `r0` after calling `sub_02027E30`**,
which is only consistent with `r0` staying live to the return. Typed `void` it
scored **90**; typed `s32` it scores **5**, and that 5 is the literal-pool
naming described below.

That is a clean, checkable signal: *a scratch register the target conspicuously
avoids is a live value.*

**Fact, and the honest half.** `sub_0202810C` and `sub_0202811C` are tail calls
that **score 0 either way**, so their own bytes settle nothing. They are typed
`s32` to match the family.

**A reviewer should read those two as following the family, not as read off the
target.** Same underdetermination as the forwarders in
[`d4b2c2fc`](d4b2c2fc.md) — except here a sibling that *is* determined makes
the guess much better supported than usual.

## `DeleteWindow` needed two things past the obvious form

**1. Operand order in the background comparison.** It is
`bg == p->template.bg_id`, **not** the reverse — worth 5 on its own, and
consistent across every other variant tried.

**2. Declaration order of the four locals: `i, top, p, bg`.** All **24
permutations were tried**; they range from **0 to 140**, and only that one
reaches 0.

The instructive part: at the best pre-permutation score of **35, every
instruction already matched.** The entire remaining difference was **which
register held `bg` and which held `i`** — 7 rows at 5 apiece. A pure
register-allocation gap, closed by declaration order alone with no change to the
code.

Worth contrasting with `DseTrackEvent_SetupKeyBendLfo`
([`59fad373`](59fad373.md)), which is stuck in exactly this state at 65 and where
local reordering was tried but **not exhaustively**. Enumerating all permutations
is cheap and should be the default move when the instructions already match.

## Three land at 5 and 10, all of it literal-pool naming

**Fact.** `sub_020280C0` scores 5; `sub_0202812C` and `sub_02027A08` score 10.
The target writes `_022A8990`, `_022A8992` and `_022A88E4` where C indexing
`WINDOW_LIST` emits `WINDOW_LIST+0xb4`, `+0xb6` and `+0x8`.

Same address, identical bytes once linked, flat 5 per word — the phenomenon
documented in [`7f6977e2`](7f6977e2.md) and in `docs/MATCHING_TIPS.md`. The
arithmetic checks out against the bss `.space` runs, and the build printed
`build/pmdsky.us/pmdsky.us.nds: OK`.

## A new placeholder struct

**Fact.** `struct unk_020AFD4C` is introduced for the 12-byte object at that
address, **sized by the gap to `_020AFD58`**. Only its word at `0x8` is touched
here — a bitmask that five of these functions set a bit in, **indexed by
`bg_id`**.

**Inference.** A per-background "needs redraw" mask. Consistent with every use
seen, but not established; the bytes at `0x0`-`0x7` are untouched here and left
as filler rather than described.

## Declaration hygiene

**Closed.** `DeleteWindow` had a provisional declaration in
`include/main_0202AAA8.h` from the menu commits, with **three decompiled
callers**. Replaced by an include of the new header; all three objects rebuild
and the ROM still matches.

**Made worse, knowingly.** `sub_0202836C` now has a **fifth** declaration in the
tree, and the existing four **do not agree**:

| file | declared as |
|---|---|
| `overlay_15_0238AE6C.c` | `int` |
| `overlay_24_end.c` | `s32` |
| `overlay_24_init.c` | `s8` |
| `overlay_25_init.c` | `s8` |
| *this commit* | `s32` |

It is declared in the **caller's own header** rather than in `window.h`,
specifically so that no overlay including `window.h` sees a conflicting one —
`include/overlay_24.h` does include it, and `overlay_24_init.c` says `s8`. All
five should collapse into one header when `sub_0202836C` lands.

## Open questions

- **`sub_02027E30`'s return type is inferred from its caller**, not from its own
  body, which is still asm. `s32` is what makes `sub_020280C0` match; that is
  evidence, but of the caller.
- **`sub_02028080`'s and `sub_02027A08`'s second parameters** are stored with
  `strb` and so are width-underdetermined; typed `s32` on the no-truncation
  default. Their callers are still asm and were not read. This is the same gap
  that produced the cascade in [`b6faa493`](b6faa493.md).
- **`sub_02027A08` calls `sub_02027B88` with `r0` holding `&_020AFD4C`**, which
  reads as a dead argument; it is declared `void sub_02027B88(void)`. If that
  function turns out to take a parameter, this call site is where to check.
