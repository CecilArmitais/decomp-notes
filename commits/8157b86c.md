## `sub_02065B14`

**Fact.** Returns `0` for an id of `-1`; otherwise a 16-bit field of the
`ENTITIES` record for that id.

**Fact, read off the asm.** The record is 12 bytes -- the stride comes from the
`smlabb` multiplier -- and the returned field's offset from the `ldrh`
displacement. That read is *unsigned*, which matters two commits later when two
sibling fields turn out to be signed.

**Inference, unasserted.** What the fields mean. The record type is declared
`struct unk_020A7FF0`, fields named for offsets. `ENTITIES` already existed and
keeps its name.

## `GetScriptEntityMonsterId`

**Fact.** It takes the address of its own parameter and of an `s16` local, hands
both to `sub_0206549C`, and returns the local. Passing `&parameter` is not a
stylistic choice -- it is what the target does.

**Provisional at the time.** `sub_0206549C` was still asm with no header, so its
prototype was declared alongside, to be moved when a better home appeared. That
happened in [`39a8db1b`](39a8db1b.md).

## The history a reviewer should know

This is the function behind `docs/MATCHING_TIPS.md` -> *A wrong compiler id looks
exactly like unmatchable C*. An earlier attempt tried dozens of C variants and
flag permutations, every one returning **the same score**, because the scratch
was configured with the wrong compiler id. Under the correct `mwcc_30_137` the
most obvious possible C matches at score 0.

**The lesson is about the harness, not the function** -- and it is the reason
this project treats a wrong compiler id as the first thing to suspect when a
mismatch is completely insensitive to the C.
