## What this is

One function: `SetLeaderAction` at `0x022F0EDC`, **1806 instructions**, the
largest single function on this branch by a wide margin. It reads the player's
input every frame and turns it into the leader's action — walking, turning,
attacking, using a move, talking, the ally-swap check, menus and the touch
screen.

**Fact.** It sits in the middle of `asm/overlay_29_022F05B4.s`, so
`extract_function.py` split the file: the tail became
`asm/overlay_29_022F2B3C.s` and both objects were added to `main.lsf`.

## How it was matched

**Fact.** Final state: score **0** on a local scratch (1816/1816 rows including
the 10 literal-pool words, 168/168 call sites, frame `sub sp, sp, #0xdc`), then
a matching build of the committed tree.

The long grind is recorded elsewhere and is not repeated here. The parts a
reviewer might want to push back on:

**The last five rows were a community suggestion, not our own work.** After the
candidate had been stuck for a long stretch at "everything matches except one
register", the fix came from outside: mask the second d-pad value **in place**
rather than into a second named variable.

```c
/* stuck: the masked value gets its own web and truncates in place  */
h1 = b1 & 0xF0;
h2 = b2 & 0xF0;
...
if (h2 == 0x40) { dir = 4; }

/* 0: b2 keeps its own register, so the truncation writes b2's       */
h1 = b1 & 0xF0;
b2 &= 0xF0;
...
if (b2 == 0x40) { dir = 4; }
```

**Inference, but well supported.** The form is *asymmetric* and that is why it
was missed: masking **both** values in place is byte-identical to masking
neither, and copying first (`h2 = b2; h2 &= 0xF0;`) is byte-identical too,
because the mask then lands on a fresh web that copy propagation collapses. Only
"one value keeps its own variable, the other gets a name" reproduces retail's
pair of registers.

## Type corrections, and the evidence for each

**Fact, from the bytes.** Each of these was required to match, and each was
checked in isolation.

| change | evidence |

| `display_data.leader_target_direction_mirror`: `enum direction_id` → `u8` | with the enum type MWCC folds the stored `0xFF` to `-1` and reuses a register that already holds it, dropping retail's `mov r0, #0xff`; measured, 285 rows |
| `CanMonsterMoveInDirection`'s `direction` parameter: `u16` → `s32` | a `u16` parameter narrows the argument (`lsl #16; lsr #16`) at the new call site, where retail passes `mov r1, r7` unchanged. Any word type matches; `enum direction_id` does not |

**Inference.** The last one is the only change here that touches a function
outside this commit's own work. `CanMonsterMoveInDirection` was already
decompiled and matching with the `u16` parameter, and it still matches with
`s32` — its own body cannot tell the two apart, and neither can its other
caller, which passes a `u8` field. This call site is the first that passes a
word-sized value, so it is the first that can distinguish them. A reviewer who
prefers upstream's `u16` should know that keeping it forces the call site to
narrow, and retail does not.

## Things a reviewer should be sceptical of

- **Two `volatile` stand-ins remain in the source** — a `(volatile struct move *)`
  cast at the move-flags site, and volatile-qualified accesses in the entry
  block. They reproduce retail's exact load/store pattern where no ordinary
  respelling does. **They are almost certainly not what the original source
  said.** Treat them as evidence of a mechanism (these accesses do not CSE), not
  as recovered code, and replace them if a natural construct with the same
  property is found.
- **`DUNGEON_PTR` is declared here as a scalar** (`extern struct dungeon
  *DUNGEON_PTR;`) while `dg_camera.c`, `dg_uty.c` and
  `overlay_29_023000E4.c` declare it as an array and index `[0]`. **The two are
  not byte-interchangeable at this call density** — the array spelling scores
  10334 here. There is no header declaration of the symbol to contradict, but
  the disagreement is real and deliberate, and it should probably be settled
  tree-wide rather than left to each translation unit.
- **The scan loop uses its own variable** (`for (j = i; j < 4; j++)`) where the
  register evidence suggests retail reused `dir`. Splitting it is what unwound a
  four-register rotation. It is a colouring device that happens to match; the
  original may well have been written the other way.
- **Local names are placeholders** (`local_5c`, `pos_9e`, `r8flag`, …) derived
  from stack offsets, not from any understanding of what they hold.
- **`struct unk_022F0BAC`** is new, named for the function that takes it
  (`GetEntityTouchscreenArea` at `0x022F0BAC`), with `field_0x0`…`field_0xc`.
  Four `s32`s; nothing here establishes what they mean beyond being a
  screen-space rectangle passed to `CheckTouchscreenArea`.

## Not verified: the JP build

**Fact.** Only the US target was built. **JP is expected not to match.**

The asm this commit replaced carries `#ifdef JAPAN` variants that go well beyond
the message-id offset the source keeps (`SET_LEADER_ACTION_DATA_OFFSET`, read
directly off that asm as `-0x2C1`):

- a display-data offset of `+0x178` where US uses `+0x21c`;
- a byte read at `[r0, #0x19a]` where US reads `[r0, #0x23e]`;
- `sub r0, r0, #3` where US has `sub r0, r0, #2`;
- two sites where JP and US swap which constant is loaded.

Making `make jp` match needs region-conditional C that was not written or
tested. EU takes the non-JAPAN path throughout and should be unaffected, but
that was not built either.

## The process failure worth recording

**Fact.** The scratch scored 0 while the real build produced a function **4
bytes longer** than retail — one extra instruction — and five modules failed
their checksums. The cause was the scratch context: it had been hand-assembled
rather than generated, and it declared `CanMonsterMoveInDirection` without a
prototype, so the scratch never emitted the narrowing the real headers demand.

Four other context lies surfaced earlier as compile errors (`field_0x1d8`
typing, the mirror field, four missing prototypes, two enum conversions). This
one was silent, which is worse.

Regenerating the context from the real headers reproduced the discrepancy
immediately and named it in one diff. **The lesson is the one already in
`MATCHING_TIPS.md` under "A cut-down scratch context can make wrong C score 0",
and it was not followed.** A scratch context should be generated from the real
headers before a large function is landed, not after it fails.

**Tooling defect found.** `tools/m2ctx/m2ctx.sh` passes `-include global.h`,
which does not exist in this repo — the project uses `include/global.pch`. The
script does not fail loudly; it emits a 12-line context consisting of nothing
but predefined macros. Substituting `include/global.pch` makes it work.
