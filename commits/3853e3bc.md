This is the largest commit on the branch: **119 functions**, four `.s` files
emptied, four objects out of `main.lsf` and none added.

**The function count is the least interesting thing about it.** It carries
**four shared-type changes** to three headers that most of the tree reaches,

items are where a reviewer's time goes; the 119 bodies are the easy part. Each
is argued below, with what was *measured* separated from what was *asserted*.

One of the five arrived with a **wrong supporting claim**, caught only after
the fact. It is written up in full in §1.4 — including the method defect that
produced it — because the defect is transferable and the next census will hit
it again.

# 1. Shared-type change: `struct monster` 0x19C..0x20F becomes an array

`include/dungeon_mode.h`. A new type is added immediately above `struct
monster`, and **112 member lines are replaced by three**:

```c
struct unk_02304D20 {
    struct position pos;
    s32 field_0x4;
    s32 field_0x8;
    s32 field_0xc;
    s32 field_0x10;
    s32 field_0x14;
    s16 field_0x18;
    u8 field_0x1a;
    u8 field_0x1b;
};

/* in struct monster, replacing `struct position pos`, 110 `u8 field_0x…`
   placeholders and `u16 walk_anim_frames_left` */
    struct unk_02304D20 field_0x19c[4];
    s16 field_0x20c;
    s16 field_0x20e;
```

Evidence and the measurement harness: `wip/overlay_29_023047DC_all/STATUS.md`
§6b and §6's layout proof; dead ends in that directory's `LEDGER.md`.

## 1.1 Why the tree had to change

**Fact, the stride.** `ov29_02304D20` computes

```
add r0, sb, #0x19c
mov r1, #0x1c
smulbb sl, r3, r1
add r7, r0, sl
```

and `DisplayActions` computes `add r3, sb, #0x19c` / `mov r0, #0x1c` /
`smlabb r8, r2, r0, r3`. That is a **stride of 0x1C from `monster + 0x19C`**,
indexed by a 16-bit value (`smulbb`/`smlabb` are 16×16 multiplies).

**Fact, the bound is 4.** `ldrsh …,[monster + 0x20c]` is compared `>= 4`, and
the case ladder loops to `j < 3`. `4 * 0x1C = 0x70`, i.e. `0x19C`..`0x20B`, and
`0x20C`/`0x20E` are the two `s16`s that follow.

**Fact, the element's field offsets** are read off the accesses: `strh` at
+0/+2, `str`/`ldr` at +4/+8/+0xC/+0x10/+0x14, `ldrsh`/`strh` at +0x18, `strb` at
+0x1A.

**Fact, two corroborations that the base is 0x19C and not something later.**
`monster + 0x1AC` / `+0x1B0` — element **0**'s `field_0x10`/`field_0x14` — are
written directly in case 2; and `monster + 0x1B4`, the header's existing
`walk_anim_frames_left`, is element **0**'s `field_0x18`, written by the same
statement that writes `field_0x19c[j].field_0x18` for the other elements. The
old flat names and the new array are therefore describing the same bytes, and
element 0 is what the header already had names for.

**Inference:** what any of this *means*. The type stays `struct unk_02304D20`
and the members stay `field_0x<off>`, claiming nothing. `pos` keeps its name
only because `struct position pos` was already in the tree at that offset and
existing names are kept.

## 1.2 Layout preservation — measured with the real compiler

`wip/overlay_29_023047DC_all/tools/layoutproof.py` compiles **one probe
function** that materialises `sizeof(struct monster)`, `sizeof(struct entity)`,
`sizeof(struct position)` and the offsets of **31 surviving members on both
sides of both changed regions**, against the **unpatched** and the **patched**
context, and compares the emitted instruction text:

```
unpatched: 70 instructions
patched:   70 instructions
LAYOUT PRESERVED: the probe compiles to IDENTICAL code against both contexts
```

**Fact.** That is a measurement with `mwcc_30_137`, not an assertion — if any
size or offset had moved, the folded constants would differ, and the tool exits
non-zero printing the differing rows. The arithmetic agrees independently:
0x19C..0x20F is 4 + 110 + 2 = **116** bytes before and 0x70 + 2 + 2 = **116**
bytes after.

**Fact.** `tools/patchhdr.py --verify` separately proves the scratchpad context
reproduces `pmd-sky`'s generated context **byte for byte** (380322 chars) when
unpatched, so the only difference between the two contexts is the two edits.

## 1.3 Blast radius — and why the build really does settle this one

The absorbed names (`pos`, `walk_anim_frames_left`, `field_0x1a0`..`field_0x20b`,
`field_0x20d`, `field_0x20f`) are **deleted outright** from `struct monster`.

**This is the rare case where the build is a complete detector.** CLAUDE.md's
landing checklist is right that a build cannot catch a stale *declaration* — two
prototypes in two translation units never meet. But a **removed struct member**
is different: any surviving `struct monster *` expression naming one is a hard
compile error in whatever TU contains it. All three ROMs build, so **no
compiled translation unit reads any of those names through a `struct monster *`**
— fact, and not one that rests on a grep.

Two name collisions that a text search sees and the compiler does not:

* **Fact.** `src/main_0203D538.c` uses `field_0x1a0`, `field_0x1ab`,
  `field_0x1b5`, `field_0x1bf` — on an unrelated struct. Untouched, still builds.
* **Fact.** `include/dungeon.h:348-349` declares `u8 field_0xac; u8 field_0xad;`
  on a *different* struct from the `struct entity` members retyped in §2. The
  §2 blast-radius grep identified that correctly; §1.4's did not do the
  equivalent.

## 1.4 **The wrong claim, and the method defect behind it — read this one**

`wip/overlay_29_023047DC_all/STATUS.md` §6b states:

> **Blast radius: one line.** A scripted scan of every `.c` in `src/` for
> `->pos`, `->walk_anim_frames_left` and `->field_0x1a0`..`field_0x20b` **on a
> variable declared `struct monster *`** finds exactly one site:
> `src/dungeon_util_2.c:20: return IsPositionInSight(&monster->pos, …)`
> which becomes `&monster->field_0x19c[0].pos` — the same address, byte-neutral.

**That is wrong, and the fix was correctly not applied.** `src/dungeon_util_2.c`
does not appear in this commit's diff at all.

**Fact**, the file as it stands:

```c
17: extern void SetPreprocessorArgsStringToName(struct preprocessor_args *preprocessor_args,
18:         s32 pos, struct monster *monster, u32 param_4, u8 name_type);
19: bool8 CanTargetPosition(struct entity *monster, struct position *position)
20: {
21:     return IsPositionInSight(&monster->pos, position, HasDropeyeStatus(monster));
```

The `monster` at line 21 is the **`struct entity *`** parameter declared on line
19. `struct entity` has its own `struct position pos` at 0x4, untouched by this
commit. `HasDropeyeStatus` takes `struct entity *`
(`include/dungeon_pokemon_attributes_1.h:14`) — fact, and it is handed the same
variable, so the type is pinned twice over.

**The mechanism, and this is the transferable part.** The scan was described as
type-aware, and it was — at **file** granularity. It found a *declaration* of a
name `monster` with type `struct monster *` in this file (line 17, a **parameter
name inside an unrelated `extern` prototype**), then matched `monster->pos`
elsewhere in the same file and attributed the type to it. **Two different
variables shared one name, one of them in a prototype that declares no variable
at all.**

Consequences worth stating plainly:

* Had the "fix" been applied it would have been a **hard compile error**
  (`struct entity` has no `field_0x19c`), so this particular instance could not
  have shipped silently. **That is luck, not method** — the same conflation in
  the other direction (a real `struct monster *` user the scan *misses* because
  the name it keys on is spelled differently in that function) produces a **false
  negative**, and a false negative here is exactly the failure mode nothing
  downstream contradicts.
* A **function-scoped** re-scan — resolve each use against the innermost
  declaration actually in scope, and never treat a prototype's parameter name as
  a declaration — finds **zero** genuine users. The three passing builds
  corroborate that independently (§1.3).
* This is the second census defect recorded on this branch. `146982f0` §4 found
  that a **line-oriented** grep misses declarations that wrap across lines, and
  the census tools were made multiline-aware in response. This one is orthogonal:
  multiline-aware and *still* wrong, because the granularity of the type lookup
  was the file rather than the scope. **Fixing the regex did not fix the
  method.**

**Not checked:** whether any other blast-radius claim on this branch used the
same file-granularity type attribution. The four censuses in this commit's wips
are separate scripts (`cand/census.txt`'s brace walker, `tools/census.py` in two
flavours); only the `struct monster` one is known to have had this defect, and
the others were not re-audited for it.

**Not checked** for this type. Unlike the `struct unk_02337EE8` case in

# 2. Shared-type change: `struct entity::field_0xac` + `field_0xad` → one `s16`

`include/dungeon_mode.h:629`.

```c
/* before */          /* after */
    u8 field_0xac;        s16 field_0xac;
    u8 field_0xad;
```

**Fact, the read.** `ov29_02304830` loads `entity + 0xAC` with
`ldrsh r6, [r5, #0xac]` — 16-bit, **signed**. MWCC takes a load's width and
signedness from the declared member type alone, so no pair of `u8` members and
no cast at the read site produces it. This is `docs/MATCHING_TIPS.md` →
*An implicit-conversion error is a WRONG DECLARATION, not a missing cast*
applied to a read rather than a call.

**Fact, layout-preserving by construction and by measurement.** Two adjacent
`u8`s replaced by one naturally-aligned `s16` at the same offset: nothing after
it moves. Covered by the same `layoutproof.py` probe as §1 (which spans both
changed regions), and by all three builds.

**Fact, blast radius: one line, and it is the new one.** After landing,
`grep -rn "field_0xac\b\|field_0xad\b" src/ include/` returns only
`src/overlay_29_023047B8.c:80` (`a = entity->field_0xac;` — the new use),
`include/dungeon_mode.h:629` (the declaration) and `include/dungeon.h:348-349`
(a **different struct** that happens to use the same placeholder names — see
§1.3). `field_0xad` has no remaining users at all.

**Inference:** nothing about what 0xAC means. It keeps its offset-derived name.

# 3. Shared-type change: `struct bag_items` loses `fill2`/`fill3`/`fill4`

`include/item.h`. Three anonymous padding blobs are replaced by the ten members
behind them, and `struct bulk_item` moves **above** `struct bag_items` because
it is now a member type.

```c
-    u8 fill2[0xFA3];
-    u32 *field_0x132C;
-    u8 fill3[0x40];
-    u32 *field_0x1370;
-    u8 fill4[0x1E];
+    u8 field_0x389;
+    s16 field_0x38A[1000];
+    u16 field_0xB5A[1000];
+    u8 field_0x132A;
+    u8 field_0x132B;
+    struct bulk_item *field_0x132C;
+    struct bulk_item field_0x1330[2][8];
+    struct bulk_item *field_0x1370;
+    struct bulk_item field_0x1374[2][4];
```

Evidence: `wip/main_0200F884_all/STATUS.md` §3.

## 3.1 Why — it is not tidying, the storage half of the file is unaddressable without it

**Fact.** Eleven of the 38 functions read or write two 1000-entry arrays that sit
*inside* `fill2`. There is no C expression for a member of an anonymous `u8`
blob, so the whole storage half of `asm/main_0200F884.s` cannot be written
against the header as it stood.

## 3.2 Every offset is read off the asm

All **fact**:

* **`field_0x38A[1000]`, `s16`.** Every storage read is
  `add rX, BAG, i, lsl #1` / `add rX, rX, #0x300` / `ldrsh rX, [rX, #0x8a]`.
  The `0x300 + 0x8a` split is **forced**: ARM addressing mode 3 (`ldrsh`/`ldrh`/
  `strh`) carries only an 8-bit immediate, so `0x38A` cannot be one
  displacement. `ldrsh` rather than `ldrh` fixes the element **signed**;
  `cmp rX, #0x3e8` in nine separate loops fixes the count at **1000**.
* **`field_0xB5A[1000]`, `u16`.** `add rX, rX, #0xb00` / `ldrh rX, [rX, #0x5a]`.
  **`ldrh` at five independent call sites** fixes it unsigned. The one `ldrsh`
  site is a deliberate reinterpretation — see §3.4.
* **The extents chain exactly**: `0x38A + 2000 = 0xB5A`, `0xB5A + 2000 = 0x132A`.
* **`field_0x1330[2][8]` of `struct bulk_item`.** `AllKecleonShopsZInit`:
  `add r3,r3,#0x330` / `add r3,r3,#0x1000` (= `+0x1330`), `add r3,r3,r2,lsl #5`
  (outer stride 0x20 = 8×4, outer bound `cmp r2,#2`), then `strh` at `[r3, j*4]`
  and `[r3 + j*4, #2]` (inner bound `cmp r6,#8`). A 4-byte element with two
  16-bit halves at +0/+2 **is** `struct bulk_item`. It replaces `fill3[0x40]`
  exactly (2 × 8 × 4 = 0x40).
* **`field_0x1374[2][4]`.** Same shape with `#0x374`, `lsl #4` (stride 0x10),
  `cmp r6,#4`. 2 × 4 × 4 = 0x20, which replaces `fill4[0x1E]` **plus the two
  bytes of alignment padding** MWCC was already inserting before `maybeMoney` —
  which is why `maybeMoney` does not move.
* **`SpecialEpisodeKecleonShopZInit` corroborates the second dimension**: it uses
  `#0x350` (= `0x1330 + 0x20`, row **1**) and `#0x384` (= `0x1374 + 0x10`, row
  **1**).
* **`field_0x132C` / `field_0x1370` are `struct bulk_item *`, not `u32 *`.**
  `SetActiveKecleonShop` stores `&field_0x1330[idx][0]` into 0x132C and
  `&field_0x1374[idx][0]` into 0x1370. The `u32 *` in the tree was a placeholder
  written from a call site; the store is what fixes it.

**Inference, and the weakest link in this section:** the **outer bound of 2** on
both 2-D arrays rests on `cmp r2, #2` in `AllKecleonShopsZInit` alone. Nothing
outside this file indexes either array, so there is no second consumer to
corroborate it. Flagged in the wip's own open questions and repeated here.

## 3.3 Layout preservation — measured, read out of mwccarm's own output

`wip/main_0200F884_all/tools/measure.py` compiles `int m(void){return (int)(EXPR);}`
per expression and recovers the folded constant from the compiler's output. **It
asserts a control expression whose value is known a priori first**, so a
mis-decoded column fails loudly instead of returning a plausible number — that
self-check is what makes the table below evidence rather than a reading.

| expression | before | after |
|---|---|---|
| `sizeof(struct bag_items)` | `0x13B4` | **`0x13B4`** |
| `&…->bag_items` | `0x384` | `0x384` |
| `&…->field_0x132C` | `0x132C` | **`0x132C`** |
| `&…->field_0x1370` | `0x1370` | **`0x1370`** |
| `&…->maybeMoney[0]` | `0x1394` | **`0x1394`** |
| `&…->field_0x13A0` | `0x13A0` | **`0x13A0`** |

**Fact.** `fill2`/`fill3`/`fill4` are named nowhere outside the struct
definition, so their removal touches nothing; every surviving member keeps its
offset and the struct keeps its size, so every other user of `struct bag_items`
is byte-neutral by construction.

## 3.4 The cascade, and the one kept cast

**Fact.** Retyping the two pointers forces a return-type change on two landed
one-liners, which is why `src/main_02010898.c`, `src/main_02010BA4.c` and both
their headers are in the diff:

```c
-u32* GetCurrentKecleonShop1ItemByIndex(s32 idx)
+struct bulk_item* GetCurrentKecleonShop1ItemByIndex(s32 idx)
```

Both headers gain `#include "item.h"` to stay self-sufficient.

**Byte-neutrality is measured, not argued** — `tools/shopcheck.py` compiles both
spellings and compares mwccarm's output instruction by instruction: **14
instructions each, byte-identical**. *(Fact.)* **Fact:** neither function has a C
caller — the only callers are untyped `bl` sites in `asm/overlay_22.s` — so the
cascade stops there.

**One explicit cast is kept, and it is worth a reviewer's eye:**

```c
/* CountNbOfValidItemsInTimeDarknessInStorage */
id = (s16)BAG_ITEMS_PTR_MIRROR->field_0xB5A[i];
```

**Fact:** `field_0xB5A` is `u16` (five `ldrh` sites), but this one site reads it

and that is why one site reinterprets it signed. **Fact:** dropping the cast (an
implicit `u16` → `s16`) also scores 0 — the cast is there to make the
reinterpretation visible, not to make it match.

# 4. Shared-type change: `window.h`'s `portrait_params` gains a `Point`

`include/window.h`. Two `u32` members become one `Point`, and `Point`'s typedef
moves above `portrait_params` because it is now used there.

```c
-    u32 offset_x;  // 0x4: Tile offset (x / 8) in the X axis to draw the portrait
-    u32 offset_y;  // 0x8: Tile offset (y / 8) in the Y axis to draw the portrait
+    Point offset;
```

**This is the strongest-evidenced change on the branch** — see §4.2 — and it is
also the one that reaches the most unrelated code, since `window.h` is a
general-purpose header.

## 4.1 Why — two independent facts, both from the asm

1. **Fact, the call site uses `ldm`.** `UpdatePortraitBox` loads the pair with
   `add r1, r4, #0xc` / `ldm r1, {r1, r2}`. `docs/MATCHING_TIPS.md` →
   *"`ldm` means your object starts at offset 0"* records that MWCC emits `ldm`
   only when the base register points exactly at the object. **Fact:** two
   separate member reads give two `ldr`s and **did** — that spelling scored
   **860**, with five structural rows (`wip/main_0202F190_all/LEDGER.md`).
2. **Fact, the callee's own prologue.** `sub_02028770`
   (`asm/main_02028354.s:318`) opens `stmdb sp!, {r0, r1, r2, r3}` and later
   re-reads its arguments from the stack home with `ldr r0, [sp, #0x14]` /
   `ldr r2, [sp, #0x18]` — MWCC's shape for a **struct passed by value and
   re-read from its home**, not for two separate word parameters.

**Inference:** that the 8 bytes are specifically a `Point` rather than any other
8-byte struct. `Point` (`{s32 x; s32 y;}`) is the shape and is already the tree's
name for it — but the asm proves *an* 8-byte struct, not *this* one.

**Fact, a note on signedness:** the members were `u32` and `Point`'s are `s32`.
Nothing in this group's measurements separates them, and the 25-TU object check
below says nothing moved. **Not checked:** whether any *future* code that does
signed arithmetic on `offset.x` would have wanted `u32`.

## 4.2 Blast radius — verified at the OBJECT level across all 25 reachers

This is the part to trust most, and it was not a grep.

* **Fact.** `wip/main_0202F190_all/tools/reach.py` walks the real `#include`
  graph — every `#include "..."` in every `src/*.c` and `include/*.h`, resolved
  against the same directory list the build's `-i` flags use — and finds **25
  translation units** that reach `include/window.h`.
* **Fact.** `tools/objcheck.sh` compiles all 25 with the build's real flag
  string, once against the tree as it stands and once against the staged
  `landing/` tree (retyped `window.h`, the `overlay_29_0234BA54.c` member
  spelling, the two deleted `extern`s in `overlay_11_02307334.c`), and diffs the
  object sha1s:

  ```
  IDENTICAL: all 25 window.h includers compile to byte-identical objects
  ```

  The two sha1 lists are preserved in `objcheck_before.log` / `objcheck_after.log`
  (50 lines = 25 objects × 2).

**The honest caveat, stated rather than buried: that run is `-DNORTH_AMERICA`
only.** *(Fact — the define is hard-coded at `tools/objcheck.sh:72`.)* The flag
set is region-independent and `portrait_params` sits in no region `#ifdef`, but
EU and JP were not compiled at the object level. Their evidence is the two ROM
builds.

## 4.3 The one file that names the members, measured against retail bytes

**Fact.** `src/overlay_29_0234BA54.c:52-53` is the **only** other place in the
tree that names `offset_x`/`offset_y`. `InitPortraitDungeon` becomes
`portrait->offset.x = 2;` / `portrait->offset.y = 9;`.

**Fact.** `tools/blast_probe.py` scores that function against its **real target
asm, recovered from git** (`e6530b43^`, the commit that landed it) — so this is
a before/after against retail bytes, not a self-comparison:
`BEFORE score 0 / AFTER score 0`.

## 4.4 A fallback exists, and both arms emit the same bytes

**Fact.** `wip/main_0202F190_all/cand/fallback_no_retype.c` is the complete
alternative — `window.h` untouched, the two call sites written
`sub_02028770(w->id, *(Point *)&box->field_0x8.offset_x);` — measured at score 0
for all four affected functions. **So this is a header-design decision, not a
matching one.** The retype was shipped because a cast there would freeze a
declaration the asm shows to be wrong; `sub_02028770`'s own struct parameter is
forced by the `ldm` either way and is not optional.

A reviewer who dislikes the shared-type change can take the fallback without
losing a single byte. That is unusual on this branch and is worth knowing.

```c
extern s32 PlayEffectAnimationPixelPos(struct pixel_position *pixel_pos, s32 effect_id,
                                       s32 param_3);
void ov29_022E563C(struct pixel_position *pixel_pos) { PlayEffectAnimationPixelPos(pixel_pos, 0x90, 1); }
```

Evidence, all **fact**:

* The callee's body (`asm/overlay_29_022E37DC.s:28`) reads `ldr r0, [r5]` and
  `ldr r2, [r5, #4]` — two **words**. `struct pixel_position` is `{u32 x; u32 y;}`;
  `struct entity` has `enum entity_type` at 0 and `struct position pos` at 4,
  which would not be read as two words.
* It returns a value on **both** paths (`ov10_022BF2B4`'s result, or `mvn r0, #0`),
  so `void` is wrong.
* `ov29_022E563C`'s own original asm (recoverable at
  `c4338759^:asm/overlay_29_022E37DC.s:2530`) is a **pure tail-call forwarder** —
  `ldr ip, =PlayEffectAnimationPixelPos; mov r1,#0x90; mov r2,#1; bx ip` — so its
  parameter type simply **is** the callee's first parameter type. The
  `struct entity *` was a placeholder someone wrote from a call site.
* Its two call sites are asm-only and both build the argument in place
  (`mov r2, r1, lsl #8` / `str r2, [sp]` / `add r0, sp, #0`) — a pixel position.
* **Byte-neutrality is measured**: `tools/origcheck.sh` compiles the file as it
  was and as the landing leaves it and compares `ov29_022E563C` word for word —
  identical in NORTH_AMERICA, EUROPE **and** JAPAN.

**This is the same failure mode CLAUDE.md warns about** — a prototype guessed
from a call site, propagating into the signature of the function that forwards
to it. Here it propagated exactly one hop and was caught because the new
`ov29_022E5BD8` calls the same function properly and returns its result.

## 5.4 **A disagreement this commit deliberately ADDS** — new, and easy to miss

`src/main_0202F180.c` now carries eight file-scope `extern`s that **contradict a


`sub_02026184` with **one** parameter, and three with `void` returns. **Fact**,
the evidence that the header is the wrong one: each forwards to a `sub_02020…`

real matching task that was **not measured**. But it should be visible in the

declaration and a wrong one for the same four functions, and the corrected copy
is the one *not* in a header.
